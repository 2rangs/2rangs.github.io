
스킬을 만들고 한두 번 써 보면 "잘 되네" 싶은 순간이 온다. 그런데 그 판단은 대개 내가 방금 쓴 프롬프트와, 스킬을 작성하며 쌓인 대화 맥락을 바탕으로 한다. 팀원이 다른 말투로 요청하거나, 새 세션에서 요청하거나, 다른 모델로 돌리면 결과가 달라진다.

Claude Code 문서는 이 점을 짧게 짚는다. 스킬이 트리거됐다면 Claude가 스킬을 찾았다는 뜻일 뿐, 의도한 일을 했다는 뜻은 아니다. 그래서 두 가지를 따로 재야 한다. 호출되어야 할 프롬프트에서 호출되는지, 호출됐을 때 결과가 기대와 맞는지다. 이 글은 작성 시점의 공식 문서(Claude Code 스킬 문서, Agent Skills 모범 사례, agentskills.io의 평가 가이드)를 바탕으로 그 방법을 정리한다.

## 평가를 먼저 만든다

모범 사례 문서는 순서를 바꾸라고 권한다. 지시를 길게 쓰기 전에 평가부터 만들라는 것이다. 머릿속으로 짐작한 요구가 아니라 실제 문제를 풀고 있는지 확인하기 위해서다. 문서가 제시하는 평가 주도 개발의 흐름은 다음과 같다.

- **빈틈 찾기**: 스킬 없이 대표적인 작업을 Claude에게 시키고, 구체적인 실패나 빠진 맥락을 기록한다.
- **평가 만들기**: 그 빈틈을 겨냥한 시나리오를 세 개 만든다.
- **기준선 측정**: 스킬 없이 돌렸을 때의 성능을 잰다.
- **최소한의 지시 작성**: 빈틈을 메우고 평가를 통과할 만큼만 쓴다.
- **반복**: 평가를 돌리고, 기준선과 비교하고, 다듬는다.

[디자인 시스템 스킬](/blog/design-system-skill/)이라면 이렇게 시작할 수 있다. 스킬 없이 "버튼 컴포넌트에 위험 상태를 추가해 줘"라고 시켜 보면 색상을 hex 값으로 하드코딩하거나 이미 있는 토큰을 무시하는 실패가 나온다. 그 실패가 첫 평가 시나리오가 된다.

모범 사례 문서는 이런 평가를 돌리는 내장 방법이 현재는 없다고 밝힌다. 평가 체계는 직접 만들어야 하고, 그 평가가 스킬 효과를 판단하는 기준이 된다.

## 호출 평가: description이 제때 걸리는가

[SKILL.md 잘 쓰기](/blog/writing-skill-md/)에서 다뤘듯 스킬 호출은 description이 좌우한다. 에이전트는 시작할 때 각 스킬의 `name`과 `description`만 읽고, 요청이 description과 맞을 때 본문을 읽는다. 그래서 호출 평가는 곧 description 평가다.

### 질의 세트 설계

agentskills.io의 description 최적화 가이드는 호출되어야 하는 질의와 호출되면 안 되는 질의에 각각 라벨을 붙인 세트를 만들라고 한다. 규모는 20개 정도, 양쪽 8~10개씩을 권한다.

```json
[
  { "query": "Badge 컴포넌트에 warning 변형 추가해 줘. 색은 기존 거랑 맞추고", "should_trigger": true },
  { "query": "PR 올리기 전에 이 폼 컴포넌트가 우리 디자인 규칙 어긴 데 없는지 봐 줘", "should_trigger": true },
  { "query": "이 차트 데이터 변환 함수 단위 테스트 좀 써 줘", "should_trigger": false },
  { "query": "Tailwind 설정 파일에서 빌드 경고 나는 이유 알려 줘", "should_trigger": false }
]
```

호출되어야 하는 질의는 여러 축으로 변화를 준다. 격식 있는 말투와 편한 말투, 오타와 약어를 섞는다. 도메인을 직접 언급하는 질의("디자인 토큰 기준으로 봐 줘")와 필요만 설명하는 질의("색이 다른 화면이랑 안 맞아")를 섞는다. 짧은 요청과 파일 경로나 배경이 긴 요청도 섞는다. 가이드가 가장 유용하다고 꼽는 것은 스킬이 도움이 되지만 질의만 봐서는 연결이 분명하지 않은 경우다. 질의가 스킬 기능을 그대로 말하면 어떤 description이든 걸리기 때문이다.

호출되면 안 되는 질의 중에서는 "아슬아슬하게 빗나가는" 질의가 가장 쓸모 있다. 키워드나 개념은 겹치지만 실제로는 다른 일이 필요한 요청이다. 위 예시의 Tailwind 설정 질문처럼 스타일 관련 단어가 나오지만 디자인 시스템 규칙 검토와는 상관없는 요청이 여기에 해당한다. "날씨 알려 줘" 같은 무관한 질의는 아무것도 시험하지 못한다.

가이드에 따르면 단순한 한 단계 요청은 description이 완벽해도 스킬을 부르지 않을 수 있다. 에이전트는 혼자 처리하기 어려운 작업에서 스킬을 찾는 경향이 있기 때문이다. 평가 질의는 스킬이 실제로 필요한 수준의 작업으로 만든다.

### 여러 번 돌려서 비율로 본다

모델의 동작은 결정적이지 않아서 같은 질의도 한 번은 호출되고 다음엔 안 될 수 있다. 가이드는 질의마다 여러 번(3회를 출발점으로) 돌려 호출 비율을 계산하라고 한다. 호출되어야 하는 질의는 비율이 임계값(기본 0.5)보다 높으면 통과, 호출되면 안 되는 질의는 낮으면 통과다. 20개 질의를 3번씩 돌리면 60회이므로 스크립트로 돌리는 편이 현실적이다.

Claude Code에서는 비대화형 모드(`claude -p`)를 쓸 수 있다. `--output-format stream-json --verbose`로 실행하면 이벤트가 한 줄에 하나씩 JSON으로 나온다. 그 안에서 `Skill` 도구 호출을 찾으면 된다. agentskills.io 가이드의 예시 스크립트도 Claude Code의 JSON 출력에서 이름이 `Skill`인 `tool_use`를 찾는 방식이다. 다만 가이드는 이 판정 로직을 각자 쓰는 클라이언트에 맞게 바꾸라고 한다. 출력 형태는 직접 확인하고 맞추는 편이 안전하다.

### 과적합을 피한다

질의 전체에 맞춰 description을 고치면 그 문구에만 맞는 description이 된다. 가이드는 질의를 학습용(약 60%)과 검증용(약 40%)으로 나누고, 수정은 학습용 실패만 보고 하라고 한다. 최종 선택은 검증용 통과율로 한다. 마지막 버전이 가장 좋은 버전이라는 보장은 없다. 실패한 질의의 단어를 description에 그대로 넣는 것도 과적합이다. 그 질의들이 대표하는 범주를 찾아서 써야 한다. description은 고칠수록 길어지기 쉬우니 1,024자 제한도 다시 확인한다.

## 결과 평가: 호출됐을 때 맞게 했는가

호출이 잘 되면 다음은 출력 품질이다. agentskills.io의 평가 가이드는 테스트 케이스를 세 부분으로 정의한다. 실제 사용자가 입력할 법한 프롬프트, 성공이 어떤 모습인지 사람이 읽을 수 있게 적은 기대 결과, 그리고 필요하면 입력 파일이다. 이것을 스킬 디렉터리의 `evals/evals.json`에 둔다.

```json
{
  "skill_name": "design-system",
  "evals": [
    {
      "id": 1,
      "prompt": "src/components/Badge.vue에 warning 변형을 추가해 줘. 기존 success, danger랑 같은 방식으로",
      "expected_output": "토큰만 사용한 warning 변형과 그에 맞는 스토리 또는 사용 예시",
      "files": ["evals/files/Badge.vue"],
      "assertions": [
        "변경된 코드에 hex, rgb 색상 리터럴이 없다",
        "warning 색상은 기존 시맨틱 토큰 이름 규칙을 따른다",
        "기존 variant prop의 타입 정의에 warning이 추가되어 있다"
      ]
    }
  ]
}
```

가이드는 2~3개로 시작하라고 한다. 첫 결과를 보기 전에 너무 많이 투자하지 말라는 뜻이다. 검증 항목(assertion)도 처음부터 다 정하지 말고, 첫 실행 결과를 보고 추가하라고 한다. 좋은 결과가 어떤 모습인지는 대개 스킬이 한 번 돌아 봐야 알기 때문이다.

### 기준선과 나란히 돌린다

각 케이스는 두 번 돌린다. 한 번은 스킬을 켜고, 한 번은 끄고(또는 이전 버전으로). Claude Code 스킬 문서도 같은 방법을 제시한다. 현실적인 프롬프트를 몇 개 모아 각각 새 세션에서 스킬이 있을 때와 없을 때 돌려 비교하라는 것이다. 새 세션이어야 하는 이유는 스킬을 작성하며 쌓인 맥락이 지시문의 빈틈을 가리기 때문이다. 개인이나 프로젝트 스킬을 끄는 방법으로 문서는 설정의 `skillOverrides`에서 해당 스킬을 `"off"`로 두는 방법을 안내한다.

```json
{
  "skillOverrides": {
    "design-system": "off"
  }
}
```

이전 버전과 비교할 때는 수정 전에 스킬 디렉터리를 복사해 스냅숏을 남기고, 기준선 실행을 그 스냅숏에 연결한다.

### 채점

검증 항목은 확인할 수 있는 문장이어야 한다. "출력이 좋다"는 채점할 수 없다. 반대로 특정 문구가 정확히 들어가야 한다는 식의 항목은 너무 깨지기 쉽다. 표현만 다른 올바른 결과도 실패로 처리되기 때문이다. 가이드의 원칙은 두 가지다. 통과에는 구체적인 근거를 요구하고, 결과뿐 아니라 검증 항목 자체도 검토한다.

"색상 리터럴이 없다" 같은 기계적인 항목은 LLM 판단보다 스크립트가 더 믿을 만하고, 반복 실행에도 재사용할 수 있다.

```ts
// scripts/check-no-color-literals.ts
import { readFileSync } from "node:fs";

const file = process.argv[2];
const source = readFileSync(file, "utf8");
const pattern = /#[0-9a-fA-F]{3,8}\b|rgba?\(/g;
const hits = [...source.matchAll(pattern)].map((m) => m[0]);

console.log(JSON.stringify({
  text: "변경된 코드에 hex, rgb 색상 리터럴이 없다",
  passed: hits.length === 0,
  evidence: hits.length === 0 ? "리터럴 없음" : `발견: ${hits.join(", ")}`,
}));
```

"시맨틱 토큰 이름 규칙을 따른다"처럼 판단이 필요한 항목은 출력과 항목을 LLM에 주고 항목마다 통과 여부와 근거를 받는다. 디자인의 완성도처럼 통과와 실패로 쪼개기 어려운 품질은 사람이 검토한다.

### 결과 숫자 읽기

케이스별 통과율, 시간, 토큰을 스킬 있음과 없음으로 나눠 모으면 스킬이 무엇을 비용으로 치르고 무엇을 얻는지 보인다. 가이드가 짚는 패턴은 이렇다. 양쪽에서 항상 통과하는 항목은 모델이 스킬 없이도 잘하는 것이니 빼거나 바꾼다. 양쪽에서 항상 실패하는 항목은 항목이나 케이스가 잘못됐을 수 있다. 가장 눈여겨볼 것은 스킬이 있을 때만 통과하는 항목이다. 스킬의 효과가 나타나는 곳이므로 어떤 지시가 차이를 만들었는지 파악한다.

## 반복 개선

실행 결과에서 얻는 신호는 세 가지다. 실패한 검증 항목, 사람의 피드백, 실행 기록이다. 실행 기록을 보면 왜 그렇게 됐는지 알 수 있다. 모범 사례 문서는 여기에 Claude가 스킬을 실제로 어떻게 탐색하는지 관찰하라고 덧붙인다. 예상하지 못한 순서로 파일을 읽는지, 중요한 참조 파일을 놓치는지, 특정 파일만 반복해서 읽는지, 한 번도 열지 않는 파일이 있는지를 본다. 반복해서 읽는 내용은 `SKILL.md` 본문으로 올리고, 아무도 열지 않는 파일은 지우거나 본문의 안내를 고친다.

문서가 권하는 작업 방식은 Claude 두 인스턴스를 쓰는 것이다. 한쪽(Claude A)과 함께 스킬을 설계하고 다듬고, 다른 쪽(Claude B, 스킬을 로드한 새 인스턴스)에 실제 작업을 시켜 본다. B가 헤매는 지점을 구체적으로 A에게 가져가 고친다. 고칠 때는 테스트 케이스에만 맞춘 좁은 수정보다 원인을 일반화한 수정을 하고, 지시는 가볍게 유지한다. 모든 테스트 실행이 비슷한 보조 스크립트를 각자 새로 짜고 있다면 그 스크립트를 스킬의 `scripts/`에 넣으라는 신호다. 이 부분은 [스킬에 스크립트 넣기](/blog/skills-with-scripts/)와 이어진다.

### 모델별로도 확인한다

스킬은 모델 위에 얹히므로 효과가 모델에 따라 달라진다. 모범 사례 문서는 쓸 모델 모두로 테스트하라고 한다. Haiku에서는 안내가 충분한지, Sonnet에서는 명확하고 효율적인지, Opus에서는 과하게 설명하지 않는지를 본다. 문서의 공유 전 체크리스트에도 평가 세 개 이상, Haiku·Sonnet·Opus로 테스트, 실제 사용 시나리오로 테스트가 들어 있다.

> **참고** Anthropic의 `skill-creator` 스킬은 이 과정의 상당 부분을 자동화한다. 케이스별 독립 실행, 검증 항목 채점, 스킬 있음과 없음의 벤치마크, description 조정까지 다룬다. 다만 평가 파일 형식은 도구마다 다를 수 있으니 쓰는 도구의 문서를 기준으로 맞춘다.

## 정리

- 호출 평가와 결과 평가는 별개다. 트리거됐다는 것은 스킬을 찾았다는 뜻일 뿐이다.
- 평가를 먼저 만든다. 스킬 없이 돌려 실패를 모으고, 그 실패를 겨냥한 시나리오로 시작한다.
- 호출 평가는 라벨 붙은 질의 약 20개로, 아슬아슬하게 빗나가는 질의를 포함하고, 여러 번 돌려 비율로 판정하며, 학습용과 검증용을 나눈다.
- 결과 평가는 새 세션에서 스킬 있음과 없음(또는 이전 버전)을 나란히 돌려 비교한다. 기계적인 검증은 스크립트로, 판단은 LLM과 사람으로 나눈다.
- 실행 기록과 Claude의 탐색 경로를 보고 고치며, 쓸 모델 모두로 확인한다.
