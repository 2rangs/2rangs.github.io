
반년 전에 짠 코드를 열었습니다. 이상한 `setTimeout(..., 0)`이 하나 있습니다. 지워도 될 것 같은데, 지우기가 무섭습니다. 분명 무슨 이유가 있었던 것 같은데 기억이 나지 않습니다.

`git blame`을 해 보니 커밋 메시지는 `fix`입니다. 작성자는 저입니다.

코드는 남아 있는데 그 코드를 쓴 이유는 사라졌습니다. 개발자라면 거의 다 해 봤을 이 경험을 줄이려면, 그 이유를 어디에 어떻게 남겨 둘지 정해 두어야 합니다.

## 가장 먼저 사라지는 것은 '왜'입니다

코드가 **무엇을** 하는지, **어떻게** 하는지는 코드를 읽으면 압니다. 하지만 **왜** 이렇게 하는지는 코드를 아무리 읽어도 알 수 없을 때가 많습니다.

"왜"에는 코드에 드러나지 않는 내용이 들어 있습니다. 검토했다가 버린 대안, 당시의 제약(마감, 라이브러리 버그, 특정 브라우저의 동작), 다른 팀과의 약속. 코드를 쓰는 순간에는 너무 당연해서 적을 생각이 들지 않고, 그래서 가장 먼저 잊힙니다.

'왜'를 잃으면 나쁜 선택지 두 개만 남습니다. 이유를 모르니 건드리지 못하고 계속 그 위에 덧대거나, 이유를 모른 채 지웠다가 반년 전에 고쳤던 버그를 다시 만나거나.

G. K. 체스터턴의 울타리 이야기가 자주 인용되는 이유도 같습니다. 길 한가운데 쓸모없어 보이는 울타리가 있을 때, 왜 세워졌는지 알기 전에는 치우지 말라는 이야기입니다. 울타리 옆에 "양이 도로로 나가지 않게 하려고 세웠다"는 팻말이 있었다면 고민할 것도 없었을 겁니다. 기록이 그 팻말 역할을 합니다.

"내가 짠 코드니까 나는 기억하겠지"라는 기대는 거의 항상 틀립니다. 반년 뒤의 나는 그때의 맥락을 하나도 기억하지 못하고, 읽는 입장에서는 남이 짠 코드와 다를 게 없습니다. 그래서 기록을 다른 사람을 위한 친절로만 생각할 필요는 없습니다. 기록은 미래의 나에게 보내는 편지에 가깝고, 받는 사람이 내 사정을 전혀 모른다고 가정하고 써야 읽힙니다.

## 결정을 기록하는 문서, ADR

아키텍처 결정 기록(Architecture Decision Record, ADR)은 Michael Nygard가 2011년 글 "Documenting Architecture Decisions"에서 제안한 형식입니다. 중요한 결정 하나마다 짧은 문서 하나를 남깁니다.

Nygard가 제안한 항목은 이 정도입니다.

- **제목**: 결정을 짧게. 예: "상태 관리에 전역 스토어 대신 서버 상태 캐시를 쓴다"
- **상태**: 제안됨, 승인됨, 폐기됨, 다른 결정으로 대체됨
- **맥락**: 어떤 상황과 제약 때문에 이 결정을 해야 했는가
- **결정**: 무엇을 하기로 했는가
- **결과**: 이 결정으로 쉬워지는 것과 어려워지는 것

이 중 제가 가장 중요하다고 생각하는 부분은 맥락과 결과입니다. 결정 자체는 코드에 이미 드러나 있습니다. 맥락은 코드가 말해 주지 않는 부분이고, 결과는 결정의 대가를 미리 적어 둔 부분입니다. "이 선택으로 오프라인 지원은 어려워진다"라고 적어 두면, 나중에 오프라인 지원 요구가 왔을 때 이 결정을 다시 볼 때라는 걸 바로 알 수 있습니다.

ADR에는 몇 가지 관례가 있습니다. 한 번 쓰면 고치지 않습니다. 결정이 바뀌면 기존 문서를 수정하지 않고 새 ADR을 쓴 뒤 이전 것의 상태를 "대체됨"으로 바꿉니다. 그래야 결정의 역사가 남습니다. 지금은 틀린 결정이라도 그때 왜 그렇게 판단했는지는 여전히 가치가 있습니다.

그리고 저장소 안에 둡니다. Nygard는 프로젝트 저장소의 `doc/arch` 같은 곳에 번호를 붙인 마크다운 파일로 두자고 했습니다. 코드와 같이 버전 관리되고, 같은 PR에서 리뷰됩니다. 분량은 한두 쪽이면 충분합니다. 길어지면 쓰지 않게 되고, 쓰더라도 읽지 않게 됩니다.

모든 결정에 ADR을 쓸 필요는 없습니다. 기준은 "나중에 누군가 이걸 보고 '왜 이렇게 했지?'라고 물을까"입니다. 라이브러리 선택, 데이터 구조, 경계를 나누는 방식, 일부러 하지 않기로 한 것 같은 결정이 대상입니다.

반론도 있습니다. 작은 팀이나 초기 프로젝트에서는 결정이 너무 자주 바뀌어 ADR이 따라가지 못하고, 아무도 안 읽는 폴더가 된다는 지적입니다. 맞는 말입니다. 그럴 때는 형식을 고집하기보다 PR 설명이나 이슈에 결정의 이유를 남기는 정도로 시작해도 됩니다. 형식보다 "왜를 남긴다"는 습관이 먼저입니다.

예를 들어 이 정도면 충분합니다.

```text
# 0007. 지도 마커 렌더링에 DOM 마커 대신 캔버스 레이어를 쓴다

상태: 승인됨

맥락: 마커가 수천 개 단위로 늘면서 DOM 마커로는 패닝이 끊긴다.
마커마다 다른 툴팁 컴포넌트를 붙여야 하는 요구는 아직 없다.

결정: 마커는 캔버스 레이어로 그리고, 클릭은 좌표로 판정한다.

결과: 패닝 성능이 좋아진다. 대신 마커에 접근성 속성을 달 수 없어서,
같은 정보를 목록 패널로도 제공해야 한다. 마커별 커스텀 UI가
필요해지면 이 결정을 다시 본다.
```

맥락은 두 줄, 결정은 한 줄, 결과는 세 줄입니다. 그래도 반년 뒤에 "왜 마커에 aria 속성이 없죠?"라는 질문에는 충분히 답합니다.

## 커밋 메시지와 PR 설명

가장 가까이 있는 기록 수단은 커밋 메시지입니다. `git blame`과 `git log`는 코드 한 줄에서 그 줄을 바꾼 커밋으로 바로 데려다주니, 코드와 이유를 가장 확실하게 이어 줍니다. 그런데 커밋 메시지는 대개 이렇게 생겼습니다.

```bash
git log --oneline
# a1b2c3d fix
# d4e5f6a 수정
# 9g8h7i6 리뷰 반영
```

무엇이 바뀌었는지는 diff가 이미 보여 주니, 메시지에는 diff가 보여 줄 수 없는 내용을 적어야 합니다. 왜 바꿨는지, 어떤 증상이 있었는지, 다른 방법은 왜 안 됐는지.

```text
지도 마커 클릭 후 상세 패널이 이전 마커 정보를 보여주는 문제 수정

마커를 빠르게 연달아 누르면 먼저 보낸 상세 요청의 응답이 나중에 도착해
패널을 덮어썼다. 응답을 받을 때 현재 선택된 마커 id와 비교해 다르면 버린다.

AbortController로 이전 요청을 취소하는 방법도 봤지만, 상세 API가
캐시 계층을 거쳐서 취소해도 서버 쪽 작업은 그대로 돌아 효과가 적었다.
```

첫 줄은 요약, 빈 줄, 그 아래 본문. 첫 줄은 `git log --oneline`에서 보이니 짧게 쓰고, 이유는 본문에 씁니다. 이 형식은 Git 커뮤니티에서 오래 쓰여 온 관례이고, Chris Beams의 글 "How to Write a Git Commit Message"가 잘 정리해 두었습니다.

PR 설명도 같은 역할을 합니다. 스쿼시 머지를 하는 팀이라면 PR 설명이 최종 커밋 메시지가 되니 더 신경 써서 쓸 만합니다.

## 주석은 무엇이 아니라 왜를 씁니다

주석에 대해서는 의견이 갈립니다. "좋은 코드는 주석이 필요 없다"는 주장도 있고, "주석이 없으면 이해할 수 없다"는 불만도 있습니다. 두 입장은 서로 다른 주석을 두고 말하는 경우가 많습니다.

```js
// 사용자 목록을 이름순으로 정렬한다
users.sort((a, b) => a.name.localeCompare(b.name));
```

이 주석은 코드가 하는 일을 한 번 더 말합니다. 코드를 읽을 수 있는 사람에게는 필요 없고, 코드가 바뀌면 주석만 남아 틀린 내용을 말하게 됩니다. "주석이 필요 없다"는 쪽이 말하는 주석이 이런 종류입니다. 이런 주석이 필요해 보인다면 대개 함수 이름이나 변수 이름을 고치는 편이 낫습니다.

```js
// iOS Safari는 이 시점에 레이아웃이 확정되지 않아 높이가 0으로 나온다.
// 다음 태스크로 미뤄서 측정한다.
setTimeout(measure, 0);
```

이 주석은 코드가 말해 줄 수 없는 내용을 담고 있습니다. 이 주석이 없으면 다음 사람은 `setTimeout`을 지우고 iOS에서 버그를 다시 만납니다. 글 첫머리의 그 `setTimeout`에 이런 두 줄이 있었다면 고민할 필요가 없었을 겁니다.

무엇을 하는지는 코드가 말하게 하고, 왜 이렇게 하는지는 주석이 말하게 합니다. 특히 이상해 보이는 코드, 직관과 반대로 동작하는 코드, 외부 버그를 피해 가는 코드에는 이유를 적습니다. 관련 이슈 번호나 외부 버그 트래커 주소가 있다면 같이 남기면 더 좋습니다.

## 문서는 왜 낡을까

위키에 정성껏 써 둔 문서가 1년 뒤에는 틀린 내용으로 가득한 경우도 흔합니다. 문서가 낡는 이유는 게으름보다 구조에 있습니다.

문서와 코드가 따로 있으면, 코드를 바꾸는 PR에서 위키 문서는 보이지 않으니 고쳐야 한다는 사실을 떠올릴 계기가 없습니다. 틀린 문서는 티도 나지 않습니다. 틀린 코드는 테스트가 깨지거나 사용자가 제보하지만, 틀린 문서는 누군가 그 내용을 믿고 일을 그르칠 때까지 드러나지 않습니다. 그리고 주인이 없습니다. 모두의 문서는 아무의 문서도 아닙니다.

그래서 문서를 오래 살리려면 코드 가까이 둡니다. 결정의 이유는 커밋 메시지와 주석에 적어 코드와 함께 움직이게 하고, 설계 결정은 저장소 안의 ADR로 남겨 같은 PR에서 리뷰되게 합니다. 사용법은 README나 실행 가능한 예제로 쓰고, 예제가 실제로 돌아가는지 CI에서 확인할 수 있으면 더 좋습니다. 타입과 테스트도 문서입니다. 특히 테스트는 "이 함수가 이런 입력에 이렇게 동작한다"를 기계가 검증하는 문서라서, 내용이 틀리면 바로 빨간불이 들어옵니다.

반대로 금방 바뀔 내용은 아예 적지 않는 것도 방법입니다. 현재 구현의 세부를 자세히 적은 문서가 가장 빨리 낡습니다. 오래 가는 내용은 "왜"와 "경계"이고, "어떻게"는 코드에 맡기는 편이 낫습니다.

## 쓰면서 생각이 정리됩니다

기록은 미래뿐 아니라 지금 당장에도 도움이 됩니다. 머릿속에서는 완벽해 보이던 설계도 글로 옮기려는 순간 빈틈이 보일 때가 있습니다. "이 상태는 여기서 관리하고, 저기서는…" 하고 적다 보면 두 곳에서 같은 상태를 들고 있다는 걸 알게 됩니다. "왜 A 대신 B를 골랐는가"를 한 문장으로 쓰려는데 써지지 않으면, 이유가 없었다는 뜻일 수 있습니다.

컴퓨터 과학자 레슬리 램포트가 한 말로 자주 인용되는, "쓰지 않고 생각하는 사람은 자기가 생각하고 있다고 착각할 뿐이다"라는 취지의 문장이 있습니다. 과장이 섞여 있지만, 글을 쓰다 보면 생각의 허술한 곳이 드러난다는 건 많은 사람이 경험으로 압니다.

그래서 ADR이나 PR 설명은 일을 끝낸 뒤 쓰는 보고서보다 일을 하면서 쓰는 메모에 가까울 때 더 쓸모가 있습니다. 구현 전에 맥락과 대안을 적어 보면 구현하면서 방향을 잃지 않습니다.

## 기록이 과해질 때

모든 것을 기록하자는 말은 아닙니다. 쓰는 데 시간이 들고, 읽는 데 시간이 들고, 틀린 기록은 없는 기록보다 해롭습니다. 코드만 읽어도 분명한 것, 곧 바뀔 것이 확실한 세부 구현, 누구도 다시 찾아보지 않을 회의의 모든 발언은 적지 않거나 줄이는 편이 낫습니다.

기준은 같은 질문입니다. "반년 뒤에 이걸 모르면 곤란한가?" 곤란하다면 적고, 아니라면 적지 않습니다.
