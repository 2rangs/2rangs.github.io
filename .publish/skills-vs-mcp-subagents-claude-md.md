
스킬을 몇 개 만들어 쓰다 보면 비슷한 질문을 자주 받는다. "그거 CLAUDE.md에 쓰면 되지 않나요?", "MCP 서버로 만들면 안 되나요?", "서브에이전트랑 뭐가 달라요?" 다섯 가지 모두 Claude에게 무언가를 더 알려 주거나 할 수 있는 일을 늘려 준다. 그래서 처음에는 무엇을 어디에 둬야 할지 헷갈린다.

고르는 기준은 두 가지면 충분하다. 언제 컨텍스트에 올라가는지, 그리고 무엇을 제공하는지(지식, 도구, 격리된 작업 공간 중 무엇인지)다. 아래 내용은 작성 시점의 Claude Code 공식 문서, 특히 확장 기능 개요(Extend Claude Code) 페이지를 기준으로 한다.

## 다섯 가지의 정의

공식 문서의 정의를 짧게 옮기면 이렇다. CLAUDE.md(메모리)는 매 세션 시작 때 읽는 지속 컨텍스트로, 빌드 명령이나 코딩 규칙처럼 "항상 이렇게 하라"는 내용을 담는다. 스킬은 필요할 때 불러오는 지식과 워크플로다. `SKILL.md` 하나로 시작하고, `/스킬이름`으로 직접 부르거나 Claude가 description을 보고 알아서 불러온다. MCP는 외부 서비스와 도구를 연결하는 프로토콜로, 이슈 트래커, 데이터베이스, 브라우저 같은 시스템을 Claude가 직접 읽고 조작하게 해 준다. 서브에이전트는 자기 컨텍스트 창에서 따로 일하고 요약만 돌려주는 작업자이고, 별도 시스템 프롬프트, 도구 제한, 권한을 가진다.

슬래시 명령은 `/이름`으로 실행하는 명령인데, 문서 기준으로 사용자 정의 명령은 이제 스킬로 합쳐졌다. `.claude/commands/`의 파일은 계속 동작하지만, 새로 만든다면 스킬을 권장한다. 이 부분은 [Claude Code에서 스킬 만들고 쓰기](/blog/claude-code-skills-in-practice/)에서도 다뤘다. `.claude/commands/deploy.md`와 `.claude/skills/deploy/SKILL.md`는 둘 다 `/deploy`가 되고, 이름이 겹치면 스킬이 이긴다. 다른 점은 스킬에는 보조 파일을 함께 둘 수 있다는 것이다. 그러니 "슬래시 명령이냐 스킬이냐"는 이제 "직접 호출만 허용하는 스킬이냐, 자동 호출도 허용하는 스킬이냐"에 가깝다. 이 차이는 frontmatter의 `disable-model-invocation: true` 한 줄로 정한다.

`/help`나 `/compact` 같은 내장 명령은 Claude Code에 정해진 동작이고, 우리가 만드는 확장과는 별개다. MCP 서버가 노출하는 프롬프트도 `/servername:promptname` 형태의 명령으로 나타나는데, 이 경우 명령의 출처는 MCP 서버다.

## 로딩 시점과 컨텍스트 비용

선택에서 가장 중요한 축은 컨텍스트 비용이다. 공식 문서의 표를 요약하면 다음과 같다.

| 기능 | 언제 올라가나 | 무엇이 올라가나 |
| - | - | - |
| CLAUDE.md | 세션 시작 | 파일 전체. 모든 요청에 포함 |
| 스킬 | 세션 시작 + 사용 시 | 시작 시 이름과 description, 사용 시 본문 |
| MCP 서버 | 세션 시작 | 도구 이름(전체 스키마는 필요할 때) |
| 서브에이전트 | 생성 시 | 메인과 분리된 새 컨텍스트 |

여기서 실무 규칙 하나를 얻을 수 있다. 모든 세션에 필요한 짧은 사실은 CLAUDE.md에, 가끔 필요한 긴 내용은 스킬에 둔다. 문서는 CLAUDE.md를 파일당 200줄 아래로 유지하라고 권하고, 길어지면 참고 자료는 스킬로 옮기거나 `.claude/rules/`로 나누라고 한다. 스킬 문서도 같은 이야기를 한다. 같은 지시나 체크리스트를 대화에 계속 붙여 넣고 있거나, CLAUDE.md의 한 절이 사실이 아니라 절차로 바뀌었다면 스킬로 만들 때라고 한다.

`disable-model-invocation: true`를 붙인 스킬은 description조차 컨텍스트에 올라가지 않는다. 직접 부르기 전까지는 비용이 들지 않는다. 배포처럼 부작용이 있는 작업에는 비용과 안전 모두에서 이 설정이 낫다.

## CLAUDE.md vs 스킬

둘 다 지시문을 담은 마크다운이라 가장 많이 헷갈린다. 차이는 로딩 방식이다. CLAUDE.md는 항상 로드된다. `@path` 문법으로 다른 파일을 가져올 수 있지만, 가져온 파일도 함께 로드되므로 컨텍스트 비용은 줄지 않는다. 스킬은 필요할 때 로드되고, `/이름`으로 워크플로를 실행할 수도 있다.

디자인 시스템을 예로 들면 이렇게 나눌 수 있다.

```md
<!-- CLAUDE.md : 항상 필요한 사실 -->
- 패키지 매니저는 pnpm을 쓴다.
- 색상은 하드코딩하지 않고 디자인 토큰을 쓴다. 자세한 규칙은 design-system 스킬을 따른다.
- 커밋 전에 `pnpm lint`와 `pnpm test`를 실행한다.
```

토큰 전체 목록, 컴포넌트별 사용 규칙, 리뷰 체크리스트처럼 긴 내용은 [디자인 시스템 규칙을 스킬로 만들기](/blog/design-system-skill/)에서 만든 스킬에 둔다. CLAUDE.md에는 "이런 규칙이 있고 어디서 찾는다"만 남긴다.

중간 단계도 있다. `.claude/rules/`의 규칙 파일은 `paths` frontmatter로 특정 파일 패턴에만 걸 수 있다. 예를 들어 `src/components/**/*.vue`를 다룰 때만 올라가는 규칙을 만들 수 있다. 문서 기준으로는 프로젝트 전체에 필요한 내용은 CLAUDE.md, 특정 언어나 디렉터리에만 해당하는 지침은 rules, 가끔 필요한 참고 자료와 반복 워크플로는 스킬이다.

CLAUDE.md와 스킬은 모두 Claude가 맥락으로 읽는 지시일 뿐 강제되는 설정이 아니다. "`.env`는 절대 수정하지 말 것"처럼 반드시 지켜져야 하는 규칙이라면 문서는 PreToolUse 훅으로 막으라고 권한다.

## MCP vs 스킬

이 둘은 서로 대체하는 관계가 아니라 맡는 층이 다르다. 문서 설명대로 MCP는 Claude를 외부 서비스에 연결하고, 스킬은 그 서비스를 잘 쓰는 법을 포함해 Claude가 아는 것을 늘린다. MCP는 도구와 데이터 접근을 주고 연결과 인증은 서버가 처리한다. 스킬은 지식, 워크플로, 참고 자료를 준다.

판단 기준은 단순하다. Claude가 볼 수 없는 시스템의 데이터를 계속 복사해서 붙여 넣고 있다면 MCP, Claude가 이미 쓸 수 있는 도구를 우리 팀 방식대로 쓰게 하고 싶다면 스킬이다. 예를 들어 디자인 도구나 이슈 트래커 연결은 MCP 서버가 맡는다. 그 데이터를 받아서 "우리 팀은 이슈 본문에서 수용 기준을 이렇게 뽑고, 컴포넌트 이름은 이렇게 매핑한다"는 절차는 스킬에 쓴다.

MCP 서버는 범위(scope)에 따라 저장 위치가 다르다. 문서 기준으로 local(기본값, `~/.claude.json`의 해당 프로젝트 항목), project(프로젝트 루트의 `.mcp.json`, 버전 관리로 팀과 공유), user(`~/.claude.json`, 내 모든 프로젝트) 세 가지가 있다.

```bash
# 팀과 공유할 서버는 project 범위로 추가하면 .mcp.json에 기록된다
claude mcp add --transport http shared-server --scope project https://example.com/mcp
```

비용 면에서는 MCP도 가볍다. 문서에 따르면 도구 검색(tool search)이 기본으로 켜져 있어, 세션 시작 때는 도구 이름과 서버 지시만 올라가고 전체 JSON 스키마는 필요할 때 불러온다. 다만 문서는 서버를 연결하기 전에 신뢰할 수 있는지 확인하라고 경고한다. 외부 콘텐츠를 가져오는 서버로 프롬프트 인젝션이 들어올 수 있다.

## 서브에이전트 vs 스킬

스킬은 메인 대화의 컨텍스트에 내용을 더한다. 서브에이전트는 별도의 컨텍스트 창에서 일하고 요약만 돌려준다. 문서의 비교표에서 주요 차이는 다음과 같다.

| | 스킬 | 서브에이전트 |
| - | - | - |
| 무엇인가 | 재사용 가능한 지시, 지식, 워크플로 | 자기 컨텍스트를 가진 격리된 작업자 |
| 컨텍스트 영향 | 메인 창에 더해짐 | 별도 창 사용 |
| 잘 맞는 일 | 참고 자료, 호출형 워크플로 | 파일을 많이 읽는 조사, 병렬 작업 |

서브에이전트는 `.claude/agents/`(프로젝트)나 `~/.claude/agents/`(개인)에 마크다운 파일로 정의한다. frontmatter에서 `name`과 `description`이 필수이고, `tools`로 쓸 수 있는 도구를 제한할 수 있다. 본문은 그 에이전트의 시스템 프롬프트가 된다.

```md
---
name: a11y-auditor
description: 변경된 컴포넌트의 접근성 문제를 조사한다. 컴포넌트 수정 후 접근성 점검이 필요할 때 사용한다.
tools: Read, Grep, Glob
---

변경된 Vue/React 컴포넌트를 읽고 접근성 문제를 찾는다.
라벨 없는 입력, 키보드로 닿지 않는 인터랙션, 대비가 부족한 토큰 사용을 파일과 줄 번호로 보고한다.
```

언제 서브에이전트를 쓸지에 대해 문서가 주는 기준은 분명하다. 다시 참조하지 않을 검색 결과, 로그, 파일 내용으로 메인 대화가 넘칠 때, 도구 제한을 강제하고 싶을 때, 작업이 독립적이라 요약만 돌려받으면 될 때다. 반대로 주고받기가 잦거나, 계획과 구현과 테스트가 많은 맥락을 공유하거나, 빠르고 작은 수정이라면 메인 대화가 낫다.

### 둘을 함께 쓰는 두 방향

스킬과 서브에이전트는 조합할 수 있고, 방향이 두 가지다.

스킬에 `context: fork`를 넣으면 스킬 본문이 서브에이전트의 작업 지시가 된다. `agent` 필드로 에이전트 유형을 고르며, 생략하면 `general-purpose`다. 서브에이전트는 대화 기록을 보지 못하므로 스킬 지시가 그 자체로 완결되어야 한다. 문서는 "이 API 규칙을 따르라" 같은 지침만 있고 할 일이 없는 스킬에 `context: fork`를 쓰면 의미 있는 결과가 나오지 않는다고 경고한다.

반대로 서브에이전트에 `skills` 필드를 넣으면 나열한 스킬의 전체 내용이 서브에이전트 시작 시 주입된다. description만 올라가는 것이 아니다. 단, `disable-model-invocation: true`인 스킬은 미리 로드할 수 없다. 앞의 `a11y-auditor`라면 `skills: [design-system]`을 넣어 토큰 규칙을 미리 알고 시작하게 할 수 있다.

## 어떤 순서로 도입하나

문서는 처음부터 다 갖출 필요는 없다며, 어떤 상황에서 무엇을 추가할지 표로 보여 준다. 프론트엔드 팀 상황에 맞게 옮기면 이렇다.

- Claude가 같은 규칙이나 명령을 두 번 틀리면 → CLAUDE.md에 추가
- 작업을 시작할 때마다 같은 프롬프트를 입력하면 → 사용자 호출형 스킬
- 같은 절차서를 세 번째 붙여 넣고 있으면 → 스킬
- Claude가 볼 수 없는 브라우저 탭에서 데이터를 계속 복사하고 있으면 → MCP 서버
- 곁가지 작업이 다시 보지 않을 출력으로 대화를 덮으면 → 서브에이전트
- 묻지 않아도 매번 일어나야 하는 일이 있으면 → 훅
- 두 번째 저장소에도 같은 구성이 필요해지면 → 플러그인

마지막 항목인 플러그인은 위의 것들을 하나로 묶어 배포하는 포장 단위다. 이 부분은 다음 글 [팀과 스킬 공유하기](/blog/sharing-skills-with-plugins/)에서 다룬다.
