## 개요

포켓몬 전투를 웹 앱에서 쉽게 쓰도록 만든 TypeScript 라이브러리입니다. 전투 규칙은 Pokémon Showdown 시뮬레이터를, 데미지 계산은 `@smogon/calc`를, 이름과 데이터는 PokeAPI를 씁니다. 이 엔진은 그 셋을 하나의 API로 묶고, 화면을 만들기 좋은 형태로 바꿔 줍니다. [Pokestra](/projects/pokestra/)의 배틀과 데미지 계산기가 이 엔진으로 돌아갑니다.

## 왜 만들었나

Showdown 시뮬레이터는 규칙 구현이 정확하지만, 화면을 만들기에는 불편합니다.

- 결과가 `|-damage|p2a: Garchomp|120/300` 같은 텍스트 프로토콜로 나와서, 화면에서 쓰려면 직접 파싱해야 합니다.
- 이름 체계가 PokeAPI와 다릅니다. PokeAPI의 `urshifu-rapid-strike`와 Showdown의 `urshifurapidstrike`처럼 같은 포켓몬을 다르게 부릅니다.
- 한국어 로그가 없습니다.

규칙을 직접 다시 구현하는 대신, 검증된 시뮬레이터를 감싸고 그 바깥쪽을 제대로 만드는 쪽을 택했습니다.

## 한 일

### 화면 쪽에서 쓰기 쉬운 API

- PokeAPI 이름으로 팀과 행동을 다루는 API(`getRequest` / `submitAction`)와 입력 검증
- 지금 고를 수 있는 행동(기술, 교체, 테라스탈, 강제 행동)을 정리해 돌려주고, 시뮬레이터 요청에 드러나지 않는 정보(숨은 교체 불가, 봉인 등)도 실제 상태에서 읽어 반영
- 같은 시드를 넣으면 같은 배틀이 재현되도록 설계
- React 훅(`useBattle`), 휴리스틱·랜덤 AI, Showdown 랜덤 배틀 팀 생성 제공

### 프로토콜을 타입 있는 이벤트로

- Showdown 프로토콜 메시지를 `move_use`, `damage`, `switch`, `faint`, `terastallize` 같은 타입 있는 이벤트로 변환하고, 로그가 쓰이는 즉시 내보냄
- `damage`·`heal` 이벤트에 정확한 수치, 남은 HP, 상성, 급소 여부를 담음
- 재생력·자연회복처럼 시뮬레이터가 로그 없이 HP나 상태를 바꾸는 경우에도 보정 이벤트를 만들어, **이벤트만 따라가도 HP가 시뮬레이터와 정확히 같게** 함
- 조사(이/가, 은/는)까지 맞춘 한국어 배틀 로그

### 데이터 연결

- PokeAPI의 포켓몬 1,351개(폼 포함)를 Showdown ID에 모두 연결
- 포켓몬·기술·특성·도구·타입·성격의 한국어 이름
- `@smogon/calc` 기반 데미지 계산과, 현재 배틀 상태에서 내 기술의 데미지 미리보기

### 여러 배틀 형식과 규칙

- 싱글·더블·트리플 배틀과 Showdown 규칙 옵션(팀 미리보기, 레벨 조정, 테라스탈 금지, 같은 포켓몬 금지, 수면 제한 등)
- **로테이션 배틀:** Showdown에는 구현되어 있지 않은 형식이라, 트리플 배틀을 기반으로 대상 지정과 선택 처리를 런타임에 고쳐 구현. 로테이션으로 표시한 배틀에만 적용해 다른 형식에 영향이 가지 않게 함

### 패키지와 문서

- tsup으로 ESM·CJS 빌드, 타입 선언 포함
- 코드를 바로 돌려 볼 수 있는 플레이그라운드 문서 사이트

## 검증: 1,000만 번의 배틀

시뮬레이터를 감싼 코드는 시뮬레이터와 어긋나는 순간 조용히 틀린 화면을 만듭니다. 사람이 짠 테스트로는 기술·특성·도구 조합을 다 볼 수 없어서, 무작위 배틀을 대량으로 돌리는 퍼징 테스트를 만들었습니다.

- **무엇을 섞나:** 배틀 형식(싱글·더블·트리플·로테이션), 팀(랜덤 배틀 세트, 또는 종·특성·도구·기술·레벨을 무작위로 섞은 팀), 행동(무작위 또는 휴리스틱 AI)
- **무엇을 검사하나:** 예외가 없을 것, 엔진이 제시한 행동을 시뮬레이터가 모두 받아들일 것, 처리하지 못한 프로토콜 메시지가 없을 것, 모든 이벤트가 실제 포켓몬을 가리킬 것, 이벤트로 다시 계산한 HP가 실제 HP와 같을 것, 기절 수와 승자가 맞을 것, 같은 시드는 같은 로그를 낼 것 — 7가지 불변식
- **어떻게 돌리나:** 푸시할 때마다 CI에서 1만 번, 필요할 때 GitHub Actions에서 10개 샤드로 나눠 1,000만 번

모든 배틀은 시드로 재현되므로, 실패한 배틀은 시드 하나로 바로 다시 열어 볼 수 있습니다.

## 배운 점

- 이미 검증된 구현이 있으면 다시 만들기보다 잘 감싸는 쪽이 낫다. 대신 감싼 쪽이 어긋나지 않는지를 끝까지 확인해야 한다.
- 사람이 떠올리는 테스트 케이스에는 한계가 있다. 불변식을 정하고 무작위 입력을 대량으로 넣으면 생각하지 못한 조합이 드러난다.
- 라이브러리의 사용자는 개발자다. 타입, 이벤트 이름, 오류 메시지가 곧 UX다.
