## 왜 만들었나

처음에는 전투 규칙을 직접 짰습니다. 기술 몇 개, 특성 몇 개까지는 괜찮았지만 9세대의 기술·특성·도구가 서로 얽히는 경우의 수를 손으로 따라가는 건 끝이 없었습니다. 그래서 방향을 바꿨습니다. **규칙은 이미 수많은 사람이 검증한 Showdown 시뮬레이터에 맡기고, 나는 그 바깥을 제대로 만든다.**

그런데 Showdown은 서버용 시뮬레이터라 그대로 쓰기에는 걸리는 점이 많았습니다.

| Showdown을 그대로 쓸 때 | 이 엔진 |
|---|---|
| 행동은 `'move 1 2, switch 3'` 같은 문자열. 틀리면 제출 뒤에 거절 | 객체로 제출, 제출 전에 검증, 지금 낼 수 있는 행동 목록 제공 |
| 결과는 `\|-damage\|p2a: Garchomp\|54/100` 같은 프로토콜 줄. 공개 줄은 HP가 퍼센트 | 타입 있는 이벤트 34종, 정확한 HP·상성 배율·급소 포함 |
| 재생력처럼 로그 없이 바뀌는 HP가 있음 | 보정 이벤트를 내서 이벤트만으로 HP가 정확히 맞음 |
| 사람이 읽는 문장 없음 | 한국어·영어·일본어 문장 |
| 이름 체계가 PokeAPI와 다름(`urshifurapidstrike`) | PokeAPI 슬러그 1,351개를 모두 연결 |
| 앱에 넣으면 8.7 MB, `eval` 경고 | 3.4 MB, 무거운 데이터는 필요할 때만 |

그리고 마지막으로 하나를 더 정했습니다. **감쌌다고 느려지면 안 되고, 오히려 빨라야 차이점이 된다.**

## Showdown보다 빠르게, 결과는 같게

### 측정

같은 배틀(같은 시드·팀·선택)을 Showdown 시뮬레이터에 그대로 재생한 시간과 이 엔진으로 재생한 시간을 비교했습니다. 엔진 쪽 시간에는 엔진이 얹는 일(이벤트 변환, 이름, 상태 정리)이 모두 포함됩니다.

| 형식 | Showdown 직접 | 이 엔진 | 차이 |
|---|---|---|---|
| 싱글 | 1.001 ms/턴 | 0.622 ms/턴 | **1.61배 빠름 (−38%)** |
| 더블 | 3.520 ms/턴 | 1.893 ms/턴 | **1.86배 빠름 (−46%)** |
| 트리플 | 5.710 ms/턴 | 3.133 ms/턴 | **1.82배 빠름 (−45%)** |

턴 10만 개로 치면 100초 걸리던 일이 62초에 끝납니다. 처음 감쌌을 때는 오히려 **Showdown보다 34% 느렸습니다.**

### 어디가 느렸나

CPU 프로파일을 떠 보니 시간의 대부분은 제 코드가 아니라 Showdown 내부의 이벤트 처리에 있었습니다. Showdown은 "데미지를 계산한다", "턴이 끝난다" 같은 이벤트가 생길 때마다 필드 위의 모든 상태이상·휘발성 상태·특성·도구·필드 효과에서 `on<이벤트>` 콜백이 있는지 문자열 키로 찾습니다. 효과 객체마다 모양이 달라 이 조회가 느리고, 대부분은 "없음"으로 끝납니다. 프로파일상 배틀 시간의 절반 가까이가 여기였습니다.

### 고친 방법

효과 객체마다 가진 콜백 목록을 **처음 한 번만 만들어 두고** 재사용합니다. 그리고 이벤트 이름 문자열과 핸들러 목록을 만들 때 생기던 임시 배열을 없앴습니다.

```ts
// 효과 객체 → 'on' 으로 시작하는 콜백만 담은 사전. 처음 조회할 때 한 번 만든다
const tables = new WeakMap<object, Record<string, unknown>>()
function callbacksOf(effect) {
  const cached = tables.get(effect)
  if (cached) return cached
  const table = Object.create(null)
  for (let o = effect; o && o !== Object.prototype; o = Object.getPrototypeOf(o))
    for (const key of Object.getOwnPropertyNames(o))
      if (key.startsWith('on') && !(key in table)) table[key] = Object.getOwnPropertyDescriptor(o, key).value
  tables.set(effect, table)
  return table
}
```

처음에는 효과 객체에 심볼 속성으로 붙였는데, 그것도 결국 모양이 제각각인 객체에서 속성을 찾는 일이라 느렸습니다. 바깥 `WeakMap`으로 옮기자 한 단계 더 빨라졌습니다.

조심한 점이 두 가지 있습니다.

- **핸들러 순서를 원본과 똑같이 지켰습니다.** 스피드가 같은 핸들러는 이 순서를 바탕으로 무작위로 섞이기 때문에, 순서가 하나만 달라도 배틀 결과가 달라집니다.
- **엔진이 만든 배틀에만 적용했습니다.** 패치는 프로토타입에 설치하지만 표시된 배틀에서만 동작하고, `{ fast: false }`로 끄면 Showdown 원본 코드 그대로 돕니다.

### 같다는 증명

빠르게 만드는 것보다, 결과가 같다는 걸 계속 증명하는 장치가 더 중요했습니다.

- **퍼징:** 모든 배틀을 패치 없이 한 번 더 돌려 프로토콜 로그를 비교합니다(1\~9세대, 모든 형식). 2만 판에서 차이 0.
- **벤치마크:** `npm run bench:compare`는 시간을 재면서 모든 배틀의 로그를 원본과 비교하고, 하나라도 다르면 실패로 끝납니다.
- **배포 번들 검사(CI):** 사용자가 받는 번들로 돌린 배틀을 원본 시뮬레이터에 다시 재생해 비교합니다.
- **문서 사이트:** 방문자가 자기 브라우저에서 같은 비교를 직접 돌려 볼 수 있습니다.

## 번들: 필요한 것만, 필요할 때

Pokestra에 엔진을 넣자 배틀 화면 청크가 **8.7 MB**였고, 빌드할 때마다 `eval` 경고가 떴습니다. 원인은 Showdown 패키지의 진입점이 모든 세대 데이터와 모든 세대 기술표, 그리고 서버용 스트림 코드(`eval` 포함)까지 한꺼번에 불러오는 구조였기 때문입니다. 앱의 번들러는 이것들을 걸러낼 수 없었습니다.

엔진 빌드에 esbuild 플러그인을 넣어 해결했습니다.

1. Showdown 진입점 대신, 필요한 모듈만 다시 내보내는 shim을 씁니다. 스트림 코드가 빠져 **`eval` 경고가 사라졌습니다.**
2. 기술표(2.8 MB)와 랜덤배틀 세트(1.1 MB)는 별도 청크로 빼고 `preloadData()` 때 불러옵니다.
3. 1\~8세대 데이터는 세대별 청크(60\~140 kB)로 빼고, 쓰려는 세대만 `preloadData({ gens: [7] })`로 불러옵니다.

결과는 **8.7 MB → 3.4 MB(−61%)** 입니다.

3번이 까다로웠습니다. Showdown은 불러오는 순간 모든 세대 데이터를 한 번 계산해 두고, 옛 세대는 위 세대 데이터를 상속받아 합쳐 둡니다(1세대 ← 2세대 ← … ← 9세대). 그래서 나중에 데이터만 채워 넣으면 안 됩니다. 빈 껍데기 객체로 시작했다가, 불러올 때 껍데기를 실제 데이터로 채운 뒤 **그 세대와 상속 사슬의 상위 세대를 다시 계산**하게 했습니다.

이 과정에서 하나를 놓쳤다가 문서 사이트에서 잡았습니다. Showdown 랜덤배틀 포맷의 "오늘의 포켓몬" 규칙이 Node에만 있는 `global`을 읽어서, 랜덤배틀을 **브라우저에서** 만들면 바로 오류가 났습니다. Node에서 돌리는 테스트로는 보이지 않던 문제라, 빌드에서 `globalThis`로 바꾸고 배포 번들에 `global.`이 남아 있으면 CI가 실패하도록 막았습니다.

## 구조: 한 턴이 흘러가는 길

1. **`submitAction()`**: 받은 행동을 `getRequest()`가 제시한 선택지와 대조해 검증하고, Showdown 선택 문자열로 바꿔 시뮬레이터에 넘깁니다.
2. **시뮬레이터가 턴을 진행**하면서 프로토콜 로그를 한 줄씩 씁니다(빠른 경로 패치 위에서).
3. 엔진은 시뮬레이터의 `log.push`를 가로채, **줄이 쓰이는 바로 그 순간** 해석해서 타입 있는 이벤트(`move_use`, `damage`, `switch`, `mega_evolve` …)로 바꿉니다.
4. **`emit()`**: 이벤트를 구독자에게 알립니다. React 훅, 다국어 로그 포매터, CLI는 모두 이 구독자입니다.
5. **턴이 끝나면** 엔진이 추적하던 HP·상태를 시뮬레이터의 실제 값과 맞춰 보고, 어긋난 만큼 보정 이벤트를 냅니다.

## 핵심 구현

### 1. 로그가 쓰이는 순간에 해석하기

턴이 끝난 뒤 로그를 한꺼번에 해석하면, 그 줄이 쓰였을 때의 상태를 이미 잃은 뒤입니다. 그래서 시뮬레이터의 `log.push`를 감싸 줄이 들어오는 즉시 해석합니다. 정확한 HP는 `|split|` 다음의 비공개 줄에만 있고 바로 뒤에 퍼센트 공개 줄이 따라오므로, 작은 상태 기계로 비공개 줄만 씁니다.

```ts
log.push = function (...lines: string[]) {
  const n = Array.prototype.push.apply(this, lines)
  if (self.ready) for (const line of lines) self.parseLine(line)
  return n
}
```

급소·상성 줄은 잠시 들고 있다가 바로 다음 `damage` 이벤트에 붙입니다. Showdown 로그는 2배와 4배를 구분하지 않아서, 상성 배율은 그 순간 진행 중인 기술의 타입과 대상의 타입으로 직접 계산해 넣습니다(0.25·0.5·2·4).

### 2. 로그 없이 바뀐 상태를 보정 이벤트로

엔진은 포켓몬마다 마지막으로 알린 HP와 상태이상을 기억합니다. 교체가 일어날 때와 매 턴이 끝날 때 이 값을 시뮬레이터의 실제 값과 비교해, 다르면 그 차이만큼 `heal`·`damage`·`status_apply`·`status_remove`를 만들어 냅니다. 덕분에 **이벤트만 순서대로 따라가도 HP가 시뮬레이터와 정확히 같아집니다.**

### 3. 언어와 무관한 메시지 → 언어별 문장

처음에는 한국어 문장을 이벤트마다 직접 만들었고, Pokestra는 같은 구조의 영어·일본어 포매터(약 660줄)를 따로 갖고 있었습니다. 문장을 고칠 때마다 세 곳을 고쳐야 했습니다. 그래서 두 단계로 나눴습니다.

1. **이벤트 → 메시지:** `{ key: 'move.use', params: { pokemon, move } }`처럼 언어와 무관한 메시지로 바꿉니다. UI는 이걸로 이름을 굵게 하거나 아이콘을 붙일 수도 있습니다.
2. **메시지 → 문장:** 언어별 로케일(문장 틀 + 용어)이 문장으로 바꿉니다. 한국어·영어·일본어가 들어 있고, 새 언어는 로케일 하나를 등록하면 됩니다.

번역할 양을 줄인 게 핵심입니다. 포켓몬·기술·특성·도구 이름은 PokeAPI 데이터(9개 언어)에서 가져오고, 스텔스록·트릭룸·도발처럼 **기술·특성 이름과 같은 상태 이름은 따로 번역하지 않고 그 이름을 그대로 씁니다.** 한국어 조사(이/가, 은/는, (으)로)는 앞 글자의 받침을 유니코드로 계산해 고릅니다.

```ts
const batchim = (code - 0xac00) % 28
if (pair === '(으)로' && batchim === 8) return prev + '로'   // ㄹ 받침 뒤에도 '로'
return prev + (batchim !== 0 ? withB : withoutB)
```

예전 출력과 새 출력을 300판, 이벤트 약 10만 개에서 한 줄씩 비교해, 의도한 개선 말고는 문장이 바뀌지 않았는지 확인했습니다.

### 4. 1\~9세대와 세대별 기믹

`gen: 1~9`를 주면 그 세대의 Showdown 포맷, 데이터, 데미지 계산기로 배틀합니다. 메가진화·울트라버스트·Z기술·다이맥스·테라스탈은 같은 모양의 행동 플래그로 다룹니다.

```ts
const req = engine.getRequest('p1')      // { can_mega_evolve: true, … }
engine.submitAction({ type: 'move', player: 'p1', pokemon_id: 'p1_0', move_index: 0, mega: true })
```

세대마다 가능한 형식이 달라서(더블은 3세대부터, 트리플은 5·6·9세대, 로테이션은 9세대만) 맞지 않는 조합은 배틀을 만들 때 거절합니다. 팀 프리뷰 기본값도 세대·포맷 규칙에서 읽어 옵니다.

### 5. Smogon 랜덤배틀 그대로

`createRandomBattle({ gen, seed, level })` 한 줄로 Showdown 공식 생성기의 팀과 실제 랜덤배틀 포맷 규칙(종 클로즈, 수면 클로즈 등)으로 배틀을 만듭니다. 포켓몬별 레벨·역할·기술 후보도 조회할 수 있습니다.

랜덤배틀은 약한 포켓몬일수록 레벨을 높여 균형을 맞춥니다. 데이터를 분석해 보니 공식이 아니라 종마다 정해 둔 값이었습니다(9세대 Lv 64\~100).

| 종족값 | 평균 레벨 |
|---|---|
| 400 미만 | 94 |
| 500\~549 | 83.5 |
| 600\~699 | 76 |
| 700 이상 | 70 |

종족값과 강하게 반비례하지만(상관계수 −0.78, 종족값 100마다 약 6.5레벨), 특성·기술폭으로 조정됩니다. 코라이돈은 종족값 670에 Lv 64, 게으름이 있는 게을킹은 같은 670에 Lv 84입니다. 실제로 생성된 팀 수백 마리를 조회 API의 레벨과 대조하는 테스트를 세대마다 둡니다.

### 6. Showdown에 없는 로테이션 배틀

Showdown에는 로테이션이 이름만 있고 규칙은 구현되어 있지 않습니다. 트리플 배틀 위에서 몇 가지 메서드를 **런타임에 감싸**, 로테이션으로 표시한 배틀에서만 앞 포켓몬끼리 싸우고 턴 시작에 자리를 돌리게 했습니다. 다른 배틀은 원래 메서드를 그대로 씁니다.

### 7. 요청에 숨은 정보 채워 넣기

Showdown은 상대에게 정보를 흘리지 않으려고 숨은 교체 불가를 `maybeTrapped`로만 알려 줍니다. 엔진은 양쪽을 다 아는 쪽이므로 실제 상태로 확정합니다. 그래서 화면에 보이는 선택지는 **누르면 반드시 받아들여지는 것**만 남습니다.

### 8. 교체: 원인까지 전달하기

유턴·볼트체인지·배턴터치·꼬리자르기·탈출버튼·탈출팩·위기회피는 모두 "턴 중간 교체"라 Showdown 요청만 보면 구분되지 않습니다. 그런데 배턴터치는 랭크가, 꼬리자르기는 대타가 넘어가니 화면도 AI도 무엇 때문인지 알아야 합니다. 교체 요청과 `switch` 이벤트에 원인을 붙였습니다.

```ts
engine.getRequest('p1')
// → { type: 'switch', reason: 'self_switch', source: { kind: 'move', id: 'baton-pass' }, … }
// 날려버리기·레드카드로 끌려 나오면 switch 이벤트에 forced: true, source: { kind: 'item', id: 'red-card' }
```

교체를 막거나 강제하는 규칙은 Showdown 판정 그대로지만, 엔진이 그것을 제대로 넘기는지는 따로 확인했습니다. 구속 21가지(그림자밟기는 6세대부터 고스트에게 안 통하고 5세대에서는 통함, 개미지옥은 비행·부유·풍선에 안 통함, 자력은 강철만, 탈출용껍질은 예외, 구속 중에도 유턴·배턴터치로는 빠짐), 장판(스텔스록은 바위 상성대로 4배 50% \~ 0.25배 3%, 땅에 닿은 독타입은 독압정을 흡수, 통굽부츠·매직가드·부유 예외), 옹골참과 일격기까지 테스트로 고정했습니다.

AI도 원인을 씁니다. 벤치가 없으면 교체 기술을 안 쓰고, 배턴터치는 넘길 랭크와 그 랭크를 잘 쓸 포켓몬(물리·특수)을 따지며, 흡반·뿌리박기·다이맥스 상대에게는 날려버리기를 쓰지 않고, 교체해 들어갈 포켓몬을 고를 때 장판 피해를 계산합니다.

### 9. 손가락흔들기 모드: 노력치로 닿지 않는 능력치

모든 포켓몬의 기술이 손가락흔들기 하나이고, 포켓몬은 고르거나 랜덤으로, HP·공격·방어·특공·특방·스피드는 1\~9999 사이에서 마음대로 정하는 모드입니다.

```ts
createMetronomeBattle({
  seed: 3, level: 50, stats: { hp: 999 },                      // 전체 → 팀 → 포켓몬 순으로 덮어쓴다
  p1: { team: ['pikachu', { species: 'snorlax', stats: { attack: 400, speed: 1 } }] },
  p2: { team: 'random' },                                      // 시드로 재현
})
```

HP 999 같은 값은 노력치·개체값·성격으로 만들 수 없어서, Showdown에 규칙(`Custom Stats Mod`) 하나를 런타임에 등록해 배틀 시작 직후 실제 능력치를 바꿉니다. 폼체인지가 종족값으로 다시 계산해도 값을 유지하고, 변신은 Showdown 그대로 상대의 (바뀐) 능력치를 복사합니다. 데미지 미리보기도 바뀐 능력치를 쓰도록, 계산기가 계산 도중 포켓몬을 복제하며 능력치를 다시 계산하는 부분까지 막았습니다. 능력치 값은 포맷 규칙에 실어 두어 저장된 입력 로그만으로 같은 배틀을 다시 재생할 수 있습니다.

## 검증

### 회귀 전수 점검: 놓친 걸 찾는 장치

배틀 판정은 Showdown이 하니, 틀릴 수 있는 곳은 엔진이 그 위에 얹은 부분입니다(이벤트 변환, 로그 문장, 요청). 무작위 퍼징은 자주 나오는 상황만 계속 밟습니다. 그래서 **모든 경우를 한 번씩은 밟는** 점검을 따로 만들었습니다.

- **대상:** 9세대 기술 685개, 9세대에 없는 기술 153개(그 기술이 있던 마지막 세대에서), 특성 310개, 도구 224개를 각각 배틀에 넣고, 1\~9세대 랜덤배틀과 9세대 더블을 돌립니다.
- **찾는 것:** 처리 못한 Showdown 로그, 전용 문장 없이 "뮤: 방어" 같은 범용 문장으로 나간 로그, 한국어 로그에 섞인 영어, 문장이 아예 없는 상태, **이벤트만으로 다시 계산한 HP·상태이상·랭크가 실제와 다른 경우**, 엔진이 내준 행동을 Showdown이 거부하는 경우.
- **고정:** CI가 매번 돌리고 의도하지 않은 결과가 하나라도 나오면 실패합니다. 세대마다 고정 시드 배틀의 한국어·영어 전체 로그도 스냅샷으로 고정해, 판정·이벤트·문장 중 무엇이 바뀌어도 리뷰에서 보입니다.

처음 돌렸을 때 **약 360종**이 나왔습니다. 대표적인 것들입니다.

| 찾은 것 | 원인 | 해결 |
|---|---|---|
| 탁쳐서떨어뜨리기에 맞으면 "먹다남은음식을 다 써버렸다!" | 아이템이 사라진 원인을 이벤트에 담지 않음 | 원인(먹음·탁쳐서떨어뜨리기·벌레먹음·불사르기·트릭 …)과 상대를 담고 원인별 문장 |
| 한국어에서만 "뮤: 방어"처럼 나오는 상태 30여 종 | 영어·일본어에만 문장이 있었음 | 한국어 문장 추가 |
| 멸망의노래·사슬묶기·트집·충전 등 문장이 아예 없음 | 보여줄 상태 목록에서 빠짐 | 30여 종 추가 (멸망 카운트 숫자 포함) |
| 배북·흑안개·변신 뒤 이벤트상 랭크가 실제와 다름 | 랭크를 "정하는" 로그에는 숫자가 없음 | 바뀐 랭크 전체를 담은 `stat_set` 이벤트 |
| 썰렁개그가 "힘을 모으고 있다!" | 준비 턴 로그를 모으기 기술로 해석 | 전용 처리 |
| Z크리스탈·Z변화기술 이름이 영어 | 이름 데이터에 없음 | 타입·포켓몬 이름 + Z로 조립 (페어리Z, Z날개쉬기) |

언어별로 문장을 약 200개씩 더했고, 다시 돌리면 의도된 차이(숨은 정보인 봉인을 엔진이 미리 막는 것, 이름 데이터 자체가 없는 2세대 아이템) 말고는 0건입니다.

**표본 크기도 중요했습니다.** 랜덤배틀을 세대당 60판 돌렸을 때는 깨끗했는데, 300판으로 늘리자 22종이 더 나왔습니다. 그중 하나는 Z나비춤이었습니다. 떨어진 랭크를 되돌린 직후 바로 랭크가 오르는데, 엔진이 "되돌린 뒤의 랭크"를 읽는 시점에는 시뮬레이터가 이미 상승까지 적용해 둬서 상승이 두 번 세어졌습니다. 다음 로그 줄이 같은 포켓몬의 상승이면 그만큼 빼서 기록하도록 고쳤습니다.

### 퍼징: 배틀마다 8가지 불변식

| 항목 | 분포 |
|---|---|
| 형식 | 싱글 65% · 더블 15% · 트리플 10% · 로테이션 10%, 20%는 팀 프리뷰 |
| 세대 | 30%는 그 형식이 있는 1\~8세대 (그 세대 랜덤배틀 세트, 메가·Z·다이맥스 포함) |
| 팀 | Showdown 랜덤배틀 세트 50% · 종·특성·도구·기술·레벨까지 무작위로 섞은 팀 50% |

1. 예외가 나지 않는다.
2. 엔진이 제시한 행동은 시뮬레이터가 모두 받아들인다.
3. 해석하지 못한 프로토콜 줄이 하나도 없다.
4. 모든 이벤트는 실제로 있는 포켓몬을 가리킨다.
5. **이벤트만으로 다시 계산한 HP가 시뮬레이터의 실제 HP와 같다.**
6. 기절 수와 승자가 서로 맞는다.
7. 같은 시드로 다시 돌리면 같은 로그가 나온다(1% 표본).
8. **빠른 경로와 Showdown 원본 경로의 로그가 같다(전수).**

푸시마다 GitHub Actions에서 타입 검사, 테스트 235개, 회귀 전수 점검, 배포 번들 검사, 퍼징 1만 번이 돌고, 수동 실행 워크플로는 10개 샤드 × 100만 번을 병렬로 돌립니다. 모든 배틀은 시드로 재현됩니다.

### 테스트와 분석이 잡은 버그

| 버그 | 원인 | 해결 |
|---|---|---|
| 낼 수 있는 행동이 0개 | 봉인으로 모든 기술이 막히고 교체할 포켓몬도 없을 때 | 발버둥으로 이어지는 행동 제시 |
| 이미 들어오기로 한 포켓몬을 또 교체 후보로 | 탈출팩처럼 턴 중간 강제 교체 뒤의 대기열을 안 봄 | 행동 대기열을 확인해 제외 |
| 미래예지 데미지가 엉뚱한 기술 데미지로 | 출처 없는 데미지를 "마지막에 쓴 기술"로 처리 | 미래예지·파멸의소원 적중을 따로 인식 |
| 대타출동 HP 비용이 공격 명중으로 | 기술 사용자 자신이 받은 데미지도 명중으로 처리 | 자기 기술로 잃은 HP는 명중이 아님 |
| 급소 표시가 다음 공격에 붙음 | 대타가 막은 급소의 표시가 지워지지 않음 | 새 기술마다 초기화, 대타 피격에 붙임 |
| 4배 약점이 2배로 기록 | Showdown 로그가 배율을 구분하지 않음 | 타입 상성으로 직접 계산 |
| 데미지 예상이 3%에서 벗어남 | 스텔라 테라스탈·바뀐 타입·슬로스타트 등을 계산기에 안 넘김 | 원인 분류 완료, 실시간 상태 기반으로 개선 예정 |
| 브라우저에서 랜덤배틀 오류 | Showdown 규칙이 Node 전용 `global`을 읽음 | 빌드에서 `globalThis`로, CI가 재발 방지 |
| 자연회복 문장이 두 번 | 상태를 지우기 **전에** 로그 줄이 쓰여 보정 단계가 한 번 더 냄 | 줄 기준으로 '없음'을 기록 |
| 기절한 포켓몬 대신 내보낼 때 "돌아와!" | 나가는 포켓몬이 이미 기절했는지 보지 않음 | 기절 후 교체는 "가랏!"만 |

데미지 예상 오차는 이벤트와 별개로, 랜덤 배틀 1,500판에서 예상 범위와 실제 데미지를 대조하는 차등 테스트를 만들어 찾았습니다.

## CLI와 문서 사이트

- **CLI:** `npx pokebattle play`(AI와 대전), `watch`(관전), `sim`(대량 시뮬레이션). `--lang ko|en|ja`, `--gen`, `--level`, `--json`(다른 프로그램이 받아 쓰는 이벤트 스트림)을 지원하고, 한글·가나 폭에 맞춰 줄을 맞춥니다.
- **CLI 손가락흔들기:** `npx pokebattle watch --metronome --hp 999`, `play --metronome --p1 pikachu,snorlax --p2 random --spe 1`.
- **문서 사이트(위의 사이트 열기):** 배틀 데모, 문서 18쪽, 실행 예제 25개. 예제를 누르면 실제 배포 번들이 브라우저에서 돌고 결과가 텍스트로 찍힙니다. Showdown 대비 성능을 수치·막대로 보여 주고, 방문자가 직접 재 볼 수 있습니다. 한국어·영어를 고르면 예제 코드의 주석, 실행한 배틀 로그, 데미지 KO 문구(`formatKO`)까지 그 언어로 바뀝니다.

## 배틀 데모: 엔진을 실제 게임처럼 보여 주기

문서 사이트의 [배틀 데모](/portfolio/pokebattle-engine/#/battle)는 배포 번들을 브라우저에서 그대로 돌리는 싱글 배틀입니다. 처음에는 Pokestra 안에 있던 배틀 시뮬레이터였는데, Pokestra를 도감에 집중시키면서 엔진이 자기 능력을 끝까지 보여 줄 수 있는 이쪽으로 옮겼습니다.

| 항목 | 내용 |

데모를 만들며 엔진에도 필요한 것을 채웠습니다. 팀 편집기를 위해 `getLearnset`(Showdown 검증기와 같은 기술 목록)·`listItems`·`getItem`을 공개했고, 이름 데이터에 폼 이름을 넣어 "로토무 (Wash)" 대신 "워시로토무"가 로그까지 나오게 했습니다. PokeAPI에 한국어 이름이 비어 있는 폼은 공식 명칭으로 채웠고, 이름 끝이 괄호나 X·Z로 끝나도 조사가 맞게(메가리자몽X가) 고쳤습니다.

리플레이는 엔진이 결정적이라는 점을 그대로 이용합니다. AI를 다시 돌리지 않고 기록한 행동만 넣기 때문에, AI가 바뀌어도 예전 링크가 같은 결과를 냅니다. 일반·손가락흔들기 배틀 모두 링크를 새 브라우저에서 열어 승패·마지막 턴·마지막 로그 줄이 원래 배틀과 같은지 확인했습니다.

## 배운 점

- **다시 만들기보다 잘 감싸기.** 이미 검증된 구현이 있다면 내 일은 그 바깥을 쓰기 좋게 만드는 것이다. 대신 감싼 쪽이 어긋나지 않는다는 걸 끝까지 증명해야 한다.
- **빠르게 만들기 전에, 같다는 걸 증명할 장치부터.** 로그 동일성 검사가 먼저 있었기 때문에 Showdown 내부를 고치는 위험한 최적화를 자신 있게 넣을 수 있었다.
- **측정하면 짐작이 틀린다.** 느린 곳은 내 래퍼라고 생각했지만, 프로파일은 시뮬레이터 내부를 가리켰다.
- **번역할 양을 줄이는 게 다국어의 시작이다.** 이름과 이름 붙은 상태를 데이터에서 가져오자 언어마다 써야 할 문장이 크게 줄었다.
- **무작위 테스트는 흔한 길만 걷는다.** 퍼징 수만 판이 통과해도 탁쳐서떨어뜨리기 문장 하나 틀린 걸 못 잡았다. 경우를 하나씩 다 밟는 전수 점검과, 결과 전체를 고정하는 스냅샷이 따로 있어야 했다. 그리고 표본을 늘릴 때마다 드문 경우가 더 나온다.
