## 개요

도로 아래 지반 침하(싱크홀) 위험을 분석하는 서비스에서, 전체 구조 설계보다는 특정 기능의 구현과 성능 개선, 유지보수를 맡았습니다.

## 한 일

### 대량 데이터 조회

분석 데이터가 많아지면서, 많은 데이터를 한 번의 요청으로 받아 오는 방식이 화면보다 먼저 병목이 됐습니다.

- 조회 요청을 여러 단위로 분할
- 분할한 요청을 병렬로 보내는 비동기 조회
- 여러 응답을 하나로 합쳐 화면에 표시
- 대량 처리 과정의 응답 흐름과 오류 상황 대응

### 분석 데이터 필터링

- 조건별 필터링 기능
- 필터 조건에 따른 조회 데이터 갱신
- 조회와 필터 처리 로직 개선
- RSA 관련 분석과 기능 구현

### Bounding Box 편집기

- 이미지 위 Bounding Box 편집기의 오류 원인 분석
- 좌표와 편집 상태에 관한 문제 수정
- 좌표 데이터와 실제 화면 표시가 어긋나는 문제 점검
- 편집 중 생기는 예외 처리 개선

### 문서화

- 기존 기능과 데이터 처리 구조 분석
- 오류 원인과 수정 내용 정리
- 유지보수용 기술 문서 작성

## 직접 내린 결정

| 문제 | 대응 |
|---|---|
| 대량 데이터 조회 부담 | 요청 분할과 병렬 처리 |
| 복잡한 데이터 검색 | 조건별 필터링 로직 개선 |
| Bounding Box 편집 오류 | 좌표와 편집 상태 처리 검토 |
| 기존 코드 이해와 유지보수 | 기능 분석과 기술 문서화 |
| 기존 구조 안에서의 부분 수정 | 변경 범위를 좁힌 기능 개선 |

## 배운 점

- 데이터가 많아질수록 화면보다 요청 방식이 먼저 병목이 된다.
- 남이 만든 구조 안에서 고칠 때는, 고칠 범위를 좁게 정하는 것이 안전하다.
- 고친 이유를 적어 두지 않으면 같은 오류를 다음 사람이 다시 분석하게 된다.
