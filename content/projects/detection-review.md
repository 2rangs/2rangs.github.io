## 개요

AI가 도로 위 위험물을 찾아내면, 사람이 그 결과를 확인하고 판단해야 합니다. 이 서비스는 그 검수 작업을 위한 화면입니다. 탐지 목록, 상세 정보, 이미지, 위치를 하나의 흐름으로 이어, 검수자가 한 건 한 건 빠르게 판단할 수 있게 하는 것이 핵심이었습니다.

## 한 일

### 검수 화면

- 탐지 데이터 목록, 상세 정보, 이미지, 위치 정보를 연결한 화면 구성
- 탐지 유형, 검수 상태, 기간 등 여러 조건을 조합하는 필터
- 이미지 위에 AI가 찾은 객체의 Bounding Box와 라벨 표시
- 한 이미지에 여러 객체가 탐지된 경우 객체별 표시 상태 제어

### 지도

- OpenLayers 기반 지도 인터페이스
- 탐지 데이터의 위도·경도를 지도 객체와 연결
- 지도 검색과 탐지 상세 정보의 상태 연동
- 지도와 이미지 위의 탐지 결과를 하나의 검수 흐름으로 구성

### 국내외 환경 대응

같은 서비스를 국내와 해외 고객이 함께 쓰면서, 환경마다 다른 것이 생각보다 많았습니다.

| 다른 점 | 대응 |
|---|---|
| 고객별 API 환경 | 운영 환경별 설정 분기 |
| 지도 공급자와 지도 데이터 | 서비스 환경에 따른 지도 공급자·데이터 차이 대응 |
| 이미지 스토리지 접근 방식과 경로 | 환경별 이미지 요청 처리 |
| 언어 | 한국어·영어·일본어 리소스 관리, 공통 리소스와 로케일별 표현 분리 |

### 구조 전환

- 기존 Vue 기반 UI를 Quasar 중심으로 전환하고 컴포넌트 구조와 공통 UI 재구성
- [공통 디자인 시스템](/projects/design-system/)으로 화면을 개편하는 PoC: 기존 기능을 유지한 채 구조를 옮길 수 있는지 검증
- Vite 8 기반으로 개발 환경 개선
- 검수 업무 흐름에 맞춰 화면 구성과 사용성 개선

## 문제 해결

### 페이지를 옮길 때 목록 요청이 두 번 더 나가던 문제

Quasar로 옮기던 중, 페이지를 이동할 때마다 목록 조회 요청이 두 번씩 더 나가는 문제가 있었습니다. 검색 컴포넌트 안에서 검색 조건을 `watch`로 지켜보다가, 값이 바뀔 때마다 검색을 실행하는 구조가 원인이었습니다.

검색 조건을 컴포넌트 안에 두지 않고 별도의 store로 옮겨, 조건이 바뀌는 곳을 한 군데로 모았습니다. 그러자 중복 요청이 사라졌습니다. 이 과정은 [2024년 회고](/blog/2024-retrospective/)에도 적었습니다.

### 이미지 존재 확인 요청 문제

운영 중 이미지 요청에서 문제가 생겼습니다. 이미지가 있는지 먼저 확인하는 데 HEAD 요청을 쓰고 있었습니다. 스토리지와 브라우저 요청 정책이 HEAD 요청을 어떻게 다루는지 검토한 뒤, 확인 요청을 GET으로 바꿔 해결했습니다.

이 외에도 배포 환경에 따라 생기는 API 연동 오류, 이미지 요청 실패, 인증 문제를 분석하고 대응했습니다.

## 현재 상태

검수 서비스의 프론트엔드 구현과 운영을 맡고 있습니다. 디자인 시스템 기반의 전체 UI 개편은 PoC 단계까지 진행했습니다.

## 배운 점

- 상태 설계가 UI 복잡도를 결정한다. 조건이 바뀌는 곳이 여러 군데면, 요청도 여러 번 나간다.
- 일관성이 신뢰를 만든다. 같은 탐지 결과가 목록과 이미지, 지도에서 같은 모양으로 보여야 검수자가 결과를 믿는다.
- 해외 서비스는 번역만의 문제가 아니다. 지도, 스토리지, API까지 환경마다 다르다.
