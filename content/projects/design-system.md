## 배경

여러 관제·관리 서비스가 각자 UI를 만들다 보니, 같은 버튼과 표가 서비스마다 조금씩 다른 모양으로 반복해서 만들어지고 있었습니다. 화면을 하나씩 맞추는 건 끝이 없었고, 한 서비스에서 고친 것이 다른 서비스에는 반영되지 않았습니다.

그래서 화면이 아니라 **부품과 기준**을 먼저 만들기로 했습니다. 서비스별로 달라져 있던 UI 구현과 스타일 규칙을 먼저 분석하고, 그 위에 공통 기준을 세웠습니다.

## 설계

### KRDS 위에서 시작한 토큰 체계

기준을 처음부터 새로 만드는 대신, 이미 검증된 공공 표준인 KRDS를 출발점으로 삼았습니다.

- 컬러, 타이포그래피, 간격, 반경을 디자인 토큰으로 정의
- 컴포넌트는 값을 직접 쓰지 않고 토큰만 참조
- 특정 서비스에 묶이지 않는 컴포넌트 API로 설계해, 서비스 요구가 늘어나도 공통 UI의 일관성이 깨지지 않게 함

### Vue와 React: 구현은 나누고 기준은 공유

서비스들은 Vue 3와 React 두 환경에 걸쳐 있었습니다. 하나의 코드로 두 프레임워크를 억지로 감싸면 양쪽 모두 어색해집니다.

- **공유:** 디자인 토큰과 다국어 리소스
- **분리:** 컴포넌트 구현은 각 프레임워크의 방식대로

이렇게 하면 모양과 문구는 같게 유지하면서, 각 환경의 개발자는 익숙한 방식으로 컴포넌트를 씁니다.

## 한 일

### 컴포넌트 라이브러리

- Vue 3 공통 컴포넌트 69종 구축
- 컴포넌트마다 Props, 이벤트, 상태, 사용법 정의
- 서비스마다 따로 만들던 UI 요소를 공통 컴포넌트로 분리
- 다국어 환경에서도 그대로 쓸 수 있도록 리소스 구조 설계
- Storybook으로 컴포넌트를 독립 실행하며 상태별로 검증

### 테스트와 품질 게이트

여러 서비스가 같이 쓰는 부품은, 하나를 고치면 어디가 깨질지 사람이 다 알 수 없습니다. 그래서 기능보다 **검증 장치**를 먼저 갖췄습니다.

| 검증 | 규모 | 무엇을 막나 |
|---|---|---|
| 단위·컴포넌트 테스트 (Vitest) | 1,859건, 라인 커버리지 93.3% | 동작 회귀 |
| 브라우저 품질 게이트 (Chromium) | 608건 | 실제 브라우저 렌더링 문제 |
| 시각 회귀 테스트 | Storybook 스토리 276개 | 의도하지 않은 모양 변화 |
| 접근성 검사 (axe-core) | 컴포넌트 전반 | 접근성 위반 |

### 패키징과 배포

- npm 패키지 빌드·배포 환경 구성
- 배포 전 9단계 스모크 테스트로, 설치하고 불러오는 단계에서 생기는 문제를 먼저 확인
- 내부 개발 서버에 적용해 기존 서비스와의 호환성 검증

### 인수인계 문서

- Figma 인계용 컴포넌트 사양 생성
- 사람뿐 아니라 AI 에이전트도 프로젝트 구조와 개발 규칙을 이해할 수 있도록 기술 문서와 LLM-WIKI 구축

## 직접 내린 결정

| 문제 | 선택 |
|---|---|
| 서비스마다 다른 스타일 | KRDS 기반 디자인 토큰으로 표준화 |
| Vue·React 환경 차이 | 프레임워크별 구현 분리, 토큰·다국어 리소스 공유 |
| 컴포넌트 수정이 다른 화면에 주는 영향 | 자동화 테스트와 시각 회귀 검증 |
| 재사용 컴포넌트의 품질 관리 | Storybook 중심의 독립 검증 |
| 패키지 배포 안정성 | 스모크 테스트와 배포 검증 절차 |
| 개발자·AI 에이전트 인수인계 | 컴포넌트 사양과 LLM-WIKI 문서화 |

## 현재 상태

공통 컴포넌트와 테스트·패키징 기반을 만들고 내부 개발 환경에서 검증했습니다. 운영 중인 서비스 전체에 정식으로 적용하는 단계까지는 가지 않았고, [탐지 데이터 검수 도구](/projects/detection-review/)에서 이 디자인 시스템으로 화면을 개편하는 PoC를 진행했습니다.

## 배운 점

- 예쁜 UI보다 일관된 UI가 더 어렵다.
- 디자인 토큰은 유지보수의 핵심이다.
- 여러 곳이 같이 쓰는 코드는, 바뀐 것이 아무것도 깨뜨리지 않았다는 걸 증명하는 장치가 있어야 고칠 수 있다.

디자인 시스템을 만들며 정리한 생각은 [디자인 시스템이 필요한 이유와 구축 전략](/blog/design-system-basics/)에, 패키지 구성을 고민하며 정리한 내용은 [모노레포란 무엇인가](/blog/what-is-monorepo/)에 적었습니다.
