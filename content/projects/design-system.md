## 개요

| 항목 | 내용 |
|---|---|
| 기준 | KRDS(대한민국 정부 디자인 시스템), 디자인 토큰 |
| 컴포넌트 | Vue 3 공통 컴포넌트 69종 |
| 테스트 | Vitest 1,859건, 라인 커버리지 93.3% |
| 브라우저 검증 | Chromium 품질 게이트 608건, 시각 회귀 대상 Storybook 스토리 276개 |
| 배포 | npm 패키지, 배포 전 9단계 스모크 테스트 |

여러 관제·관리 서비스가 각자 UI를 만들다 보니, 같은 버튼과 표가 서비스마다 조금씩 다른 모양으로 반복해서 만들어지고 있었습니다. 화면을 하나씩 맞추는 건 끝이 없었고, 한 서비스에서 고친 것이 다른 서비스에는 반영되지 않았습니다.

그래서 화면보다 부품과 기준을 먼저 만들기로 하고, 서비스별로 달라져 있던 UI 구현과 스타일 규칙을 분석해 공통 기준을 세웠습니다. 프론트엔드 아키텍처와 디자인 시스템의 설계·구현을 주도했습니다.

## 설계

### KRDS 위에서 시작한 토큰 체계

기준은 공공 표준인 KRDS에서 출발했습니다. 컬러, 타이포그래피, 간격, 반경을 디자인 토큰으로 정의하고, 컴포넌트는 값을 직접 쓰지 않고 토큰만 참조하게 해서 색이나 간격을 바꿀 때 토큰 한 군데만 고치면 됩니다. 컴포넌트 API는 특정 서비스에 묶이지 않게 설계해, 한 서비스의 요구 때문에 공통 컴포넌트가 그 서비스 전용으로 바뀌지 않도록 했습니다.

### Vue와 React는 토큰만 공유

서비스들은 Vue 3와 React 두 환경에 걸쳐 있었습니다. 하나의 코드로 두 프레임워크를 감싸면 양쪽 모두 어색해지기 때문에, 디자인 토큰과 다국어 리소스만 공유하고 컴포넌트 구현은 프레임워크마다 따로 두었습니다. 모양과 문구는 같고, 각 환경의 개발자는 익숙한 방식으로 컴포넌트를 씁니다.

## 컴포넌트 라이브러리

서비스마다 따로 만들던 UI 요소를 공통 컴포넌트로 분리해 Vue 3 컴포넌트 69종을 만들었습니다. 컴포넌트마다 Props, 이벤트, 상태, 사용법을 정의했고, 다국어 환경에서도 그대로 쓸 수 있도록 리소스 구조를 잡았습니다. 각 컴포넌트는 Storybook에서 독립적으로 띄워 상태별로 확인했습니다.

## 테스트와 품질 게이트

여러 서비스가 같이 쓰는 부품은 하나를 고치면 어디가 깨질지 사람이 다 알 수 없어서, 기능을 늘리기 전에 검증 장치부터 갖췄습니다. 동작 회귀는 Vitest 단위·컴포넌트 테스트 1,859건(라인 커버리지 93.3%)으로, 실제 브라우저 렌더링 문제는 Chromium 품질 게이트 608건으로, 의도하지 않은 모양 변화는 Storybook 스토리 276개의 시각 회귀 테스트로 확인합니다. 컴포넌트 전반에 axe-core 접근성 검사도 돌립니다.

## 패키징, 배포, 인수인계 문서

npm 패키지로 빌드·배포하는 환경을 구성하고, 배포 전에 9단계 스모크 테스트를 돌려 설치하고 불러오는 단계에서 생기는 문제를 먼저 확인했습니다. 만든 패키지는 내부 개발 서버에 적용해 기존 서비스와 호환되는지 검증했습니다.

Figma로 인계할 컴포넌트 사양을 생성했고, 사람뿐 아니라 AI 에이전트도 프로젝트 구조와 개발 규칙을 이해할 수 있도록 기술 문서와 LLM-WIKI를 만들었습니다.

## 현재 상태

공통 컴포넌트와 테스트·패키징 기반을 만들고 내부 개발 환경에서 검증했습니다. 운영 중인 서비스 전체에 정식으로 적용하는 단계까지는 가지 않았고, [탐지 데이터 검수 도구](/projects/detection-review/)에서 이 디자인 시스템으로 화면을 개편하는 PoC를 진행했습니다.

## 배운 점

여러 곳이 같이 쓰는 코드는 바뀐 것이 아무것도 깨뜨리지 않았다는 걸 보여 줄 장치가 있어야 마음 놓고 고칠 수 있었습니다.

디자인 시스템을 만들며 정리한 생각은 [디자인 시스템이 필요한 이유와 구축 전략](/blog/design-system-basics/)에, 패키지 구성을 고민하며 정리한 내용은 [모노레포란 무엇인가](/blog/what-is-monorepo/)에 적었습니다.
