## 시작한 이유

여러 서비스가 각자 UI를 만들다 보니 같은 버튼과 표가 서비스마다 조금씩 다른 모양으로 반복해서 만들어지고 있었습니다. 화면을 하나씩 맞추는 일은 끝이 없었고, 한 서비스에서 고친 것이 다른 서비스에는 반영되지 않았습니다. 그래서 화면보다 부품과 기준을 먼저 만들기로 했고, 설계와 구현을 주도했습니다.

## 기준 세우기

먼저 서비스별로 달라져 있던 UI 구현과 스타일 규칙을 모아 비교했습니다. 기준은 공공 표준인 KRDS에서 출발해 컬러, 타이포그래피, 간격 같은 값을 디자인 토큰으로 정의했습니다. 컴포넌트는 값을 직접 쓰지 않고 토큰만 참조하게 해서, 색이나 간격을 바꿀 때 한 군데만 고치면 되도록 했습니다.

서비스들이 Vue와 React 두 환경에 걸쳐 있어서, 하나의 코드로 두 프레임워크를 억지로 감싸지 않고 토큰과 다국어 리소스만 공유했습니다. 컴포넌트 구현은 프레임워크마다 따로 두어 각 환경의 개발자가 익숙한 방식으로 쓰게 했습니다.

## 컴포넌트를 만들고 검증한 과정

서비스마다 따로 만들던 UI 요소를 공통 컴포넌트로 하나씩 분리했습니다. 컴포넌트마다 Props, 이벤트, 상태, 사용법을 정하고, 특정 서비스의 요구 때문에 공통 컴포넌트가 그 서비스 전용으로 바뀌지 않도록 API를 설계했습니다. 만든 컴포넌트는 Storybook에서 따로 띄워 상태별로 확인했습니다.

여러 서비스가 같이 쓰는 부품은 하나를 고쳤을 때 어디가 깨질지 사람이 다 알 수 없습니다. 그래서 컴포넌트를 늘리기 전에 검증 장치부터 갖췄습니다. 동작은 단위·컴포넌트 테스트로, 실제 브라우저에서의 렌더링과 모양 변화는 브라우저 테스트와 시각 회귀 테스트로 확인하고, 접근성 검사도 함께 돌렸습니다. 패키지로 배포하기 전에는 설치하고 불러오는 단계에서 문제가 없는지 따로 점검했습니다.

## 인수인계

만든 패키지는 내부 개발 환경에 적용해 기존 서비스와 함께 쓸 수 있는지 확인했습니다. 디자이너에게 넘길 컴포넌트 사양은 Figma로 정리했고, 사람뿐 아니라 AI 에이전트도 프로젝트 구조와 개발 규칙을 이해할 수 있도록 기술 문서와 LLM-WIKI를 작성했습니다.

## 현재 상태

공통 컴포넌트와 검증·배포 기반을 만들어 내부 개발 환경에서 검증한 단계입니다. 운영 중인 서비스 전체에 정식으로 적용하지는 않았고, [탐지 데이터 검수 도구](/projects/detection-review/)에서 이 디자인 시스템으로 화면을 개편하는 PoC를 진행했습니다.

디자인 시스템을 만들며 한 생각은 [디자인 시스템이 필요한 이유와 구축 전략](/blog/design-system-basics/)에, 패키지 구성을 고민한 내용은 [모노레포란 무엇인가](/blog/what-is-monorepo/)에 적었습니다.

## 배운 점

여러 곳이 같이 쓰는 코드는 바뀐 것이 아무것도 깨뜨리지 않았다는 걸 보여 줄 장치가 있어야 마음 놓고 고칠 수 있었습니다.

기준은 정해 두는 것만으로는 지켜지지 않았습니다. 규칙과 함께 왜 그렇게 정했는지까지 문서로 남겨야 다음 사람이 같은 판단을 할 수 있었습니다.

## AI를 대하는 태도

LLM-WIKI를 만든 건 AI 에이전트가 이 프로젝트의 규칙을 알고 코드를 쓰게 하려는 목적이었습니다. 반복되는 컴포넌트 작업과 자료 조사는 AI에게 맡기지만, 나온 결과는 Storybook과 실제 화면에서 다시 확인합니다. 어떤 기준을 공통으로 둘지는 제가 정합니다.
