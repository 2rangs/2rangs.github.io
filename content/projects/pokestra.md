## 두 번 만든 프로젝트

**첫 번째(2026년 2\~3월)** 는 평범한 도감이었습니다. 목록을 페이지 단위로 PokeAPI에서 받아 오고, 카드 하나마다 상세 정보를 다시 요청했습니다. 필터 하나를 바꿀 때마다 네트워크를 기다려야 했고, 1,000개가 넘는 포켓몬을 "배울 수 있는 기술"로 거르는 건 사실상 불가능했습니다.

**두 번째(2026년 11월)** 는 구조부터 다시 짰습니다.

- 목록·검색·필터에 필요한 데이터는 미리 만들어 함께 배포
- 3개 언어 지원
- 디자인 시스템 위에서 UI 재구성
- 세대 타임라인, 도구·나무열매, 촘촘한 배치로 도감 자체를 깊게

두 번째 버전에는 한동안 직접 만든 엔진으로 돌리는 배틀 데모와 데미지 계산기도 들어 있었습니다. 지금은 둘 다 엔진 쪽으로 옮기고, Pokestra는 도감만 남겼습니다(아래 "도감에 집중하기로 한 이유").

## 도감에 집중하기로 한 이유

처음에는 팀 빌더와 배틀 화면을, 그다음에는 엔진이 CPU끼리 배틀을 돌리는 데모와 데미지 계산기를 Pokestra에 넣었습니다. 동작은 했지만 도감 앱 안에 반쯤 만든 게임과 계산기가 들어 있는 모양이었고, 엔진은 도감의 한 메뉴 크기로만 자신을 보여 줄 수 있었습니다.

그래서 역할을 나눴습니다.

- **Pokestra는 도감만 합니다.** 배틀 시뮬레이터, 배틀 엔진 데모, 데미지 계산기를 지우고 엔진 의존성도 뺐습니다. 실능치 패널처럼 엔진을 빌려 쓰던 곳은 로컬 데이터와 순수 함수로 다시 만들었습니다.
- **배틀과 계산은 엔진이 직접 보여 줍니다.** [pokebattle-engine](/projects/pokebattle-engine/) 문서 사이트의 [배틀 데모](https://2rangs.github.io/portfolio/pokebattle-engine/#/battle)가 그 자리를 맡습니다. 실제 게임처럼 움직이는 스프라이트와 실제 배틀 배경을 쓰는 배틀 화면, 손가락흔들기 모드, 같은 배틀을 다시 보는 리플레이 링크를 지원하며, 지금 마무리하고 있습니다.

덜어 내고 나니 Pokestra는 "찾고 비교하는 화면"에, 엔진은 "배틀을 돌리는 화면"에 각자 집중할 수 있게 됐습니다.

## 구조

### 데이터: 미리 만들 것과 그때 받을 것을 나누기

모든 데이터를 미리 만들 필요는 없었습니다. **자주, 빠르게 걸러야 하는 데이터만** 미리 만들고, 한 번 보고 마는 데이터는 그때 받기로 나눴습니다.

| 구분 | 데이터 | 방식 |
|---|---|---|
| 미리 만들어 함께 배포 | 목록·검색·필터용 포켓몬, 기술, 특성, 도구·나무열매, 3개 언어 이름 | 스크립트가 PokeAPI REST와 CSV 덤프에서 모아 JSON으로 저장(약 4.0MB) |
| 상세 화면에서 요청 | 도감 설명, 진화 단계, 세대별 기록(`past_types`·`past_abilities`·`past_stats`), 울음소리 주소 | TanStack Query로 요청하고 캐시 |

JSON을 불러올 때 이름·번호로 찾는 조회표를 한 번만 만들어 두고, 어느 화면에서든 같은 조회표를 씁니다. `mr-mime-galar` 같은 폼 이름에서 기본 종(`mr-mime`)을 찾을 때는 알려진 이름 중 가장 긴 앞부분부터 맞춰 봅니다.

### 상태: 성격에 따라 둘 곳을 다르게

| 상태 | 저장 위치 | 이유 |
|---|---|---|
| 언어 | localStorage (Zustand) | 다음에 와도 같은 언어로. 첫 방문은 브라우저 언어를 따름 |
| 도감 필터, 불러온 페이지 수 | sessionStorage (Zustand) | 상세를 보고 돌아와도 보던 자리 그대로, 탭을 닫으면 초기화 |
| 기술·특성·도구·스프라이트 필터, 상세의 탭·세대·암수 | URL 쿼리 | 링크로 공유 가능. `/pokemon/35?gen=5` |
| PokeAPI 응답 | TanStack Query | 같은 포켓몬을 다시 열면 바로 |

## 핵심 구현

### 1. 세대 타임라인: 흩어진 정보를 한 화면에

세대별 스프라이트, 울음소리, "이 포켓몬은 몇 세대에 무엇이 바뀌었나"는 보통 여러 사이트에 흩어져 있습니다. 새 정보를 만드는 대신 **모아서 한 번에 보이게 하는 것**을 차별점으로 잡았습니다. 세대 하나를 고르면 머리말의 스프라이트·타입·특성·종족값이 모두 그 세대 기준으로 바뀌고, 현재와 다른 항목에는 "N세대에 변경"을 붙입니다(예: 픽시는 5세대까지 노말, 6세대부터 페어리).

데이터는 새로 만들지 않았습니다. 상세 화면이 이미 받는 PokeAPI 응답의 `past_*` 기록은 "N세대까지는 이 값"이라는 뜻이라, 고른 세대 G에 대해 `N >= G`인 기록 중 가장 이른 것을 쓰고 없으면 현재 값을 씁니다. 이 계산을 `typesAt`·`abilitiesAt`·`statsAt`·`spriteAt`·`cryAt` 순수 함수로 분리해 실제 응답 픽스처(피카츄, 삐삐)로 테스트했습니다.

- 1세대는 특공/특방 대신 "특수" 한 칸, 1·2세대는 "특성은 3세대부터" 안내, 3·4세대는 숨겨진 특성 없음.
- 1\~5세대를 고르면 옛날 울음소리를, 6세대 이상은 최신 울음소리를 먼저 냅니다.
- 선택 줄은 등장 세대부터만 보여 줘서, 그 세대에 없던 포켓몬을 있는 것처럼 보여 주지 않습니다. 다른 폼은 세대 줄을 숨깁니다.
- 타입 상성은 세대별 상성표가 아니라 현재 기준으로 두고, 그렇다고 표시합니다. 일부만 바뀌어 어느 세대 기준인지 헷갈리는 화면이 가장 피하고 싶은 실패였습니다.

### 2. 촘촘하게, 하지만 읽히게

빈 공간이 많아 한 화면에서 얻는 정보가 적었습니다. 테마의 간격 값을 줄이는 방법은 배치 문제를 못 고치고 버튼까지 작아져서 버렸고, 화면마다 배치를 다시 짰습니다. 기준은 세 가지였습니다.

- **시선.** 스크롤하기 전 첫 화면이 그 화면의 할 일을 끝냅니다. 가장 중요한 정보는 왼쪽 위, 다음은 같은 줄 오른쪽, 그다음 줄 순서로.
- **마우스 동선(Fitts).** 조작은 그것이 바꾸는 결과 바로 위에 두고, 행 전체를 클릭 영역으로 만들고, 결과가 바뀌어도 필터 바가 밀리지 않게 고정했습니다. 다음 행동(더 보기, 이전/다음 포켓몬)은 마지막으로 누른 자리 근처에 둡니다.
- **읽는 방식.** 훑어보는 데이터는 표로(라벨은 흐리게, 값은 진하게, 숫자는 오른쪽 정렬), 읽는 글은 한 줄 65자 안팎으로.

줄이지 않은 것도 정했습니다. 글자 크기와 휴대폰의 44px 터치 영역은 그대로 두고, 빈 공간과 이미지 칸만 줄였습니다. 그리고 **한눈에 이해되지 않는 수치는 목록에서 빼고 상세에서 설명과 함께** 보여 줍니다. 그래서 도구 목록에는 이름·분류·한 줄 설명·맛만 있고, 자연의은혜나 내던지기 위력은 상세 화면에서 짧은 설명(ⓘ)과 함께 나옵니다. `/`를 누르면 검색창으로, 상세 화면에서는 ←/→로 이전·다음으로 갑니다.

### 3. 빈칸도, 밀림도 없는 이미지 로딩

포켓몬 이미지가 20곳 가까이에서 제각각 그려졌고, 28\~40px 자리에 475px 공식 일러스트를 받는 곳도 있었습니다. 이를 `PokeImage` 컴포넌트 하나로 모았습니다.

```ts
// ≤40px: [SV 박스 아이콘, 7세대 박스 아이콘, 도트, 아트워크]
// ≤64px: [도트, 아트워크], >64px: [아트워크, 도트]
const list = displayPx <= SPRITE_MAX_PX ? [sprite, art] : [art, sprite]
if (opts.back) list.unshift(backSpriteUrl(id))
else if (displayPx <= BOX_ICON_MAX_PX) list.unshift(...boxIconUrls(id))
return [...new Set(list.filter(Boolean))]
```

- 표시 크기에 맞는 이미지 후보를 순서대로 시도하고, 모두 실패하면 빈 자리를 남깁니다.
- 크기를 고정하고 로드 전에는 같은 크기의 스켈레톤을 보여 줘 레이아웃이 밀리지 않습니다.
- 상세 화면의 메인 아트워크는 우선순위를 높여 받고, 이전/다음 포켓몬 아트워크는 브라우저가 한가할 때 미리 받아 둡니다.
- 화면을 지연 로딩하는 동안에도 같은 높이의 스켈레톤을 두어, 바닥글이 위아래로 튀지 않게 했습니다.

### 4. 하나의 검색창으로 세 언어, 영문 ID, 번호까지

사용자는 "피카츄", "pikachu", "ピカチュウ", "ぴかちゅう", "Mr. Mime", "mr-mime", "#25", "No.25" 등 무엇이든 입력합니다. 검색어와 이름을 같은 규칙으로 정규화해서 비교합니다.

```ts
function toKatakana(s: string) {
  return s.replace(/[ぁ-ゖ]/g, (c) => String.fromCharCode(c.charCodeAt(0) + 0x60))
}
export function norm(s: string) {
  return toKatakana(s.normalize('NFKC').toLowerCase()).replace(/[\s\-_.'’:・]+/g, '')
}
```

- 전각·반각을 맞추고(NFKC), 히라가나를 가타카나로 바꾸고, 공백·하이픈·점 같은 구분자를 지웁니다.
- 검색 색인은 처음 한 번만 만듭니다.
- 숫자를 입력하면 전국도감 번호로 찾기 때문에 같은 번호의 폼도 함께 나옵니다.
- 입력은 `useDeferredValue`로 처리해, 타이핑은 즉시 반응하고 목록 갱신은 그 뒤를 따라옵니다.
- 이름 정렬은 언어별 `Intl.Collator`를 하나씩만 만들어 재사용합니다.

### 5. 엔진 없이 계산하는 실능치

실능치 패널(Lv50/Lv100 최소·무보정·최대)은 원래 엔진의 계산 함수를 빌려 썼습니다. 엔진을 빼면서 표준 공식을 순수 함수로 옮기고, 알려진 값으로 단위 테스트를 붙였습니다.

```ts
/** HP: ⌊(2B + I + ⌊E/4⌋) · L / 100⌋ + L + 10. 껍질몬(종족값 1)은 항상 1 */
export function calcHp(base: number, level: number, iv: number, ev: number): number {
  if (base === 1) return 1
  return Math.floor(((2 * base + iv + Math.floor(ev / 4)) * level) / 100) + level + 10
}
```

최소는 개체값 0·노력치 0·하락 성격, 무보정은 31·0·무보정, 최대는 31·252·상승 성격입니다. 로컬 종족값만으로 계산하니 패널이 엔진 데이터를 기다리지 않습니다.

### 6. 타입 색을 테마 토큰으로

18개 타입(+스텔라)마다 배경·글자·테두리 색을 `:root` 덮어쓰기가 아니라 Astryx `neutral` 테마를 확장한 커스텀 `pokestra` 테마의 토큰으로 만들었습니다. 라이트·다크 모드가 테마를 따라 함께 바뀌고, Tailwind 유틸리티(`bg-type-fire` 등)로 이어집니다. 실제 빌드된 테마 값을 읽어 **타입 배지 글자 대비가 모든 타입·모드에서 WCAG AA(4.5:1) 이상인지 테스트**합니다. 40px 이하 자리에는 도트 대신 PC 박스 아이콘을 써서 작은 크기에서도 포켓몬이 알아보이게 했습니다.

### 7. 빠진 번역은 컴파일 오류로

```ts
export function defineMessages<const K extends string>(m: {
  ko: Record<K, string>; en: NoInfer<Record<K, string>>; ja: NoInfer<Record<K, string>>
}): Messages<K> { return m }
```

키 목록은 한국어 문구에서만 정해지고, `NoInfer`가 영어·일본어 쪽에서 키가 늘어나지 않게 막습니다. 그래서 **영어나 일본어에 키가 하나라도 빠지면 타입 검사에서 실패**합니다. 혹시 실행 중에 문구가 없으면 한국어, 그다음 키 이름 순으로 대신 보여 줍니다.

### 8. 이펙트 없이 초기화되는 점진 렌더링

긴 목록은 60개씩 나눠 그리고, 끝에 둔 감시 요소가 화면 600px 앞에 오면 다음 묶음을 그립니다. 필터가 바뀌면 처음 개수로 돌아가야 하는데, 이를 `useEffect`로 처리하면 한 번 더 렌더링됩니다. 대신 **"어떤 필터 조합에서의 개수인지"를 함께 저장**하고, 렌더링 중에 필터가 달라졌으면 바로 처음 개수를 쓰게 했습니다.

## 고친 것들

| 문제 | 원인 | 해결 |
|---|---|---|
| 필터를 바꿀 때마다 네트워크 대기 | 카드마다 PokeAPI를 호출 | 목록용 데이터를 미리 만들어 함께 배포(약 4.0MB를 내주고 검색·필터를 네트워크 없이 처리) |
| 이미지가 뜰 때 화면이 튐, 작은 자리에 큰 이미지 | 이미지마다 크기 지정·폴백이 제각각 | `PokeImage`로 통일, 크기 고정 + 같은 크기 스켈레톤, 표시 크기별 소스 선택 |
| 페이지를 옮길 때 바닥글이 위아래로 튐 | 지연 로딩 중 대체 화면에 높이가 없었음 | 실제 화면과 비슷한 높이를 잡아 둔 공통 스켈레톤 |
| 휴대폰에서 메뉴·언어 전환·맨 위로 버튼이 누르기 어려움 | 터치 영역이 44px보다 작았음 | 44px 터치 영역, 고정 머리말 높이에 맞춰 sticky 위치 정렬 |
| 긴 폼 이름이 스프라이트 타일에서 양쪽이 잘림 | 한 줄 말줄임 | 두 줄까지 줄바꿈 |
| 16px 파비콘이 뭉개짐 | 작은 크기에서 세부가 많았음 | 단순한 SVG로 다시 그림 |

세 번째 타입을 고르면 가장 먼저 고른 타입이 빠지는 것(두 타입은 "모두 가진" 조건), 껍질몬은 HP가 항상 1이라 실능치 패널에서 따로 처리하는 것, 암수 모습 차이는 기본 폼에만 표시하는 것(메가진화나 이미 암컷인 폼에 표시가 붙지 않게)처럼, 데이터의 예외를 화면 규칙으로 정리하는 일도 많았습니다.

## 배포

이 블로그 저장소가 Pokestra의 `main`을 받아 `/portfolio/pokestra/` 경로로 빌드해 함께 게시합니다. 엔진 의존성이 빠지면서 빌드는 Pokestra 저장소만으로 끝납니다.

## 배운 점

- **데이터를 어디에 둘지가 곧 UX다.** 미리 만들 데이터와 그때 받을 데이터를 나누고 나니 검색과 필터 코드가 짧아지고 화면이 빨라졌다.
- **상태는 수명에 맞는 곳에.** 언어·필터·공유 링크는 각각 남아야 하는 기간이 달라서 저장 위치도 달라야 했다.
- **새 정보보다 모아 보여 주기가 차별점이 될 수 있다.** 세대 타임라인은 새 데이터 없이, 이미 받던 응답을 한 화면에 정리하는 것만으로 다른 도감과 구별되는 기능이 됐다.
- **촘촘함은 간격을 줄이는 게 아니라 배치를 다시 짜는 일이다.** 시선과 손의 동선을 먼저 정하고 나서야 무엇을 줄일지 보였다.
- **어색한 기능은 다듬기보다 제자리를 찾아 주는 게 답일 때가 있다.** 배틀과 계산기를 엔진의 데모로 옮기자 앱도 엔진도 각자 할 일이 분명해졌다.
- **사이드 프로젝트는 같은 걸 두 번 만들어 볼 수 있는 곳이다.** 처음 구조의 한계를 직접 겪어 봐야 다음 구조의 이유가 분명해진다.
