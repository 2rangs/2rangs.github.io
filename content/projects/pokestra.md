## 두 번 만든 프로젝트

**첫 번째(2026년 2\~3월)** 는 평범한 도감이었습니다. 목록을 페이지 단위로 PokeAPI에서 받아 오고, 카드 하나마다 상세 정보를 다시 요청했습니다. 필터 하나를 바꿀 때마다 네트워크를 기다려야 했고, 1,000개가 넘는 포켓몬을 "배울 수 있는 기술"로 거르는 건 사실상 불가능했습니다.

**두 번째(2026년 11월)** 는 구조부터 다시 짰습니다.

- 목록·검색·필터에 필요한 데이터는 미리 만들어 함께 배포
- 3개 언어 지원
- 디자인 시스템 위에서 UI 재구성
- 세대 타임라인, 도구·나무열매, 촘촘한 배치로 도감 자체를 깊게

두 번째 버전에는 한동안 배틀 데모와 데미지 계산기도 들어 있었습니다. 지금은 둘 다 빼고 도감만 남겼습니다(아래 "도감에 집중하기로 한 이유").

## 화면 구성

| 기술·특성 | 타입·분류·세대 필터, 위력·명중·PP 정렬, 배우는(가진) 포켓몬 목록 |

예전 `/battle`, `/calc` 링크로 들어오면 404 대신 첫 화면으로 조용히 보냅니다.

## 도감에 집중하기로 한 이유

처음에는 팀 빌더와 배틀 화면을, 그다음에는 CPU끼리 배틀을 돌리는 데모와 데미지 계산기를 Pokestra에 넣었습니다. 동작은 했지만 도감 앱 안에 반쯤 만든 게임과 계산기가 들어 있는 모양이었습니다.

그래서 배틀 시뮬레이터, 배틀 데모, 데미지 계산기를 모두 지우고 외부 배틀 엔진 의존성도 뺐습니다. 실능치 패널처럼 그 엔진을 빌려 쓰던 곳은 로컬 데이터와 순수 함수로 다시 만들었습니다. 덜어 내고 나니 Pokestra는 "찾고 비교하는 화면" 하나에 집중할 수 있게 됐습니다.

## 피드백으로 다듬은 UX

화면은 한 번에 정하지 않고, 실제로 써 본 사람의 짧은 피드백을 받을 때마다 고쳐서 다시 보여 주는 식으로 다듬었습니다. 돌아보면 고친 것들은 대부분 "처음 보는 사람이 바로 알아보는가"로 모입니다.

| 받은 피드백 | 바꾼 것 |
|---|---|
| "도감 같지 않다, 카드가 어지럽다" | 옅은 판 위의 큰 그림 → 번호 → 이름 → 타입 순의 갤러리 카드. 휴대폰에서는 게임 도감처럼 한 줄 목록 |
| "바탕에 타입 색 넣지 마라" | 색은 타입 배지와 능력치 막대에만(아래 6번) |
| "불꽃이 땅 타입처럼 보인다" | 배지 색을 게임 레퍼런스 색·아이콘으로 바꾸고 흰 글자 + 옅은 그림자 |

## 구조

### 데이터: 미리 만들 것과 그때 받을 것을 나누기

모든 데이터를 미리 만들 필요는 없었습니다. **자주, 빠르게 걸러야 하는 데이터만** 미리 만들고, 한 번 보고 마는 데이터는 그때 받기로 나눴습니다.

| 구분 | 데이터 | 방식 |
|---|---|---|
| 미리 만들어 함께 배포 | 목록·검색·필터용 포켓몬, 기술, 특성, 도구·나무열매, 3개 언어 이름 | 스크립트가 PokeAPI REST와 CSV 덤프에서 모아 JSON으로 저장(약 4.0MB) |
| 미리 만들어 두고 필요할 때 받기 | PokeAPI에 없는 한국어 도감 설명(포켓몬 위키) | 종마다 작은 파일 하나(1,023개, 합계 4.5MB). 상세 화면이 그 종의 파일만 받는다 |
| 상세 화면에서 요청 | 도감 설명, 진화 단계, 세대별 기록(`past_types`·`past_abilities`·`past_stats`), 울음소리 주소 | TanStack Query로 요청하고 캐시 |

JSON을 불러올 때 이름·번호로 찾는 조회표를 한 번만 만들어 두고, 어느 화면에서든 같은 조회표를 씁니다. `mr-mime-galar` 같은 폼 이름에서 기본 종(`mr-mime`)을 찾을 때는 알려진 이름 중 가장 긴 앞부분부터 맞춰 봅니다.

### 상태: 성격에 따라 둘 곳을 다르게

| 상태 | 저장 위치 | 이유 |
|---|---|---|
| 언어 | localStorage (Zustand) | 다음에 와도 같은 언어로. 첫 방문은 브라우저 언어를 따름 |
| 도감 필터, 불러온 페이지 수 | sessionStorage (Zustand) | 상세를 보고 돌아와도 보던 자리 그대로, 탭을 닫으면 초기화 |
| 기술·특성·도구·스프라이트 필터, 상세의 탭·세대·암수 | URL 쿼리 | 링크로 공유 가능. `/pokemon/35?gen=5` |
| PokeAPI 응답 | TanStack Query | 같은 포켓몬을 다시 열면 바로 |

## 핵심 구현

### 1. 세대 타임라인: 흩어진 정보를 한 화면에

세대별 스프라이트, 울음소리, "이 포켓몬은 몇 세대에 무엇이 바뀌었나"는 보통 여러 사이트에 흩어져 있습니다. 새 정보를 만드는 대신 **모아서 한 번에 보이게 하는 것**을 차별점으로 잡았습니다. 세대 하나를 고르면 머리말의 스프라이트·타입·특성·종족값이 모두 그 세대 기준으로 바뀌고, 현재와 다른 항목에는 "N세대에 변경"을 붙입니다(예: 픽시는 5세대까지 노말, 6세대부터 페어리).

데이터는 새로 만들지 않았습니다. 상세 화면이 이미 받는 PokeAPI 응답의 `past_*` 기록은 "N세대까지는 이 값"이라는 뜻이라, 고른 세대 G에 대해 `N >= G`인 기록 중 가장 이른 것을 쓰고 없으면 현재 값을 씁니다. 이 계산을 `typesAt`·`abilitiesAt`·`statsAt`·`spriteAt`·`cryAt` 순수 함수로 분리해 실제 응답 픽스처(피카츄, 삐삐)로 테스트했습니다.

- 1세대는 특공/특방 대신 "특수" 한 칸, 1·2세대는 "특성은 3세대부터" 안내, 3·4세대는 숨겨진 특성 없음.
- 1\~5세대를 고르면 옛날 울음소리를, 6세대 이상은 최신 울음소리를 먼저 냅니다.
- 선택 줄은 등장 세대부터만 보여 줘서, 그 세대에 없던 포켓몬을 있는 것처럼 보여 주지 않습니다. 다른 폼은 세대 줄을 숨깁니다.
- 타입 상성은 세대별 상성표가 아니라 현재 기준으로 두고, 그렇다고 표시합니다. 일부만 바뀌어 어느 세대 기준인지 헷갈리는 화면이 가장 피하고 싶은 실패였습니다.

### 2. 촘촘하게, 하지만 읽히게

빈 공간이 많아 한 화면에서 얻는 정보가 적었습니다. 테마의 간격 값을 줄이는 방법은 배치 문제를 못 고치고 버튼까지 작아져서 버렸고, 화면마다 배치를 다시 짰습니다. 기준은 세 가지였습니다.

- **시선.** 스크롤하기 전 첫 화면이 그 화면의 할 일을 끝냅니다. 가장 중요한 정보는 왼쪽 위, 다음은 같은 줄 오른쪽, 그다음 줄 순서로.
- **마우스 동선(Fitts).** 조작은 그것이 바꾸는 결과 바로 위에 두고, 행 전체를 클릭 영역으로 만들고, 결과가 바뀌어도 필터 바가 밀리지 않게 고정했습니다. 다음 행동(더 보기, 이전/다음 포켓몬)은 마지막으로 누른 자리 근처에 둡니다.
- **읽는 방식.** 훑어보는 데이터는 표로(라벨은 흐리게, 값은 진하게, 숫자는 오른쪽 정렬), 읽는 글은 한 줄 65자 안팎으로.

줄이지 않은 것도 정했습니다. 글자 크기와 휴대폰의 44px 터치 영역은 그대로 두고, 빈 공간과 이미지 칸만 줄였습니다. 그리고 **한눈에 이해되지 않는 수치는 목록에서 빼고 상세에서 설명과 함께** 보여 줍니다. 그래서 도구 목록에는 이름·분류·한 줄 설명·맛만 있고, 자연의은혜나 내던지기 위력은 상세 화면에서 짧은 설명(ⓘ)과 함께 나옵니다. `/`를 누르면 검색창으로, 상세 화면에서는 ←/→로 이전·다음으로 갑니다.

### 3. 빈칸도, 밀림도 없는 이미지 로딩

포켓몬 이미지가 20곳 가까이에서 제각각 그려졌고, 28\~40px 자리에 475px 공식 일러스트를 받는 곳도 있었습니다. 이를 `PokeImage` 컴포넌트 하나로 모았습니다.

```ts
// ≤40px: [SV 박스 아이콘, 7세대 박스 아이콘, 도트, 아트워크]
// ≤64px: [도트, 아트워크], >64px: [아트워크, 도트]
const list = displayPx <= SPRITE_MAX_PX ? [sprite, art] : [art, sprite]
if (opts.back) list.unshift(backSpriteUrl(id))
else if (displayPx <= BOX_ICON_MAX_PX) list.unshift(...boxIconUrls(id))
return [...new Set(list.filter(Boolean))]
```

- 표시 크기에 맞는 이미지 후보를 순서대로 시도하고, 모두 실패하면 빈 자리를 남깁니다.
- 크기를 고정하고 로드 전에는 같은 크기의 스켈레톤을 보여 줘 레이아웃이 밀리지 않습니다.
- 상세 화면의 메인 아트워크는 우선순위를 높여 받고, 이전/다음 포켓몬 아트워크는 브라우저가 한가할 때 미리 받아 둡니다.
- 화면을 지연 로딩하는 동안에도 같은 높이의 스켈레톤을 두어, 바닥글이 위아래로 튀지 않게 했습니다.

### 4. 하나의 검색창으로 세 언어, 영문 ID, 번호까지

사용자는 "피카츄", "pikachu", "ピカチュウ", "ぴかちゅう", "Mr. Mime", "mr-mime", "#25", "No.25" 등 무엇이든 입력합니다. 검색어와 이름을 같은 규칙으로 정규화해서 비교합니다.

```ts
function toKatakana(s: string) {
  return s.replace(/[ぁ-ゖ]/g, (c) => String.fromCharCode(c.charCodeAt(0) + 0x60))
}
export function norm(s: string) {
  return toKatakana(s.normalize('NFKC').toLowerCase()).replace(/[\s\-_.'’:・]+/g, '')
}
```

- 전각·반각을 맞추고(NFKC), 히라가나를 가타카나로 바꾸고, 공백·하이픈·점 같은 구분자를 지웁니다.
- 검색 색인은 처음 한 번만 만듭니다.
- 숫자를 입력하면 전국도감 번호로 찾기 때문에 같은 번호의 폼도 함께 나옵니다.
- 입력은 `useDeferredValue`로 처리해, 타이핑은 즉시 반응하고 목록 갱신은 그 뒤를 따라옵니다.
- 이름 정렬은 언어별 `Intl.Collator`를 하나씩만 만들어 재사용합니다.
- 한국어 이름은 초성 색인도 함께 만들어 "ㄹㅈㅁ"으로 리자몽을, 기술 이름도 초성으로 찾습니다.

### 5. 로컬 데이터로 계산하는 실능치

실능치 패널(Lv50/Lv100 최소·무보정·최대)은 처음에 외부 배틀 엔진의 계산 함수를 빌려 썼습니다. 그 의존성을 빼면서 표준 공식을 순수 함수로 옮기고, 알려진 값으로 단위 테스트를 붙였습니다.

```ts
/** HP: ⌊(2B + I + ⌊E/4⌋) · L / 100⌋ + L + 10. 껍질몬(종족값 1)은 항상 1 */
export function calcHp(base: number, level: number, iv: number, ev: number): number {
  if (base === 1) return 1
  return Math.floor(((2 * base + iv + Math.floor(ev / 4)) * level) / 100) + level + 10
}
```

최소는 개체값 0·노력치 0·하락 성격, 무보정은 31·0·무보정, 최대는 31·252·상승 성격입니다. 로컬 종족값만으로 계산하니 패널이 다른 데이터를 기다리지 않습니다.

### 6. 색은 두 곳에만: 타입 배지와 능력치 막대

화면을 여러 번 갈아엎으며 얻은 결론은 "색은 의미가 있는 곳에만"이었습니다. 카드 배경을 타입 색으로 칠한 버전은 화면이 시끄럽고 정보 구분이 오히려 흐려져서 버렸고, 지금은 **타입 배지와 능력치 막대만 색을 가집니다.**

- **타입 배지.** 게임에서 익숙한 색과 아이콘을 따랐습니다. 18개 타입 색을 `:root` 덮어쓰기가 아니라 Astryx `neutral` 테마를 확장한 커스텀 `pokestra` 테마의 토큰으로 만들어 라이트·다크 모드가 함께 바뀌고, 생성 스크립트 하나가 테마 값·Tailwind 유틸리티(`bg-type-fire` 등)·클래스 표를 같이 씁니다. 불꽃과 땅처럼 비슷해 보이는 색은 아이콘과 흰 글자·옅은 그림자로 구분합니다.
- **능력치 막대.** 모든 막대가 같은 색이라 비교가 안 된다는 피드백을 받고, 30/60/90/120/150 구간마다 다른 색을 줬습니다. 막대 옆에는 "전체 1,025종 중 상위 N%"를 소수 첫째 자리까지 붙여 숫자의 의미를 바로 읽게 했습니다(예: 리자몽 특공 109는 상위 12.0%, 해피너스 HP 255는 0.1% 대신 "단독 1위", 같은 값이 여럿이면 "공동 1위").

40px 이하 자리에는 도트 대신 PC 박스 아이콘을 써서 작은 크기에서도 포켓몬이 알아보이게 했습니다.

### 7. 빠진 번역은 컴파일 오류로

```ts
export function defineMessages<const K extends string>(m: {
  ko: Record<K, string>; en: NoInfer<Record<K, string>>; ja: NoInfer<Record<K, string>>
}): Messages<K> { return m }
```

키 목록은 한국어 문구에서만 정해지고, `NoInfer`가 영어·일본어 쪽에서 키가 늘어나지 않게 막습니다. 그래서 **영어나 일본어에 키가 하나라도 빠지면 타입 검사에서 실패**합니다. 혹시 실행 중에 문구가 없으면 한국어, 그다음 키 이름 순으로 대신 보여 줍니다.

### 8. 이펙트 없이 초기화되는 점진 렌더링

긴 목록은 60개씩 나눠 그리고, 끝에 둔 감시 요소가 화면 600px 앞에 오면 다음 묶음을 그립니다. 필터가 바뀌면 처음 개수로 돌아가야 하는데, 이를 `useEffect`로 처리하면 한 번 더 렌더링됩니다. 대신 **"어떤 필터 조합에서의 개수인지"를 함께 저장**하고, 렌더링 중에 필터가 달라졌으면 바로 처음 개수를 쓰게 했습니다.

### 9. 홈: 같은 카드 줄 대신 서로 다른 입구 세 개

첫 화면은 "빈 공간이 많다" → "카드 줄이 다 똑같다"는 피드백을 차례로 받았습니다. 종족값 TOP, 전설, 최신 세대… 를 가로 줄로 늘어놓는 구성은 결국 도감 목록의 축소판이었습니다. 그래서 도감에 들어오는 **방법이 서로 다른** 세 덩어리로 바꿨습니다.

- **실루엣 퀴즈.** 날짜로 정해지는 오늘의 문제(누구에게나 같은 포켓몬)를 검은 실루엣으로 보여 주고, 세 언어 이름 또는 초성으로 맞힙니다. 힌트는 타입·세대, 맞히면 그림이 드러나며 상세로 이어지고, 연속 정답 일수를 셉니다. 판정·문제 고르기·연속 기록은 순수 함수로 분리해 테스트했습니다.
- **찾아보기.** 검색, 자주 찾는 포켓몬, 타입·세대 칩. 칩을 누르면 그 필터가 걸린 도감으로 갑니다.
- **종족값 지도.** 전체 종을 SVG 산점도로 그립니다. 가로·세로 축은 6가지 능력치, 공격력(공격·특공 중 높은 값), 합계 중에서 자유롭게 고르고, 점 크기는 합계, 색은 타입입니다.

처음 만든 지도는 "이해 못 하는 사람이 있을 것 같다"는 피드백을 받았습니다. 그래서 그래프를 읽는 법을 화면에 직접 적었습니다.

- 축 고르기를 문장으로: "→ 오른쪽일수록 높은 [공격력] · ↑ 위쪽일수록 높은 [스피드]"
- 한 번에 두 축을 바꾸는 추천 비교: 빠른 공격수, 단단한 방어형, 체력과 방어, 강한데 빠른
- 그래프 네 귀퉁이에 뜻: "↗ 둘 다 높음", "↖ 스피드만 높음", "↙ 둘 다 낮음"
- 범례 한 줄: "점 1개 = 포켓몬 1마리 · 클수록 종족값 합계가 높음 · 색 = 타입"
- 브라우저 기본 말풍선 대신 그림·이름·타입·두 값이 담긴 정보 카드. 데스크톱은 올리면 카드·누르면 상세, 휴대폰은 탭하면 카드와 "상세 보기" 버튼

![종족값 지도: 드래곤 타입을 강조하고 점에 마우스를 올린 모습](/img/projects/pokestra/stat-map.webp)

타입을 고르면 그 타입만 남기고 흐려지고, 상위 3마리 이름표는 서로·강조 고리와 겹치지 않는 자리를 찾아 붙습니다. 그림을 viewBox로 줄이지 않고 칸 너비의 실제 픽셀로 그려, 휴대폰에서도 글자가 같은 크기로 읽힙니다.

### 10. 뒤로 가면 보던 자리로

긴 도감을 내리다 상세를 보고 돌아오면 맨 위로 튕기는 문제가 있었습니다. 새로 이동할 때(PUSH)는 맨 위로, 뒤로/앞으로(POP)는 경로별로 저장해 둔 위치로 돌아가되, 무한 스크롤 목록이 충분히 길어질 때까지 잠깐 기다렸다가 맞춥니다.

### 12. 한국어 데이터의 빈칸 찾아 메우기

한국어 화면 곳곳에 영어가 섞여 있었습니다. "한글 데이터가 없을 리 없다"는 말대로, 대부분은 데이터가 없는 게 아니라 **가져오는 과정에서 빠진 것**이었습니다.

| 빈칸 | 원인 | 해결 |
|---|---|---|
| 폼 이름 121개가 영어(Attack, Rock Star…) | 토큰 사전으로 폼 이름을 만들었는데 사전에 없는 폼 | PokeAPI `pokemon_form_names`의 공식 이름(어택폼, 붉은 달…)을 데이터로 만들고, 사전 라벨이 다 옮겨졌을 때만 짧은 사전 라벨("메가 X")을 쓴다. 공식 데이터에도 한국어가 없는 37개는 한국어판 표기로 직접 |
| 도구 설명 58개 | PokeAPI에 한국어가 있었는데 생성 스크립트가 놓침 | 다시 받아 채움 |
| 특성 설명 7개(포켓몬 챔피언스 신규) | PokeAPI의 챔피언스 데이터는 영어·일본어뿐 | 챔피언스 한국어판 문구로 |
| 기술 설명 23개(스타모빌·다크포켓몬 전용) | 어느 언어로도 설명이 없음 | 게임 문체로 직접 작성 |
| 도감 설명이 영어로 뜸 | 최신 작품에 영어 설명만 있으면 그게 기본값 | 사용자 언어 설명을 먼저 고르고, 영어는 목록에서 선택 |

다시 빠지지 않도록 **폼 이름(한·일)과 기술·특성·도구 설명 중 하나라도 한국어가 비면 실패하는 테스트**를 붙였습니다.

### 13. 포켓몬 위키에서 한국어 도감 설명 가져오기

PokeAPI의 한국어 도감 설명은 6세대(X·Y)부터만 있고, 메가진화·리전폼 같은 **모습별 설명은 영어뿐**이었습니다. 그래서 루카리오의 4·5세대 설명이나 메가루카리오의 설명은 영어로 나왔습니다. 한국어 [포켓몬 위키](https://pokemon.fandom.com/ko/)에는 1세대부터 모습별 설명까지 정리돼 있어서, 이를 한 번 모아 데이터로 만들었습니다.

- **가져오는 방법.** 위키의 일반 페이지는 봇 확인이 걸려 있어 우회하지 않고, MediaWiki 공개 API로 문서 원문(wikitext)만 읽었습니다. 1,025종 문서를 요청 사이에 쉬어 가며 한 번씩만 받고 캐시해 두어, 다시 만들 때는 위키에 요청하지 않습니다.
- **틀 두 가지.** 새 틀(`{{도감/세대}}`·`{{도감/설명N}}`·`{{도감/폼|메가루카리오}}`)과 옛 틀(`{{포켓몬도감설명|금 도감=…}}`)을 모두 읽습니다. 처음에는 새 틀만 읽어 절반 가까운 종이 빠졌고, 확인 과정에서 "등장하지 않음" 같은 자리 표시, `[[문서|글]]` 링크 안의 `|` 때문에 잘린 설명, 남은 HTML 태그를 찾아 하나씩 걸렀습니다.
- **모습 짝짓기.** 위키의 "메가리자몽X", "알로라의 모습", "오리지널캡 피카츄"를 공식 폼 이름과 키워드(메가·알로라·거다이맥스·오리진…)로 데이터의 모습에 맞춥니다. 짝이 없는 것은 대개 기본 모습(킬가르도 실드폼 등)이나 데이터에 없는 꾸밈 모습(사철록의 계절)이라 종의 설명으로 넣었습니다.
- **결과.** 1,023종, 설명 16,457개. 5세대까지의 649종 모두 4·5세대 한국어 설명이 생겼습니다. 종마다 작은 파일로 나눠 앱 번들은 커지지 않습니다.
- **출처 표시.** 위키에서 온 설명에는 "포켓몬 위키", 한국어판이 나오지 않은 작품(1~3세대, 크리스탈)의 설명에는 "한국어판 미발매 · 위키 번역"을 붙이고, 목록 아래에 출처와 라이선스(CC BY-SA 3.0)를 적었습니다.

화면도 위키처럼 바꿨습니다. "모두 보기"를 누르면 세대별로, 그 안에서 종의 설명 다음에 모습별 설명이 이어지고, 같은 글이 여러 세대에 실렸으면 세대마다 한 줄씩 나옵니다. 작품은 공식 로고 대신 작품 고유 색 배지(R·B·Sw·ZA…)로 표시합니다. 세대를 고르면 그 세대(없으면 리메이크 작품)의 설명이, 반대로 설명을 고르면 그 작품의 세대와 도트가 따라옵니다.

같은 날 데이터가 오래된 것도 발견했습니다. 데이터 스냅숏이 레전드 Z-A·메가 차원 러시 이전이라 **새 메가진화 49종**(메가픽시, 메가망나뇽, 메가루카리오Z, 메가라이츄X·Y…)이 없었습니다. 전체 데이터를 새로 만드는 원래 스크립트는 그동안의 한국어 보정을 덮어쓰기 때문에, **없는 id만 덧붙이는 스크립트**를 따로 만들었습니다.

### 14. 업데이트 소식: 무엇이 바뀌었는지 사용자에게 알리기

하루에도 화면과 데이터가 여러 번 바뀌는데, 사용자 입장에서는 무엇이 새로 생겼는지 알 방법이 없었습니다. 그래서 공지사항처럼 읽는 **업데이트 소식** 페이지(`/updates`)를 만들었습니다.

- **내용은 데이터 파일 하나.** 소식마다 날짜·종류(새 기능·개선·데이터·고침)·제목·요점·바로 가기 링크를 세 언어로 적고, 새 소식은 맨 위에 추가합니다.
- **새 소식 알림.** 헤더의 종 아이콘에 아직 보지 않은 소식이 있으면 작은 점이 붙습니다. 마지막으로 본 소식을 브라우저에 기억해 두고, 페이지에 들어오면 점이 꺼집니다.
- **읽기 쉽게.** 처음에는 소식마다 카드로 감쌌는데 "가독성 좋게"라는 피드백을 받고 타임라인으로 바꿨습니다. 데스크톱은 왼쪽에 날짜(스크롤해도 따라옴), 오른쪽에 소식이 이어지고, 카드 대신 구분선, 종류는 제목 위 작은 글자, 본문은 한 줄 길이를 줄이고 줄 간격을 넓혔습니다. 색 원칙(색은 타입 배지와 능력치 막대에만)도 그대로 지켜 종류 표시는 회색입니다.

## 배포

이 블로그 저장소가 Pokestra의 `main`을 받아 `/portfolio/pokestra/` 경로로 빌드해 함께 게시합니다. 빌드는 Pokestra 저장소만으로 끝납니다.

## 배운 점

- **데이터를 어디에 둘지가 곧 UX다.** 미리 만들 데이터와 그때 받을 데이터를 나누고 나니 검색과 필터 코드가 짧아지고 화면이 빨라졌다.
- **상태는 수명에 맞는 곳에.** 언어·필터·공유 링크는 각각 남아야 하는 기간이 달라서 저장 위치도 달라야 했다.
- **새 정보보다 모아 보여 주기가 차별점이 될 수 있다.** 세대 타임라인은 새 데이터 없이, 이미 받던 응답을 한 화면에 정리하는 것만으로 다른 도감과 구별되는 기능이 됐다.
- **설명서는 화면 안에.** 그래프 읽는 법, 버튼의 뜻을 따로 설명하지 않고 화면 문장과 귀퉁이 표시로 적어 두니 "이게 뭐예요?"가 사라졌다.
- **데이터를 가져올 때는 검증까지가 한 작업이다.** 위키 가져오기는 처음 돌렸을 때 절반이 비고 자리 표시가 설명으로 들어가 있었다. 결과를 세어 보고 이상한 값을 찾는 단계가 없었으면 그대로 배포됐을 것이다.
- **빈칸은 대개 없는 데이터가 아니라 빠뜨린 데이터다.** 영어가 섞인 자리를 하나씩 추적하니 원본에는 거의 다 있었다. 그리고 다시 빠지지 않게 테스트로 막았다.
- **색은 줄일수록 의미가 생긴다.** 배경까지 칠하던 타입 색을 배지와 막대에만 남기자 정보가 오히려 잘 읽혔다.
- **촘촘함은 간격을 줄이는 게 아니라 배치를 다시 짜는 일이다.** 시선과 손의 동선을 먼저 정하고 나서야 무엇을 줄일지 보였다.
- **어색한 기능은 다듬기보다 덜어 내는 게 답일 때가 있다.** 배틀과 계산기를 빼자 도감이 할 일이 분명해졌다.
- **사이드 프로젝트는 같은 걸 두 번 만들어 볼 수 있는 곳이다.** 처음 구조의 한계를 직접 겪어 봐야 다음 구조의 이유가 분명해진다.
