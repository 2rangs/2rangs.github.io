## 두 번 만든 프로젝트

**첫 번째(2026년 2~3월)** 는 평범한 도감이었습니다. 목록을 페이지 단위로 PokeAPI에서 받아 오고, 카드 하나마다 상세 정보를 다시 요청했습니다. 필터 하나를 바꿀 때마다 네트워크를 기다려야 했고, 1,000개가 넘는 포켓몬을 "배울 수 있는 기술"로 거르는 건 사실상 불가능했습니다.

**두 번째(2026년 11월)** 는 구조부터 다시 짰습니다.

- 목록·검색·필터에 필요한 데이터는 미리 만들어 함께 배포
- 직접 만든 엔진으로 배틀과 데미지 계산 추가
- 3개 언어 지원
- 디자인 시스템 위에서 UI 재구성

## 구조

### 데이터: 미리 만들 것과 그때 받을 것을 나누기

모든 데이터를 미리 만들 필요는 없었습니다. **자주, 빠르게 걸러야 하는 데이터만** 미리 만들고, 한 번 보고 마는 데이터는 그때 받기로 나눴습니다.

| 구분 | 데이터 | 방식 |
|---|---|---|
| 미리 만들어 함께 배포 | 목록·검색·필터용 포켓몬, 기술, 특성, 3개 언어 이름 | 스크립트가 PokeAPI를 20개씩 동시에 호출하고 CSV 덤프에서 영어·일본어 이름을 채워 JSON으로 저장(약 3.8MB) |
| 상세 화면에서 요청 | 도감 설명, 진화 단계 | TanStack Query로 요청하고 캐시 |

JSON을 불러올 때 이름·번호로 찾는 조회표를 한 번만 만들어 두고, 어느 화면에서든 같은 조회표를 씁니다. `mr-mime-galar` 같은 폼 이름에서 기본 종(`mr-mime`)을 찾을 때는 알려진 이름 중 가장 긴 앞부분부터 맞춰 봅니다.

### 상태: 성격에 따라 둘 곳을 다르게

| 상태 | 저장 위치 | 이유 |
|---|---|---|
| 언어 | localStorage (Zustand) | 다음에 와도 같은 언어로. 첫 방문은 브라우저 언어를 따름 |
| 배틀 팀, 난이도, 재생 속도 | localStorage (Zustand, 버전·마이그레이션 포함) | 공들여 짠 팀은 오래 남아야 함 |
| 도감 필터, 무한 스크롤 위치 | sessionStorage (Zustand) | 상세를 보고 돌아와도 보던 자리 그대로, 탭을 닫으면 초기화 |
| 기술·특성·스프라이트 필터, 계산기 대결 조합 | URL 쿼리 | 링크로 공유 가능. `?atk=garchomp&def=gholdengo` |
| 엔진 데이터, PokeAPI 응답 | TanStack Query | 한 번 받은 엔진 데이터는 모든 화면이 함께 씀 |

엔진은 크기가 커서 배틀·계산기 화면에 처음 들어갈 때만 내려받습니다. 내려받는 작업을 TanStack Query로 감싸 두어, 두 화면을 오가도 한 번만 받습니다.

## 핵심 구현

### 1. 엔진은 한 번에, 화면은 한 장면씩

엔진은 한 턴을 동기적으로 한 번에 끝냅니다. 그대로 그리면 HP가 순식간에 바뀌어 무슨 일이 있었는지 알 수 없습니다. 그래서 엔진이 이벤트를 낼 때마다 **그 순간의 양쪽 상태를 장면(frame)으로 찍어 두고**, 타이머로 한 장면씩 보여 줍니다.

```ts
const capture = (ev: BattleEvent) => {
  const st = e.getState()
  if (!st.sides.p1.active[0] || !st.sides.p2.active[0]) return
  const p1 = viewSide(st.sides.p1), p2 = viewSide(st.sides.p2)
  framesRef.current.push({
    index: framesRef.current.length, event: ev,
    silent: formatBattleEvent(ev, frameContext({ p1, p2 }), 'en') === null,
    turn: st.turn, p1, p2, weather: st.field.weather,
  })
}
e.on('*', capture)

// 재생: 말할 게 없는 장면은 기다리지 않고 넘어간다
const t = setTimeout(() => setRevealed((r) => r + 1), next.silent ? 0 : speed)
```

- **장면에는 문장이 아니라 이벤트를 저장합니다.** 문장은 그릴 때 현재 언어로 만들기 때문에, 배틀 도중 언어를 바꿔도 지난 로그까지 바뀐 언어로 다시 보입니다.
- **CPU는 모든 장면이 재생된 뒤에 행동합니다.** 사람이 아직 고르는 중이면 CPU는 사람의 선택을 보지 않고 바로 제출합니다.
- **CPU 시드를 고정해** 같은 조건이면 CPU끼리의 배틀이 똑같이 재현됩니다.

### 2. 하나의 검색창으로 세 언어, 영문 ID, 번호까지

사용자는 "피카츄", "pikachu", "ピカチュウ", "ぴかちゅう", "Mr. Mime", "mr-mime", "#25", "No.25" 등 무엇이든 입력합니다. 검색어와 이름을 같은 규칙으로 정규화해서 비교합니다.

```ts
function toKatakana(s: string) {
  return s.replace(/[ぁ-ゖ]/g, (c) => String.fromCharCode(c.charCodeAt(0) + 0x60))
}
export function norm(s: string) {
  return toKatakana(s.normalize('NFKC').toLowerCase()).replace(/[\s\-_.'’:・]+/g, '')
}
```

- 전각·반각을 맞추고(NFKC), 히라가나를 가타카나로 바꾸고, 공백·하이픈·점 같은 구분자를 지웁니다.
- 검색 색인은 처음 한 번만 만듭니다.
- 숫자를 입력하면 전국도감 번호로 찾기 때문에 같은 번호의 폼도 함께 나옵니다.
- 입력은 `useDeferredValue`로 처리해, 타이핑은 즉시 반응하고 목록 갱신은 그 뒤를 따라옵니다.
- 이름 정렬은 언어별 `Intl.Collator`를 하나씩만 만들어 재사용합니다.

### 3. 계산기를 열자마자 쓸 만한 기본값

포켓몬을 고르면 기술 4개를 자동으로 채워 줍니다. 그런데 무작위 세트에는 변화기(데미지가 없는 기술)가 섞여 있어 계산기에서는 쓸모가 없습니다.

```ts
const score = (m: MoveData) => (m.power ?? 0) * (stab.has(m.type) ? 1.5 : 1)
  * (m.accuracy ?? 100) / 100 * (RECHARGE_MOVES.has(m.name) ? 0.5 : 1)
const pool = damagingLearnset(p).sort((a, b) => score(b) - score(a))
const moves = set.moves.filter((m): m is string => !!m && isDamagingMove(m))
for (const m of pool) { if (moves.length >= 4) break; if (!moves.includes(m.name)) moves.push(m.name) }
```

- 변화기를 빼고, 남은 자리는 "위력 × 자속 보정 × 명중률, 반동으로 쉬어야 하는 기술은 절반" 점수가 높은 순서로 채웁니다.
- 무작위 세트의 시드를 도감 번호로 고정해, 같은 포켓몬은 언제 열어도 같은 기본값이 나옵니다.
- 노력치 입력은 0~252, 총합 510 안에 남은 만큼, 4의 배수로 맞춥니다.
- 결과는 확정 몇 타 / 난수 몇 타 / 불가로 정리하고, 언어마다 실제 게임 커뮤니티에서 쓰는 표현(확정 2타 / guaranteed 2HKO / 乱数1発)으로 보여 줍니다.

### 4. 세 언어의 배틀 로그

엔진은 한국어 로그만 만듭니다. Pokestra는 한국어는 엔진에 맡기고, **같은 이벤트를 받아 영어·일본어 문장을 만드는 포매터를 직접 작성**했습니다(약 660줄). 엔진에는 이름을 바꿔 주는 함수를 넘겨, 한국어 문장 안의 포켓몬 이름도 현재 언어를 따르게 했습니다. 영어 문장은 `[`나 `(`로 시작하는 경우까지 고려해 첫 글자를 대문자로 바꿉니다.

### 5. 빠진 번역은 컴파일 오류로

```ts
export function defineMessages<const K extends string>(m: {
  ko: Record<K, string>; en: NoInfer<Record<K, string>>; ja: NoInfer<Record<K, string>>
}): Messages<K> { return m }
```

키 목록은 한국어 문구에서만 정해지고, `NoInfer`가 영어·일본어 쪽에서 키가 늘어나지 않게 막습니다. 그래서 **영어나 일본어에 키가 하나라도 빠지면 타입 검사에서 실패**합니다. 혹시 실행 중에 문구가 없으면 한국어, 그다음 키 이름 순으로 대신 보여 줍니다.

### 6. 이펙트 없이 초기화되는 점진 렌더링

긴 목록은 60개씩 나눠 그리고, 끝에 둔 감시 요소가 화면 600px 앞에 오면 다음 묶음을 그립니다. 필터가 바뀌면 처음 개수로 돌아가야 하는데, 이를 `useEffect`로 처리하면 한 번 더 렌더링됩니다. 대신 **"어떤 필터 조합에서의 개수인지"를 함께 저장**하고, 렌더링 중에 필터가 달라졌으면 바로 처음 개수를 쓰게 했습니다.

## 고친 것들

| 문제 | 원인 | 해결 |
|---|---|---|
| 언어를 바꿔도 배틀 팀 이름이 한국어로 남음 | 예전에 저장한 팀에 자동 생성된 한국어 별명이 함께 저장되어 있었음 | 모든 언어와 폼 변화 전 이름으로 자동 별명을 판별해 저장 전에 지우고, 저장소 버전을 올려 이미 저장된 팀도 정리하는 마이그레이션 추가 |
| 필터를 바꿀 때마다 네트워크 대기 | 카드마다 PokeAPI를 호출 | 목록용 데이터를 미리 만들어 함께 배포(약 3.8MB를 내주고 검색·필터를 네트워크 없이 처리) |
| CI에서 설치 실패 | 직접 고정한 엔진 의존성 항목에 하위 의존성이 빠져 있었음 | 잠금 파일 항목을 다시 생성 |
| 팀을 불러오기 전 장면 기록 오류 | 첫 포켓몬이 나오기 전에는 그릴 것이 없는데 장면을 찍으려 했음 | 양쪽 포켓몬이 모두 나온 뒤부터 기록 |
| 16px 파비콘이 뭉개짐 | 작은 크기에서 세부가 많았음 | 단순한 SVG로 다시 그림 |

세 번째 타입을 고르면 가장 먼저 고른 타입이 빠지는 것(두 타입은 "모두 가진" 조건), 껍질몬은 HP가 항상 1이라 실능치 패널에서 따로 처리하는 것처럼, 데이터의 예외를 화면 규칙으로 정리하는 일도 많았습니다.

## 배포

이 블로그 저장소가 Pokestra의 `main`을 받아 `/portfolio/pokestra/` 경로로 빌드해 함께 게시합니다. 엔진은 GitHub 저장소에서 바로 설치하고, 설치할 때 엔진의 `prepare` 스크립트가 빌드를 마칩니다.

## 배운 점

- **데이터를 어디에 둘지가 곧 UX다.** 미리 만들 데이터와 그때 받을 데이터를 나누고 나니 검색과 필터 코드가 짧아지고 화면이 빨라졌다.
- **상태는 수명에 맞는 곳에.** 언어·팀·필터·공유 링크는 각각 남아야 하는 기간이 달라서 저장 위치도 달라야 했다.
- **한 번에 바뀌는 상태는 사용자가 따라가지 못한다.** 결과를 순서대로 보여 주는 것도 설계다.
- **사이드 프로젝트는 같은 걸 두 번 만들어 볼 수 있는 곳이다.** 처음 구조의 한계를 직접 겪어 봐야 다음 구조의 이유가 분명해진다.
