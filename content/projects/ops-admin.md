## 개요

차량에 단 AI 탐지 장비와, 그 장비에서 돌아가는 모델을 운영하는 관리자 시스템입니다. 고객사와 장비를 관리하고, 장비의 통신·운행 상태를 살피고, 모델별 탐지 정책을 바꾸고, 그 변경 이력을 되짚는 일을 한 체계 안에서 할 수 있게 만들었습니다. 화면 개발뿐 아니라 타입·테스트 기준과 배포 파이프라인까지 맡았습니다.

## 한 일

### AI 탐지 정책 관리

- 모델별 탐지 임계값과 정책 설정 화면
- 정책 데이터를 **추론 모델 목록을 기준으로** 구성하도록 개선
- 가드레일, 중앙분리대처럼 새로 추가된 탐지 대상과 모델 정책 대응
- 설정값 저장과 서버 응답 사이의 상태 동기화
- 정책 변경 시 기존 설정값을 다루는 처리 로직 개선

### 장비·차량 모니터링

- 장비별 통신 상태와 운행 정보 표시
- 고객사, 단말기, 날짜, 통신 상태를 조합하는 복합 필터
- 차량번호, 단말기 정보, 소속 업체, 상태 표시
- ROI 변경, 점검 상태 같은 운영 정보를 카드로 시각화
- 장비 상세 화면과 탐지 정보 연결
- 현지 시간과 한국 시간 함께 표시

### 탐지 결과와 ROI

- 이미지 위에서 ROI(관심 영역)를 보여 주고 설정하는 화면
- 탐지 객체의 좌표, 탐지 점수, 라벨을 파싱해 Bounding Box로 표시
- 여러 탐지 결과가 겹칠 때 표시 순서와 가시성 제어, Bounding Box 켜고 끄기
- 탐지 결과 상세 조회

### 운영 기능

- 장비 정보 관리와 CSV 일괄 등록
- 복합 조건 검색·필터링
- 정책·설정 변경 이력 조회
- **변경 전후 값을 비교해 바뀐 부분만 강조하는 Diff 하이라이트**

임계값이나 ROI를 바꾸면 장비가 찾아내는 결과 자체가 달라집니다. 그래서 바꾸는 화면만큼, 무엇이 언제 바뀌었는지 되짚는 화면이 중요했습니다.

## 품질: any 485개를 걷어내기

API 응답이 동적이라 코드 곳곳에 `any`가 있었고, 데이터 모양이 바뀌면 화면이 어디서 깨질지 알 수 없었습니다.

- 기존 `any` 485개 제거
- API 응답과 컴포넌트 데이터 구조의 타입 정의
- TypeScript 엄격 타입 검사 도입
- ESLint·Prettier 설정 정비
- Vitest 테스트 환경 구성
- 불명확했던 데이터 타입과 예외 처리 흐름 정리

## 배포 자동화

손으로 하던 배포는 단계를 빠뜨리기 쉽고, 문제가 생겼을 때 되돌릴 방법이 마땅치 않았습니다.

- GitHub Actions 기반 자동 배포 파이프라인
- 개발·운영 브랜치별 배포 환경 분리
- 배포 전 기존 버전을 백업하는 단계 추가로 실패 시 복구 경로 확보
- 운영 배포 이후 환경별로 생기는 문제 분석

## 직접 내린 결정

| 문제 | 선택 |
|---|---|
| 동적 API 데이터로 인한 타입 불안정 | 명시적 타입 정의와 `any` 제거 |
| 탐지 모델과 정책이 계속 늘어남 | 모델 목록을 중심으로 정책 구성 |
| 복잡한 운영 정보 조회 | 복합 필터와 상태 중심 UI |
| 수동 배포 부담 | GitHub Actions 자동화 |
| 배포 실패 시 복구 | 배포 전 백업 절차 |
| 설정 변경 원인 추적 | 변경 이력과 Diff 시각화 |

## 배운 점

- 정보 구조 설계가 UI의 절반이다.
- 타입은 나중에 붙일수록 비싸다. 동적인 API 데이터일수록 처음부터 모양을 정해 두어야 한다.
- 배포는 기능이다. 되돌릴 수 있어야 안심하고 내보낼 수 있다.
