## 개요

차량에 단 AI 탐지 장비와 그 장비에서 돌아가는 모델을 운영하는 관리자용 시스템입니다. 고객사와 장비 관리, 장비의 통신·운행 상태 확인, 모델별 탐지 정책 변경과 변경 이력 조회를 한 시스템에서 합니다. 화면 개발뿐 아니라 타입·테스트 기준과 배포 파이프라인까지 맡았고, 그 밖에 ESLint, Prettier, Docker, AWS를 썼습니다.

## AI 탐지 정책 관리

모델별 탐지 임계값과 정책을 설정하는 화면을 만들었습니다. 정책 데이터는 추론 모델 목록을 기준으로 구성하도록 바꿔서, 가드레일·중앙분리대처럼 탐지 대상과 모델이 늘어나도 목록에 모델만 추가되면 정책 화면이 따라옵니다. 설정값을 저장할 때 서버 응답과 화면 상태가 어긋나지 않게 맞췄고, 정책이 바뀔 때 기존 설정값을 다루는 처리도 고쳤습니다.

## 장비·차량 모니터링과 탐지 결과

장비별 통신 상태와 운행 정보, 차량번호, 단말기 정보, 소속 업체를 보여 주고, 고객사·단말기·날짜·통신 상태를 조합해 걸러 볼 수 있는 복합 필터를 만들었습니다. ROI 변경이나 점검 상태 같은 운영 정보는 카드로 보여 주고, 장비 상세 화면에서 탐지 정보로 이어지게 했습니다. 시간은 현지 시간과 한국 시간을 함께 표시합니다.

탐지 결과 화면에서는 이미지 위에 ROI(관심 영역)를 보여 주고 설정할 수 있게 했습니다. 탐지 객체의 좌표, 탐지 점수, 라벨을 파싱해 Bounding Box로 그리고, 여러 결과가 겹칠 때는 표시 순서와 가시성을 제어하고 Bounding Box를 켜고 끌 수 있게 했습니다.

## 운영 기능과 변경 이력

장비 정보는 화면에서 관리하거나 CSV로 일괄 등록할 수 있고, 복합 조건으로 검색할 수 있습니다. 정책과 설정의 변경 이력도 조회할 수 있는데, 변경 전후 값을 비교해 바뀐 부분만 강조하는 Diff 하이라이트를 넣었습니다.

임계값이나 ROI를 바꾸면 장비가 찾아내는 결과 자체가 달라지기 때문에, 무엇이 언제 바뀌었는지 되짚을 수 있어야 했습니다.

## any 485개 걷어내기

API 응답이 동적이라 코드 곳곳에 `any`가 있었고, 데이터 모양이 바뀌면 화면이 어디서 깨질지 알 수 없었습니다. API 응답과 컴포넌트 데이터 구조에 타입을 정의해 기존 `any` 485개를 제거하고, TypeScript 엄격 타입 검사를 켰습니다. 그러면서 불명확했던 데이터 타입과 예외 처리 흐름을 정리했고, ESLint·Prettier 설정을 정비하고 Vitest 테스트 환경을 구성했습니다.

## 배포 자동화

손으로 하던 배포는 단계를 빠뜨리기 쉽고, 문제가 생기면 되돌릴 방법이 마땅치 않았습니다. GitHub Actions로 자동 배포 파이프라인을 만들고, 개발·운영 브랜치별로 배포 환경을 나눴습니다. 배포 전에 기존 버전을 백업하는 단계를 넣어 실패하면 이전 버전으로 되돌릴 수 있게 했고, 운영 배포 이후 환경별로 생기는 문제를 분석해 대응했습니다.
