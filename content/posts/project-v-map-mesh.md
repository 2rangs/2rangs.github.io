구역 22개의 위치는 진짜였지만, 그 사이를 잇는 길의 길이는 직선이었고, 서로 보이는 구역 쌍 11개는 감으로 정한 것이었습니다.

마스터 프롬프트에 링크로 넣어 둔 구글 드라이브의 Blender 맵 11개를 받아서 실제 지형을 읽는 것입니다.
10.3절의 마지막 문장은 이렇습니다.

> 원본에 충돌 메시가 없다면 직접 생성해야 한다.

실제로 없었습니다.
이번 편은 맵 세션(PV-5)이 3억 2,600만 바이트짜리 `.blend` 파일에서 걸을 수 있는 바닥을 뽑아내고, 표준 도구가 실패한 자리를 직접 만든 격자로 메운 이야기입니다.

## 한눈에 보기

- 구글 드라이브의 "바이러스 검사 경고" 페이지 때문에 단순 다운로드가 실패했습니다. 헤드리스 브라우저로 사람이 누르는 버튼을 그대로 눌러서 받았습니다.
- Blender 4.2를 헤드리스로 돌려 장면을 분석했습니다. 오브젝트 9,931개, 정점 441만 개. 충돌 메시는 없었고 미술용 메시뿐이었습니다. 단위는 "미터"라고 적혀 있었지만 실제로는 언리얼 단위였습니다.
- 바닥·벽·경사 삼각형을 법선으로 분류해 뽑았고, 플레이 영역은 164 × 162 × 74m였습니다.
- Blender 좌표와 게임 좌표 사이의 변환을 기준점 5개로 맞췄습니다. 오차는 RMS 6.6m입니다. 두 좌표계는 서로 **거울상**이었습니다.
- 표준 NavMesh 도구(Recast)는 걸을 수 있는 영역의 약 27%만 하나로 이었습니다. 측정할 수 있었던 간선은 32개 중 2개였습니다.
- 직접 만든 2.5D 보행 격자는 95.2%를 이었고, 자동으로 찾은 다리 하나를 더해 **22개 구역을 전부** 연결했습니다. 실제 경로는 직선보다 평균 1.27배 길었습니다.
- 실제 벽으로 시야를 계산한 결과, 7편의 손으로 그린 시야선 11개 중 2개만 확실히 확인됐습니다. 다만 변환 오차 때문에 이 결과는 "차단을 과대평가"하는 쪽으로 치우쳐 있어서, 엔진에는 반영하지 않았습니다.

## 1. 받기

7편의 PV-4가 먼저 시도했습니다.
드라이브의 `uc?export=download` 주소로 요청하면 파일이 아니라 2,474바이트짜리 HTML이 돌아왔습니다.
큰 파일에 대해 드라이브가 띄우는 "바이러스 검사를 할 수 없습니다" 경고 페이지입니다.

PV-5는 헤드리스 Chromium(Playwright)으로 사람이 하는 순서를 그대로 밟았습니다.

```js
// tools/map-mesh/download/download-drive-map.cjs
    const downloadLabels = ['Download', '다운로드', 'Download anyway', '무시하고 다운로드'];
    const downloadPromise = page.waitForEvent('download', { timeout: 90000 });
    let clicked = await clickByText(page, downloadLabels);
    log('initial download control:', clicked || 'none found, waiting for interstitial');
    // Drive may navigate to the virus-scan warning page after the first click.
    await page.waitForTimeout(2500);
    const anyway = await clickByText(page, ['Download anyway', '무시하고 다운로드', 'Download']);

    const download = await downloadPromise;
```

1. 파일 보기 페이지를 엽니다.
2. "다운로드" 버튼을 누릅니다.
3. 2.5초 기다렸다가 경고 페이지의 "무시하고 다운로드"를 누릅니다.
4. 그래도 안 되면 경고 페이지에 있는 다운로드 폼을 직접 제출합니다.

문서는 이것이 "정상적인 버튼 흐름이며 어떤 보호도 우회하지 않았다"고 분명히 적어 둡니다.
공유된 파일을 사람이 누르는 것과 같은 버튼으로 받은 것입니다.

결과는 `Ascent (blender 4.2).blend`, 326,114,514바이트입니다.
SHA-256과 파일 헤더(`BLENDER-v402`)를 기록했습니다.
나머지 맵 10개는 페이지 제목만 읽어서 접근 가능 여부와 버전(모두 Blender 4.2)만 확인했고, 받지는 않았습니다.
DECISION-009(첫 맵은 Ascent 하나)를 따른 것입니다.

그리고 받은 파일은 커밋하지 않았습니다.
이 파일에는 Riot의 맵 아트가 들어 있고 재배포 라이선스를 확인할 수 없습니다.
그래서 원본 `.blend`, 거기서 뽑은 메시 바이너리, NavMesh 파일은 전부 gitignore이고, **스크립트와 숫자 통계만** 커밋했습니다.
2편의 원칙 "불명확하면 생성 스크립트만 커밋한다"입니다.

그런데 지오메트리가 ±8,500 범위에 걸쳐 있습니다.
발로란트 맵은 한 변이 대략 140m입니다.
그러니 Blender의 1단위는 1m가 아니라 언리얼의 1uu(1cm)입니다.

**부모 오브젝트.** 메시들이 빈 오브젝트 1,614개 아래에 자식으로 붙어 있었습니다.
언리얼의 인스턴스 메시를 내보낼 때 생기는 구조입니다.
`object.location`은 부모 기준 위치라서, 세계 좌표를 얻으려면 `matrix_world`를 써야 합니다.

**충돌 메시가 없다.** 컬렉션 이름이 `Ascent_Art_A`, `_AtkPathA`, `_Mid`처럼 구역별로 나뉘어 있을 뿐, 충돌용 컬렉션은 없었습니다.
전부 눈에 보이는 미술 메시입니다.
`Vista`로 시작하는 컬렉션 다섯 개는 맵 바깥 배경(병원, 섬, 종탑)이라 제외했습니다.

## 3. 바닥과 벽 뽑기

`extract-collision.py`는 플레이 영역 컬렉션 10개를 합치고, 모디파이어를 적용하고, 세계 좌표로 삼각형화한 뒤 삼각형마다 법선의 기울기로 분류합니다.

- **바닥**: 법선의 z 성분이 cos 45° 이상 (45°보다 완만한 면)
- **벽**: z 성분의 절댓값이 cos 70° 이하 (거의 수직인 면)
- **경사**: 그 사이

| 항목 | 값 |
| --- | --- |
| 오브젝트 | 6,736 |
| 정점 / 삼각형 | 3,135,792 / 2,355,371 |
| 바닥 / 벽 / 경사 | 410,858 / 1,111,794 / 832,719 |
| 플레이 영역 크기 | **164.0 × 161.7 × 73.6 m** |

플레이 영역이 160m 정도로 나온 것이 단위 해석이 맞았다는 확인입니다.
출력은 직접 정의한 단순한 바이너리 형식(`PVMESH01`: float32 좌표 + uint32 인덱스)입니다.

용도별로 몇 가지를 더 뽑았습니다.
바닥 높이 −6m~14m 구간만, 풀이나 소품 같은 이름은 정규식으로 빼고 뽑은 "지면 띠" 27만 9천 개, 시야 계산용 벽 삼각형 92만 7천 개입니다.

## 4. 두 좌표계 맞추기

이제 Blender 좌표의 바닥을 7편 그래프의 구역(게임 좌표)과 연결해야 합니다.
문제는 양쪽에 서로 대응하는 점이 거의 없다는 것입니다.
Blender 쪽에는 "A 사이트 컬렉션"은 있지만 "A 사이트 중심점"은 없습니다.

PV-5는 기준점 다섯 쌍을 만들었습니다.
공격 스폰, 수비 스폰, A 사이트, B 사이트, 미드.
Blender 쪽은 해당 영역 바닥의 면적 가중 무게중심과 이름 있는 랜드마크(`ABombsite*`, `BSite*`)의 중심, 게임 쪽은 PV-4의 구역 좌표입니다.
그리고 numpy 최소제곱으로 변환을 맞췄습니다.

| 변환 | 결과 | 오차(RMS / 최대) |
| --- | --- | --- |
| 아핀 | 행렬 `[[81.19, 32.09], [−0.34, −112.40]]` | **6.6m** / 9.1m |
| 닮음(회전+배율) | 배율 93.25uu/m, 회전 10.31°, **반사 있음** | 11.8m / 15.3m |

반사가 있다는 것이 흥미롭습니다.
Blender는 오른손 좌표계, 언리얼(그리고 valorant-api)은 왼손 좌표계입니다.
둘은 거울상 관계이고, 배율은 1m당 90~100uu 근처입니다.
닮음 변환이 이 관계를 확인해 줬고, 실제 작업에는 오차가 작은 아핀 변환을 씁니다.

6.6m는 작지 않은 오차입니다.
Ascent의 좁은 통로 폭보다 큽니다.
그래서 구역을 격자에 붙일 때는 반경 10m 안에서 가장 가까운 "걸을 수 있는 점"에 붙이도록 했습니다.

독립적인 확인도 하나 있습니다.
9편의 PV-6가 실제 리플레이 파일에서 뽑은 위치 샘플 3,001개(전부 수비 스폰)의 범위를 이 변환으로 역투영해 보니, 중심이 걸을 수 있는 바닥에서 2.9m, 수비 스폰 구역에서 6.8m 떨어진 곳에 떨어졌습니다.
판정은 통과입니다.
세 세션(PV-4의 valorant-api 좌표, PV-5의 Blender 변환, PV-6의 실제 리플레이)이 서로 다른 데이터로 같은 맵을 가리킨다는 확인입니다.

## 5. 실패: NavMesh 27%

게임 업계에서 길찾기 메시를 만드는 표준 도구는 Recast입니다.
PV-5는 recast-navigation-js 0.44.0(WASM)으로 NavMesh를 만들었습니다.
Blender의 Z-up을 Recast의 Y-up으로 바꾸고, 셀 크기 0.3m, 최대 경사 45°, 사람 키 2m, 오를 수 있는 높이 2m, 반경 0.3m로 설정했습니다.

결과물은 타일 7개, 폴리곤 66개, 정점 147개였습니다.
숫자부터 이상했습니다.
Ascent 전체가 폴리곤 66개라니요.

연결성을 쟀습니다.
랜덤한 점들 사이의 도달 가능성을 보고, 가장 큰 연결 덩어리가 전체의 몇 %인지 셌습니다.

| Recast 입력 | 가장 큰 덩어리 |
| --- | --- |
| 플레이 영역 메시 전체 | **약 7%** (벽 위, 소품 위, 난간에 조각이 흩어짐) |
| 바닥만 | 약 35% |
| 지면 띠 바닥 | **약 27~39%** (커밋한 버전) |

가장 큰 덩어리 근처 18m 안에 들어오는 구역이 미드의 3개뿐이었습니다.
그래서 측정할 수 있었던 간선은 **32개 중 2개**였습니다.

문서는 나머지 30개에 대해 이렇게 적었습니다.
"측정할 수 없음. 그 경로가 존재하지 않는다는 뜻이 아님."
실패한 측정을 "길이 없다"로 해석하지 않도록 못 박아 둔 것입니다.

원인 진단도 남아 있습니다.
Recast는 메시를 복셀로 쪼개서 걸을 수 있는 면을 찾는데, 미술용 메시는 그런 용도로 만들어지지 않았습니다.

- 여러 층으로 된 건물
- 계단이 경사면이 아니라 개별 단으로 모델링됨
- 문 폭이 침식(erosion) 크기보다 좁음
- 소품이 바닥을 잘게 쪼갬

해결책 후보로는 깨끗한 블록아웃 메시를 따로 만들기, 열두 군데쯤 되는 연결 지점에 수동으로 off-mesh 링크 넣기, 지면을 새로 재구성하기가 적혀 있습니다.
PV-5는 다른 길을 택했습니다.

## 6. 직접 만든 격자: 95%

아이디어는 단순합니다.
**미술 메시 전체가 아니라 바닥 삼각형만 보자. 그리고 층을 높이로 구분하자.**

`build_grid.py`(표준 라이브러리만 사용)는 이렇게 동작합니다.

1. 모든 높이의 바닥 삼각형을 XY 격자 칸(1.2m)에 래스터화합니다.
2. 한 칸 안의 바닥 높이들을 층으로 묶습니다(0.8m 이내면 같은 층).
3. 이웃한 8칸의 층끼리 높이 차가 3.0m 이하면 잇습니다.
4. 비용은 `수평 거리 + 높이 차 × 0.5`입니다.

```python
# tools/map-mesh/nav2d/build_grid.py
def build_adjacency(nodes_by_cell, cs, step_tol, vert_penalty=0.5):
    """nodes_by_cell: {(ix,iy): [(height, nodeId), ...]}.
    Returns adjacency {nodeId: [(nbrId, cost_m), ...]}.
    Link two nodes in neighbouring cells iff |dh| <= step_tol."""
    adj = {}
    for (ix, iy), layers in nodes_by_cell.items():
        for h, nid in layers:
            adj.setdefault(nid, [])
            for dx, dy, hc in _NEIGHBORS:
                nb = nodes_by_cell.get((ix + dx, iy + dy))
                if not nb:
                    continue
                for h2, nid2 in nb:
                    dh = abs(h - h2)
                    if dh <= step_tol:
                        cost = hc * cs + dh * vert_penalty
                        adj[nid].append((nid2, cost))
    return adj
```

계단은 "높이 차가 조금씩 나는 이웃 칸"이 되어 자연스럽게 이어집니다.
2층 바닥과 1층 바닥은 같은 칸 안의 다른 층이라 섞이지 않습니다.
문은 칸 해상도(1.2m)만 넘으면 살아남습니다.
전체 실행은 약 2초입니다.

| 지표 | Recast | 격자 |
| --- | --- | --- |
| 가장 큰 덩어리 | 약 27% | **95.2%** (노드 15,422개 중 14,686개) |
| 연결된 구역 | 3 / 22 | **21 / 22** |
| 측정 가능한 간선 | 2 / 32 | 30 / 32 |

### 마지막 한 구역

끝까지 떨어져 있던 구역은 B 사이트 옆 보트하우스(독 쪽 알코브)였습니다.
`offmesh_candidates.py`는 서로 다른 덩어리에 속한 노드 쌍 중 "수평으로 12m 이내, 수직으로 6m 이내"인 것을 찾습니다.

```python
# tools/map-mesh/nav2d/offmesh_candidates.py
def is_bridge_candidate(dxy, dz, radius, max_gap):
    """A node pair bridges components iff close horizontally and within a
    climbable/droppable vertical gap. Pure predicate for testing."""
    return dxy <= radius and dz <= max_gap
```

수평 3.79m, 수직 1.2m짜리 다리 하나가 자동으로 잡혔고, 이걸 넣자 **22개 구역이 전부 연결**되고 간선 32개가 전부 측정됐습니다.
수동으로 다리를 지정하는 파일(`offmesh-manual.json`)도 만들어 뒀지만 쓸 일은 없었습니다.

### 길은 직선보다 얼마나 긴가

간선 32개의 "격자 경로 길이 ÷ 직선거리"입니다.

| 통계 | 값 |
| --- | --- |
| 최소 | 1.08 |
| 중앙값 | **1.21** |
| 평균 | 1.27 |
| 최대 | **2.19** |

벽 때문에 크게 돌아가야 하는 구간이 눈에 띕니다.

- A 사이트 → A 와인: 2.19배 (직선 27.8m → 경로 60.8m)
- A 로비 → A 메인: 2.04배
- 미드 하단 → 마켓: 1.67배
- B 로비 → B 메인: 1.46배

반대로 트인 구간은 거의 직선입니다(A 사이트 → 래프터 1.09배, 미드 코트야드 → 캣워크 1.13배).

알려진 비용도 있습니다.
높이 차 허용값 3.0m는 꽤 커서, 일부 낙하나 점프 구간도 걸을 수 있는 길로 잡힙니다.
그만큼 이동 시간의 상한이 짧게 잡힐 수 있습니다.
내려갈 때만 큰 허용값을 주는 방향별 허용값이 다음 과제로 적혀 있습니다.

### 그래프에 반영

PV-5는 결과를 "교체 제안서"(`replacement-proposal.json`)로만 냈습니다.
간선 32개의 측정 거리, 이동 시간(초속 6.75m 기준), 우회 비율, 신뢰도(구역을 붙인 거리에 따라 중간 30개, 낮음 2개)가 들어 있고, 지오메트리는 없습니다.
1편의 규칙대로 PV-5는 PV-4의 파일을 직접 고치지 않았습니다.

PV-4가 14:37에 이 제안서에서 신뢰도 "중간"인 30개만 골라 반영했습니다.
간선 총길이는 952m에서 1,310m로 늘었습니다.
공격 스폰 → A 로비는 53.9m(8.0초)에서 63.1m(9.3초)가 됐습니다.

그리고 7편 끝에서 말한 대로, 라운드 시뮬레이터는 이 측정값을 **경로 선택**에만 쓰고 실제 이동 시간은 여전히 직선거리로 계산합니다.
측정은 들어갔는데, 시계는 그대로인 셈입니다.

## 7. 실제 벽으로 시야 재기

7편의 시야선 11개는 감으로 정한 것이었습니다.
벽 삼각형 92만 7천 개가 있으니 실제로 재 볼 수 있습니다.

`los.py`의 방법입니다.

1. 구역마다 격자 바닥 높이 + 1.6m(눈높이)에 점을 잡습니다.
2. 그 주변 반경 2.5m 안에 시드 고정 무작위 점 8개를 흩뿌립니다.
3. 두 구역의 점 쌍마다 선분을 긋고, 벽 삼각형과 교차하는지 봅니다.
4. 막히지 않은 선분의 비율이 "보일 확률"입니다.

벽 삼각형 92만 개를 전부 검사하면 느리니, 4m 격자로 삼각형을 미리 나눠 두고 선분이 지나가는 칸의 삼각형만 검사합니다.
교차 판정은 numpy로 묶어서 처리하는 Möller–Trumbore 알고리즘입니다.

```python
# tools/map-mesh/los/los.py
    def occluded(self, p, q):
        cand = self.candidates(p, q)
        if cand.size == 0:
            return False
        d = np.asarray(q, float) - np.asarray(p, float)
        t = moeller_trumbore_batch(p, d, self.v0[cand], self.v1[cand], self.v2[cand])
        return bool(np.isfinite(t).any())
```

결과는 231쌍 중 217쌍이 **완전히 막힘**, 완전히 보이는 쌍은 1개, 평균 보일 확률 0.028이었습니다.

7편의 시야선 11개와 비교하면 이렇습니다.

| PV-4 시야선 | 측정 |
| --- | --- |
| A 메인 ↔ A 사이트 | 0.61 |
| 미드 코트야드 ↔ 미드 하단 | 0.67 |
| A 래프터 ↔ A 사이트 | 0.17 |
| B 메인 ↔ B 사이트 | 0.17 |
| 나머지 7개 | 0 |

문서는 "11개 중 4개 확인"이라고 적었는데, 측정 파일은 0.17인 두 쌍을 "측정상 막힘"으로 표시합니다.
0보다 크면 확인으로 친 셈이라, 확실한 것은 2개입니다.

그런데 이 결과를 그대로 믿을 수는 없습니다.
문서가 스스로 그 이유를 적어 둡니다.
**눈 위치가 좌표 변환 오차(6~9m)를 그대로 물려받아서, 벽 근처나 벽 뒤에 떨어집니다.**
벽 뒤에서 보면 당연히 아무것도 안 보입니다.
그래서 이 측정은 차단을 과대평가하고, PV-4가 "직접 보인다"고 한 구역 쌍이 0으로 나온 것은 "반박"이 아니라 "배치 오류"로 해석해야 한다고 적었습니다.

결정은 반영하지 않는 것이었습니다.
시야선 교체 제안 11개는 전부 신뢰도 "낮음"이고, PV-4는 하나도 적용하지 않았습니다.
측정했지만 쓰지 않은 결과입니다.
3편의 LightGBM과 비슷하게, "더 정교해 보이는 숫자"가 기존 근사보다 낫다는 근거가 없으면 바꾸지 않았습니다.

## 남은 일

- **정렬 오차를 2m 이하로.** 지금은 6.6m입니다. 오브젝트 6,736개의 중심을 이미 뽑아 뒀으니, 이름 있는 오브젝트를 콜아웃과 짝지어 기준점을 늘리고, 아핀 대신 "반사 + 회전 + 배율" 변환으로 다시 맞출 계획입니다. 그다음에 격자, 시야, 간선을 다시 계산합니다.
- 점 단위 기준점을 늘리려면 실제 리플레이(`.vrf`)가 더 필요합니다. 이건 제가 커스텀 게임을 해서 넘겨야 하는 부분입니다.
- 엔진이 바로 쓸 수 있는 가벼운 행렬(구역 쌍 보일 확률, 구역 간 이동 시간)을 그래프 형식으로 내보내기.
- 두 번째 맵은 Lotus입니다. 다운로드와 장면 분석까지만 준비되어 있습니다.

## 정리

이번 편의 교훈은 두 가지입니다.

하나는 **표준 도구가 실패하면 문제를 다시 정의하라**는 것입니다.
Recast는 "이 입체 덩어리 위 어디를 걸을 수 있나"를 풀려고 했고, 미술 메시 앞에서 무너졌습니다.
격자는 "바닥 면들이 높이로 어떻게 이어지나"라는 더 작은 문제를 풀었고, 95%를 이었습니다.
표준 라이브러리만 쓰는 수백 줄짜리 스크립트가 WASM NavMesh 라이브러리를 이겼습니다.

다른 하나는 **측정의 한계를 측정 결과와 같이 넘기라**는 것입니다.
"측정 불가 ≠ 길이 없음", "시야 0 ≠ 안 보임, 배치 오류일 수 있음".
PV-5의 문서에는 이런 단서가 결과마다 붙어 있었고, 덕분에 PV-4는 간선 측정은 받아들이고 시야 측정은 거절하는 판단을 할 수 있었습니다.

다음 편은 실제 경기 데이터 쪽의 마지막 퍼즐, 리플레이 파일과 그 위에 올린 데스크톱 앱입니다.
