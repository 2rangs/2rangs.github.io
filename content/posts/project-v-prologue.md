> **참고** 이 글은 "PROJECT V 개발기" 연재의 1편입니다. [Project-VM 저장소](https://github.com/2rangs/Project-VM)의 커밋 기록과 문서, 코드를 근거로 썼습니다. 글에 나오는 수치는 모두 저장소에 남은 기록이거나 제가 직접 다시 돌려 본 결과입니다.

발로란트 프로 경기를 보다 보면 이런 생각이 듭니다.
"저 상황에서 B로 돌았으면 어땠을까?"
"에코 라운드에 저 선수가 오퍼레이터를 살렸으면 다음 라운드는 이겼을까?"

축구에는 Football Manager가 있고, 야구에는 Out of the Park Baseball이 있습니다.
실제 스포츠를 숫자와 규칙으로 옮겨 놓고, 감독이 되어 그 안에서 경기를 굴려 볼 수 있는 게임입니다.
발로란트에는 그런 게임이 없습니다.

PROJECT V는 그 빈자리를 노린 프로젝트입니다.
발로란트 5v5 경기를 독립적인 시뮬레이션 엔진으로 다시 만들고, 그 위에 매니저 게임을 얹는 것이 최종 목표입니다.

이 연재는 그 엔진의 첫 초안을 만든 기록입니다.
조금 특이한 점이 있습니다.
코드의 대부분을 AI 에이전트가 썼고, 그것도 여섯 개 세션이 동시에 썼습니다.
첫 AI 커밋에서 시뮬레이션 가능한 초안이 main에 들어가기까지 걸린 시간은 6시간 16분이었고, 그중 4시간 8분은 사용량 제한으로 모든 세션이 멈춰 있던 시간이었습니다.

## 한눈에 보기

- PROJECT V는 발로란트 e스포츠 경기를 "결과를 먼저 정하지 않고" 실제로 진행시켜 보는 전술 시뮬레이션 엔진입니다. 첫 맵은 Ascent 하나입니다.
- 제가 직접 쓴 것은 2,840줄짜리 마스터 프롬프트(`README.md`)와 1,961줄짜리 인수인계 문서(`Handoff.md`) 두 개입니다. 코드는 오케스트레이터 세션 1개가 일을 나누고, 하위 세션 6개(PV-1 ~ PV-6)가 각자 브랜치에서 썼습니다.
- 2026년 11월 18일 08:49(UTC)에 첫 AI 커밋이 올라왔고, 15:05에 시뮬레이션 초안이 main에 머지됐습니다. 여섯 브랜치를 합칠 때 충돌은 0건이었습니다.
- 지금 저장소에는 TypeScript 패키지 19개, 도구 8개, 앱 2개(PixiJS 리플레이 뷰어, Electron 데스크톱 앱)가 있습니다. 커밋은 169개입니다.
- `pnpm sim:match` 한 줄로 실제 VCT 팀 로스터끼리 Ascent 한 경기를 약 2초 만에 끝까지 돌릴 수 있습니다.
- 초안은 처음엔 엉망이었습니다. 라운드의 87%가 시간 초과로 끝났습니다. 이를 실제 VCT 통계에 맞춰 가는 과정이 이 연재의 후반부입니다.

## 왜 "결과를 먼저 정하지 않는다"가 첫 원칙인가

스포츠 게임의 경기 엔진을 만드는 가장 쉬운 방법은 이렇습니다.

```text
Team A OVR = 85
Team B OVR = 80

Calculate Match Winner
        ↓
Generate Fake Replay
```

능력치로 승자를 먼저 뽑고, 그럴듯한 하이라이트를 나중에 지어 붙이는 방식입니다.
빠르고 단순하지만, 이 방식에서는 감독의 지시가 의미를 잃습니다.
"B 사이트로 페이크를 주고 A로 돌아라"라는 지시가 결과에 영향을 주려면, 결과가 지시보다 먼저 정해져 있으면 안 됩니다.

그래서 인수인계 문서의 두 번째 결정(DECISION-002)은 이 방식을 명시적으로 거부합니다.

```text
Team A / Team B Initial State
        ↓
Generate Tactical Decisions
        ↓
Execute Movement / Abilities / Combat
        ↓
Resolve Events
        ↓
Determine Round Result
```

선수 열 명이 각자 보이는 것만 보고 판단하고, 움직이고, 스킬을 쓰고, 총을 쏩니다.
그 사건들이 쌓여서 라운드 결과가 나옵니다.
승패는 출력이지 입력이 아닙니다.

이 원칙 하나가 나머지 설계를 거의 다 끌고 갑니다.
결과를 정하지 않으려면 맵이 있어야 하고(공간 엔진), 선수가 무엇을 볼 수 있는지 알아야 하고(지각 엔진), 볼 수 없는 것은 추측해야 하고(Belief State), 그 상황에서 할 수 있는 행동을 만들어 내야 하고(Action Generator), 총싸움을 판정해야 합니다(교전 엔진).

### 마스터 프롬프트: 무엇을 만들지

`README.md`는 제목부터 "통합 개발 마스터 프롬프트"입니다.
AI에게 역할을 주는 것으로 시작합니다.
게임 엔진 아키텍트, 시뮬레이션 엔지니어, 게임 AI 엔지니어, 발로란트 전술 분석가, e스포츠 데이터 과학자, ETL 엔지니어, 머신러닝 연구자, 컴퓨터 비전 엔지니어, 공간·내비게이션 엔지니어, Electron 엔지니어, QA, 기술 리서처까지 열두 개입니다.

그리고 바로 이 문장이 나옵니다.

> 문서만 작성하고 개발이 완료되었다고 보고하지 마라.

이 프롬프트에서 가장 신경 쓴 부분은 사실 기능 목록이 아니라 데이터 규칙입니다.
3장 전체가 "모든 데이터 소스를 실제로 검증한다"는 규칙입니다.
조사한 자료를 "확보함", "접근 가능하지만 미검증", "접근 불가" 같은 상태로 나누고, 출처와 라이선스를 기록하게 했습니다.
사용자가 주지 않은 API 키나 비공개 권한을 가진 것처럼 가정하지 말라는 문장도 넣었습니다.

이유는 단순합니다.
AI에게 "VCT 데이터로 선수 능력치를 만들어"라고 하면, 데이터가 없어도 그럴듯한 능력치 표를 만들어 옵니다.
그 표가 진짜인지 확인하는 비용은 결국 제가 냅니다.
그래서 처음부터 "없으면 없다고 적어라"를 규칙으로 박아 두었습니다.
2편에서 보겠지만 이 규칙은 실제로 여러 번 작동했습니다.

### 인수인계 문서: 이미 정한 것

`Handoff.md`는 이 프로젝트를 이어받을 AI가 이전 대화를 읽지 않고도 일을 시작할 수 있게 쓴 문서입니다.
핵심은 3장의 설계 결정 열한 개입니다.

| 번호 | 결정 | 한 줄 요약 |
| --- | --- | --- |
| 001 | 매니지먼트보다 경기 엔진 우선 | 구단 경영 UI는 맨 마지막 |
| 002 | 결과 선결정 방식 거부 | 승패는 사건의 결과 |
| 003 | 상황 기반 선택지 생성 우선 | 평가보다 후보 생성이 먼저 |
| 004 | 실제 상태와 인지 상태 분리 | AI는 못 보는 적의 위치를 모른다 |
| 005 | AI 학습은 선택적 고도화 | 초기 엔진은 ML 없이 돌아야 한다. LLM이 실시간으로 10명을 조종하지 않는다 |
| 006 | GPU 의존 최소화 | 경기 연산과 렌더링 분리 |
| 007 | Electron 기반 PC 게임 | React, TypeScript, PixiJS |
| 008 | 시뮬레이션 코어 | TypeScript로 시작, 필요하면 Rust로 |
| 009 | 최초 구현 맵은 Ascent | 3레인, 미드 컨트롤, 전술 테스트에 적합 |
| 010 | Deterministic Simulation | 같은 초기 상태와 시드면 같은 경기 |
| 011 | 세이브와 궁극기는 주요 전략 요소 | 지는 라운드의 행동도 의사결정 |

4장도 중요합니다.
"개발이 완료된 것으로 오해하면 안 되는 사항"이라는 표입니다.
저장소 생성, VCT 데이터 다운로드, 리플레이 디코딩, NavMesh 생성, World State 구현 같은 항목이 전부 "미확인" 또는 "미구현"으로 적혀 있습니다.
이전 대화에서 조사하고 설계한 것과 실제로 만든 것을 구분하라는 표시입니다.

## 일곱 개의 세션

문서 두 개를 올린 뒤에는 오케스트레이터 역할의 세션 하나에 일을 맡겼습니다.
오케스트레이터는 두 문서를 읽고 일을 여섯 갈래로 나눴습니다.

| 세션 | 담당 | 브랜치 |
| --- | --- | --- |
| PV-1 Research | 데이터 소스 레지스트리와 라이선스, 게임 데이터 카탈로그, 전술 지식 베이스, 감사 | `claude/pv-research` |
| PV-2 Data | 데이터 스키마와 ETL, 실측 통계, 경제 엔진, 검증 도구, 선수·팀 프로필 | `claude/pv-data` |
| PV-3 Core | 모노레포, World State와 규칙, 의사결정·행동·팀 엔진, 통합 준비 | `claude/pv-core` |
| PV-4 Spatial | 공간·지각·교전·스킬 엔진, 라운드 시뮬레이터 | `claude/pv-spatial` |
| PV-5 MapMesh | Ascent Blender 맵 처리, NavMesh, 실측 시야 | `claude/pv-mapmesh` |
| PV-6 Replay | `.vrf` 리플레이 파서, 리플레이 포맷과 뷰어, 데스크톱 앱 UI | `claude/pv-replay` |

운영 규칙은 `docs/WORK_HISTORY.md`에 그대로 남아 있습니다.

- 각 세션은 **자기 소유 경로만 수정**하고, 자기 브랜치에만 커밋하고 push한다.
- 다른 브랜치는 fetch해서 읽기만 한다.
- 브랜치 사이의 의존성은 머지로 풀지 않고 **인터페이스와 구조적 미러**로 푼다. 실제 연결은 마지막 통합 때 한다.
- 머지는 모든 작업이 끝난 뒤 맨 마지막에 오케스트레이터가 한다.
- 일이 끝난 세션에는 바로 다음 일을 준다.

이 규칙이 없었다면 여섯 세션이 같은 `package.json`을 동시에 고치면서 충돌 지옥이 열렸을 것입니다.
대신 PV-3가 "공간 질의는 이런 인터페이스로 받겠다"고 타입을 먼저 정해 두고, PV-4가 그 타입에 맞춰 구현하는 식으로 일이 흘렀습니다.
이 방식이 정말 충돌 0건으로 끝났는지, 그 대가로 무엇을 치렀는지는 10편에서 자세히 씁니다.

```text
│   └── desktop            Electron 매니저 게임 UI
├── datasets/          # 스키마, 정규화 데이터, 파생 통계, 공간 데이터
└── docs/              # 설계, 감사, 인수인계, 연구 기록
```

패키지 의존 관계를 단순하게 그리면 이렇습니다.

```text
                 shared-types (모든 타입)
                       │
     ┌─────────────────┼──────────────────┐
     │                 │                  │
 [PV-3 판단]        [PV-4 공간]        [PV-2 경제]
 world-state        spatial-engine     economy-engine
 decision-engine    perception-engine
 action-generator   combat-engine
 team-engine  ◀───  ability-engine
 outcome-predictor  round-simulator
     │                 │
     └──── match-runner ────┘
                 │
     [PV-6] replay-engine → replay-viewer / desktop
```

라운드 시뮬레이터(PV-4)는 매 순간 선수들에게 "지금 보이는 것"만 건네고, 무엇을 할지는 팀 엔진(PV-3)의 `DecisionPolicy`에게 묻습니다.
시뮬레이터가 실제 세계를 쥐고 있고, AI는 관측만 봅니다.
DECISION-004가 코드 경계로 굳은 모습입니다.

## 직접 한 경기 돌려 보기

글을 쓰면서 저장소를 새로 받아 한 경기를 돌려 봤습니다.

```bash
pnpm install --frozen-lockfile
```

```bash
pnpm sim:match --teamA 1001 --teamB 1034 --map ascent --seed 42
```

팀 번호 1001은 Team Heretics, 1034는 NRG입니다.
`@pv/game-data`에 들어 있는 실제 VCT 팀 로스터입니다.

```text
=== MATCH: Team Heretics (A) vs NRG (B) — map ascent, seed 42 ===

R 1 PISTOL atk=Team Heretics win=NRG        [elimination] kills A:1 B:5 buy A:Classic(pistol) B:Classic(pistol) $A:2900 $B:4800 score 0-1
R 2        atk=Team Heretics win=NRG        [elimination] kills A:1 B:5 buy A:Spectre(force) B:Vandal(full) $A:3500 $B:4900 score 0-2
R 3        atk=Team Heretics win=NRG        [spikeDefused planted] kills A:3 B:5 buy A:Spectre(force) B:Vandal(full) $A:5300 $B:5000 score 0-3
R 4        atk=Team Heretics win=Team Heretics [elimination planted] kills A:5 B:3 buy A:Vandal(full) B:Vandal(full) $A:5700 $B:3600 score 1-3
...
R 8        atk=Team Heretics win=Team Heretics [spikeDetonation planted] kills A:4 B:3 buy A:Vandal(full) B:Spectre(force) $A:7100 $B:4500 score 5-3
...
R13 PISTOL atk=NRG        win=Team Heretics [elimination] kills A:5 B:1 buy A:Classic(pistol) B:Classic(pistol) $A:4800 $B:2900 score 8-5
...
R23        atk=NRG        win=NRG        [elimination planted] kills A:4 B:5 buy A:Spectre(force) B:Vandal(full) $A:4600 $B:5800 score 10-13

FINAL: Team Heretics 10 — 13 NRG  →  NRG wins
```

23라운드를 도는 데 약 2초가 걸렸습니다.
한 줄이 한 라운드입니다.
누가 공격이었는지, 어떻게 끝났는지(전멸, 해체, 폭발), 스파이크가 설치됐는지, 양 팀이 무엇을 샀는지(피스톨, 포스 바이, 풀 바이), 라운드가 끝난 뒤 돈이 얼마 남았는지가 찍힙니다.

몇 가지가 눈에 띕니다.

- 1라운드 피스톨을 진 Team Heretics는 2, 3라운드에 Spectre로 포스 바이를 했고, 둘 다 졌습니다. 4라운드에야 풀 바이가 됩니다. 패배 보너스가 누적되는 경제 규칙이 실제로 돌고 있다는 뜻입니다.
- 13라운드에 공수가 바뀌고 다시 피스톨 라운드가 옵니다.
- 8라운드는 스파이크 폭발로 끝났습니다. 이 한 줄이 나오기까지의 사연은 11편에 씁니다. 한동안 이 시뮬레이터에서 스파이크는 절대 터지지 않았습니다.

재미있는 점이 하나 더 있습니다.
`docs/WORK_HISTORY.md`에는 첫 main 머지 때 같은 명령, 같은 시드로 돌린 결과가 남아 있습니다.
그때는 **Team Heretics가 13–11로 이겼습니다.**
지금은 NRG가 13–10으로 이깁니다.

시드가 같으면 결과가 같아야 한다는 DECISION-010을 어긴 걸까요?
아닙니다.
같은 코드, 같은 시드면 몇 번을 돌려도 같은 결과가 나옵니다.
그 사이에 바뀐 것은 코드입니다.
수비수가 앵커 자리를 지키게 되고, 스파이크 소지자가 설치를 끝까지 마치게 되고, 가망 없는 리테이크를 포기하게 되면서 같은 난수열 위에서 다른 경기가 펼쳐진 것입니다.
결정론이 있기 때문에 이 차이를 "코드가 바뀐 탓"이라고 확신할 수 있습니다.

명령을 실행하면 `match-out/` 폴더에 `summary.txt`, `events.json`, `replay.json`, `trace.json`이 생깁니다.
이벤트 로그와 리플레이, 그리고 AI가 왜 그 행동을 골랐는지 남긴 의사결정 추적입니다.

## 초안은 얼마나 엉망이었나

첫 main 머지 때 남긴 "알려진 한계"는 솔직합니다.

> 시간 초과 라운드 과다: 예시 경기 24라운드 중 19라운드가 timeExpired(실측 약 3%).

라운드 대부분이 아무도 스파이크를 설치하지 못한 채 시간이 다 돼서 끝났다는 뜻입니다.
두 번째 머지 뒤에 세 시드로 53라운드를 돌렸을 때도 46라운드(약 87%)가 시간 초과였습니다.

원인은 의외로 단순했습니다.
팀 엔진이 500ms마다 명령을 다시 뽑고 있었습니다.
스파이크 설치에는 4초, 해체에는 7초가 걸리는데, 0.5초마다 "이번엔 뭘 할까"를 새로 고르니 설치가 매번 중간에 끊긴 것입니다.
이걸 고치자 시간 초과는 20경기 배치 기준으로 61.8%에서 0%가 됐습니다(87%는 세 경기로 잰 값이고, 61.8%는 20경기로 잰 값입니다).
그러자 이번엔 공격 승률이 61.7%로 치솟았습니다. 실제 VCT는 50.9%입니다.

이런 식의 숨바꼭질이 여덟 번의 main 머지 동안 이어졌습니다.
저장소에는 이 과정을 재는 도구(`sim:batch`)가 있어서, 20경기를 돌리고 실제 VCT 통계와 나란히 비교합니다.

| 지표 | 처음 | 8차 머지 후 | 실제 VCT |
| --- | --- | --- | --- |
| 시간 초과로 끝난 라운드 | 61.8% | 4.6% | 4.3% |
| 스파이크 폭발로 끝난 라운드 | 0.4% | 9.0% | 8.2% |
| 공격 승률 | 19.7% | 61.7% | 50.9% |
| 판정 지표 통과 | 0 / 9 | 4 / 8 | — |

아직 절반만 맞습니다.
공격이 너무 강합니다.
이 표가 어떻게 만들어졌고, 각 숫자를 움직이려고 무엇을 고쳤는지가 11편의 내용입니다.

## 연재 순서

이 연재는 세션별 작업을 따라가다가, 통합과 보정, 회고로 끝납니다.
아래는 계획이고, 쓰면서 조금 바뀔 수 있습니다.

1. **프롤로그** — 이 글
2. **데이터 찾기** — 쓸 수 있는 데이터와 쓰면 안 되는 데이터. vlr.gg 약관, Riot API 403, GRID (PV-1)
3. **데이터를 숫자로** — 스키마, 실측 기준선, 쓰지 않기로 한 LightGBM 모델, 불확실성을 숨기지 않는 선수 능력치 (PV-2)
4. **경제와 궁극기 엔진** — 세이브는 지는 라운드의 행동이 아니라 다음 라운드를 위한 투자 (PV-2)
5. **상황 기반 선택지 생성** — World State, Belief State, Action Generator (PV-3)
6. **팀 엔진과 한 경기** — IGL, 선수 정책, 미래 탐색, 매치 러너, 전술 타임아웃 (PV-3)
7. **공간, 지각, 교전** — Ascent 구역 그래프, 시야와 소리, 결정적 총싸움, 스킬 (PV-4)
8. **맵을 직접 읽다** — Blender 맵에서 충돌 메시를 뽑고, NavMesh가 27%만 이어진 이유 (PV-5)
9. **리플레이와 데스크톱 앱** — `.vrf` 파싱, 안개 뷰, 한국어 UI (PV-6)
10. **충돌 0건 통합** — 여섯 세션이 서로를 기다리지 않고 일한 방법
11. **현실에 맞추기** — 시간 초과 87%에서 판정 4/8까지
12. **회고** — AI 여섯에게 게임 엔진을 맡겨 보고 배운 것

## 이 연재를 읽는 방법

각 편은 독립적으로 읽어도 되게 썼습니다.
게임 AI에 관심이 있다면 5, 6, 11편을, 데이터 쪽이라면 2, 3, 4편을, 여러 AI 에이전트로 큰 프로젝트를 굴리는 방법이 궁금하다면 10, 12편을 먼저 읽으셔도 됩니다.

한 가지만 미리 말씀드립니다.
이 프로젝트는 출시된 게임이 아니라 내부 개발 단계의 엔진 초안입니다.
실제 프로 선수와 팀 이름을 쓰고 있고, 출시 전에는 초상권과 상표, Riot 자산 라이선스를 다시 검토해야 한다는 것이 저장소에 기록된 결정입니다.
이 엔진이 내놓는 경기 결과는 실제 팀의 실력을 예측한 것이 아닙니다.

다음 편에서는 엔진의 재료, 데이터 이야기부터 시작합니다.
"VCT 경기 데이터를 모아 와"라는 한 문장이 실제로는 얼마나 많은 "안 됩니다"로 돌아왔는지에 대한 이야기입니다.
