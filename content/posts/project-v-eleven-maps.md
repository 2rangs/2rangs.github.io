시리즈와 밴픽을 만들었을 때 모든 경기는 Ascent에서 치러졌다. Lotus를 픽해도 Lotus의 숙련도로 Ascent에서 싸웠고, `series.ts`에는 `SIMULATED_GEOMETRY = "Ascent"` 상수가 남았다. 공간 데이터가 Ascent 하나뿐이었기 때문이다. 이 글은 나머지 열 개 맵에 데이터를 채우고, 각 맵을 자기 지형에서 돌려 본 이야기다. 15차 머지에서 시야 표와 `geometry: "own"` 옵션이 들어갔고, 19차 머지에서 끊긴 구역이 모두 이어지고 맵별 전술이 들어갔다. 그래도 기본값은 Ascent로 남았다.

## 열 개 맵의 구역 그래프

출발점은 11월 19일의 `claude/maps-data-df31bb` 브랜치다. 13차 머지 때 함께 들어갔다. 구역은 valorant-api의 콜아웃에서 하나씩 만들었고, 원본 응답은 Ascent 때처럼 맵별로 그대로 커밋했다. 지형은 8편에서 Ascent에 썼던 방식을 열 개 맵에 똑같이 돌렸다. Blender 장면에서 삼각형을 뽑고, 0.5m 셀의 2.5D 보행 격자를 만들고, 셀이 닿는 두 구역 사이에 간선을 둔다. `.blend`와 뽑은 메시는 여전히 저장소 밖이고, 커밋된 건 개수, 거리, 시야 비율, 그래프만 그린 PNG다.

좌표 변환은 Ascent 때보다 단순해졌다. 열한 개 장면 모두 `game_uu = 100 · (x, −y, z)`, 즉 같은 배율에 Y축만 뒤집힌 평범한 내보내기였다. 예전에 Ascent에서 얻었던 RMS 6.6m짜리 아핀 변환은 거친 영역 중심점에 맞춘 데서 생긴 오차였다고 문서는 정리했다. 콜아웃의 z가 실제 바닥 높이인 여섯 맵(Ascent, Bind, Fracture, Haven, Icebox, Split)에서는 후보 24개 중 고른 변환이 콜아웃 중간값 높이를 0.01m 안에서 재현했다. 나머지 다섯 맵은 콜아웃 z가 라벨용 높이라(Sunset은 전부 −200) 영역 단위로만 확인했다.

이 브랜치에서 가장 쓸모 있었던 건 대조 실험이었다. 같은 파이프라인을 Ascent에도 돌려서 손으로 만든 그래프와 비교했다. 손으로 넣은 시야선 11개 중 8개는 실제로 보였지만 세 개(`a-window↔a-site`, `mid-link↔b-site`, `b-boathouse↔b-site`)는 0.00이 나왔다. 그리고 같은 규칙이면 Ascent의 시야선은 약 38개가 된다. 시뮬레이션의 균형을 맞춘 Ascent보다 새 맵들의 시야선이 세 배쯤 촘촘하다는 뜻이다. 소리 연결도 비슷했다. Ascent의 소리 연결 6개와 감쇠값은 손으로 정한 것이었는데, 거리 기준 규칙(25m 이하 0.2, 50m 이하 0.3, 그 이상 0.4)을 역으로 맞춰 여섯 개를 모두 재현한 뒤 새 맵에 적용했다. 그러자 새 맵의 소리 연결은 24~39개가 됐다. 문서는 이 두 차이를 "새 맵의 밸런스 숫자를 믿기 전에 확인할 것" 목록에 올려 두었다.

보행 격자가 잇지 못한 구역도 있었다. 233개 중 9개가 주 보행면 밖에 있었고, 한쪽 방향으로만 닿는 구역이 3개 더 있었다. 이런 곳에는 `approx-link`라는 꼬리표를 단 직선 연결을 넣었다. 처음 12개에서 경로 측정 단계를 거쳐 10개가 됐다. Haven B Site는 이 근사 연결 하나로만 들어갈 수 있었고, Pearl은 26개 구역 중 4개가 떨어져 있어서 "가장 약한 맵"으로 적혔다. 엔진 쪽에서 Ascent를 가정한 곳도 27군데를 파일과 줄 번호까지 표로 남겼다. 수비 시작 위치에 `mid-courtyard`가 박혀 있다거나, 사이트가 A와 B뿐이라 Haven과 Lotus의 C가 어디에도 속하지 않는다거나, Bind, Fracture, Lotus에는 `mid` 구역이 아예 없다는 식이다. 데이터는 다 들어왔지만 엔진은 여전히 Ascent만 플레이할 수 있었다.

## 시야 표: 지점 쌍당 1비트

14차 이동 엔진 개편 때 Ascent에는 위치 기반 시야 표 `ascent.vis.json`이 생겼다. 로드맵의 서 있을 수 있는 지점들 사이에서, 46m 이내의 모든 쌍에 대해 눈높이(1.6m)나 가슴 높이(1.1m)가 보이는지를 실제 삼각형과 교차 검사하고 쌍당 1비트로 저장한 표다. 15차 머지의 `3aadf2d`는 나머지 열 개 맵에 같은 생성기(`vis_map.py`)를 같은 조건으로 돌렸다.

결과는 맵마다 꽤 달랐다. 로드맵 지점은 Haven 867개에서 Breeze 2,671개까지였고, 검사한 쌍 중 보이는 비율은 Haven 13.4%, Pearl 14.2%부터 Icebox 27.7%, Breeze 31.6%까지 퍼졌다. Ascent는 17.4%다. 파일 크기는 Breeze가 581KB로 가장 컸고, 열한 개를 합쳐 1.96MB였다. 메시는 맵마다 저장소 밖에서 만들고 표를 뽑은 직후 지웠다.

표가 맞는지는 테스트 두 개로 본다. 보행 선분으로 이어진 두 지점은 서로 보여야 하고, 30m 이내의 두 구역이 구역 시야표에서 서로 보인다고 되어 있으면 두 구역의 서 있는 지점 중 어떤 쌍은 실제로 보여야 한다. 첫 번째는 모든 맵에서 100%였다. 두 번째에서 빠진 네 건은 테스트에 이름으로 박아 두었다. Ascent의 `a-window ~ a-site`는 위에서 본 손으로 넣은 시야선이고, 나머지 셋은 Pearl의 B Club이다. B Club의 콜아웃이 Mid Shops와 같은 x, y에 층만 다르게 겹쳐 있어서 엉뚱한 층에 서 있었다. 노드 수가 다른 로드맵에 맞춰 만든 표는 불러올 때 거부하고 구역 시야표로 돌아가게 했다. 표가 없거나 맞지 않아도 맵 로딩이 실패하지는 않는다.

이 파일을 커밋해도 되는지는 따로 정해야 했다. 맵의 IP는 Riot에 있고 Blender 원본의 재배포 라이선스는 확인되지 않았다. 11월 20일에 내가 로드맵(`<map>.nav.json`)을 커밋하기로 정했고, 같은 날 Ascent의 시야 표도 같은 결정에 넣었다. `docs/LICENSE_AUDIT.md` §2.0b에 그 범위가 적혀 있다. 로드맵에는 점과 선분만, 시야 표에는 지점 번호 쌍에 대한 비트만 있고, 삼각형, 정점, 격자 셀, 높이맵은 어떤 형태로도 없어서 이것만으로 메시를 복원할 수 없다. 15차의 열 개 맵 시야 표도 같은 범위로 기록했다. 다만 이건 내부 개발 저장소에 파생 좌표를 두는 결정이지 재배포 허가가 아니라서, 출시 전에 다시 검토해야 한다는 조건이 같이 붙어 있다.

## 자기 지형으로 돌려 보니

시야 표가 생겨도 경기는 여전히 Ascent에서 돌았다. `MatchConfig.map`은 숙련도와 스카우팅, 기록에만 쓰였다. 15차에서 옵트인 스위치를 하나 넣었다.

```ts
export function geometryOf(config: Pick<MatchConfig, "map" | "geometry">): string {
  if (config.geometry !== "own") return "ascent";
  const id = config.map.trim().toLowerCase();
  if (!isMapId(id)) throw new Error(`MatchConfig.geometry "own": no spatial data for map "${config.map}" (available: ${MAP_IDS.join(", ")})`);
  return id;
}
```

기본값은 그대로 `"ascent"`라서 데스크톱 앱과 시리즈 계층은 바뀌지 않는다. `sim-batch --geometry own`을 주면 이름 붙은 맵을 그 맵의 구역 그래프, 로드맵, 시야 표로 돌린다.

맵마다 60경기씩 돌린 결과가 `NAVIGATION_ENGINE.md` §7.5에 있다. 이 측정은 `sim-batch`가 팀 id를 잘못 읽던 버그를 고치기(`6bfb689`) 40분쯤 전이라, 모든 선수가 0.6인 미러 경기 조건이다. 수준을 실제와 비교할 숫자는 아니고 맵 사이의 차이만 볼 수 있다. 공격 승률은 Haven 0.390부터 Sunset 0.575까지 나왔다. 한쪽이 0.60을 넘은 건 Haven의 수비(0.61) 하나였다. 더 눈에 띈 건 라운드가 끝나는 방식이었다. Split은 전멸로 끝난 라운드가 36%뿐이고 폭발 34%, 해체 28%였다. Sunset도 전멸이 46%였다. 실측 Ascent는 전멸 0.714, 폭발 0.082다.

같은 맵을 시야 표 없이 구역 시야로 돌려 보면 Split의 전멸 비율은 0.815로 돌아온다. 그렇다고 시야 표가 틀린 건 아니었다. 표는 위의 검사를 모든 맵에서 통과했다. 원인은 전술 계층이었다. 수비가 어디에 서고 어디를 조준하는지, 설치 후 공격이 어디서 스파이크를 지키는지가 전부 Ascent 구역 id로 쓰인 표였고, 구역 시야에서는 그게 가려져 있었다. 구역 시야에서는 사이트 구역에 있기만 하면 어느 쪽을 보든 사이트 전체를 "봤다". 실제 시야에서는 스파이크가 보이는 곳에 서서 그쪽을 봐야 한다. 그래서 Split에서는 해체의 60%, Haven에서는 80%가 공격수가 살아 있는 채로 끝났다. 수비 한 명이 스파이크까지 걸어가서 7초 동안 아무에게도 보이지 않고 해체했다.

Haven은 더 심했다. 정책이 조준하라고 지시하는 구역 3개와 연막 대상 5개 중 Haven에 존재하는 건 하나도 없었다. 시작 위치도 Ascent 것이었고, C 사이트는 공격도 수비도 하지 않았고, B Site는 로드맵에서 아예 닿을 수 없었다. 설치의 절반이 킬 하나 없이 이뤄졌다. 이 단계에서는 아무것도 다시 맞추지 않았다. 교전, 속도, 정책 상수를 어느 맵에서도 바꾸지 않았고, 측정한 원인만 문서에 적고 15차에 머지했다.

## 맵에서 전술을 뽑는다

같은 날 `557b672`에서 맵별 전술 데이터를 맵 자체에서 계산하게 했다. 열 개 맵에 손으로 표를 쓰는 대신, 구역 그래프와 이동 시간과 시야선만으로 모든 맵에 같은 규칙을 적용한다. `spatial-engine/src/tactics.ts` 머리 주석이 규칙을 그대로 적고 있다.

```ts
//   main entry      the zone before the site on the attackers' fastest route ATK → site — the
//                   choke the attack comes through (the round simulator's default hold direction)
//   ...
//   mid anchor      among zones of type "mid" that the defenders reach first (t(DEF→z) ≤ t(ATK→z)):
//                   the one the attack reaches soonest after them (least t(ATK→z) − t(DEF→z)) —
//                   the forward edge of what the defense can hold. If the defenders are first to
//                   none, the zone where the two arrive closest to together, but only if the
//                   defenders are at most MID_LATE_MS behind; otherwise the map has no mid anchor
```

공격이 가장 빨리 사이트로 가는 경로에서 사이트 바로 앞 구역이 주 진입로이고, 수비는 그곳을 조준한다. 연막은 주 진입로와, 수비 쪽에 있으면서 사이트가 보이는 구역 최대 두 개다. 미드 거점은 수비가 먼저 도착하는 미드 구역 중 공격이 가장 바짝 따라오는 곳, 즉 수비가 지킬 수 있는 앞선이다. 수비 다섯 명의 시작 위치는 사이트마다 한 명, 그다음 미드 거점, 나머지는 공격이 빨리 닿는 사이트 순서로 채운다. 손으로 고칠 값이 있으면 `<map>.tactics.json`에 넣는데, 지금은 Ascent에만 있다. Ascent는 이 파일로 기존 미드 조준과 연막 목록을 유지했고, 그래서 파생된 Ascent 전술이 예전 표와 같아졌다. 경기 서명 해시가 main과 같다는 것까지 확인했다.

같은 커밋에서 전략 어휘에 C가 들어갔다(`cExecute`, `stackC`). IGL의 사이트 선택과 라운드 중 전환이 사이트 목록을 받게 됐고, 사이트가 둘인 맵은 예전 코드 경로를 그대로 탄다. 이어진 커밋들은 시야를 전술에 붙였다. 사이트를 지키는 선수는 자기가 지켜야 할 곳이 보이는 지점에 서고, 설치 후 공격은 스파이크가 보이는 곳에 선다. 리테이크에서는 가장 가까운 수비 한 명이 스파이크로 가고 나머지는 스파이크가 보이면서 가장 덜 노출된 지점으로 간다(`27bac33`). 사이트마다 진입로별 표준·오프앵글 홀딩 지점과 기본·안전·개방 설치 지점도 열한 개 맵 모두에 파생했다(`fc74531`). 다만 여기서 `cover`는 측정한 노출도의 순위일 뿐 몸을 가리는 엄폐를 잰 값은 아니라고 적혀 있다.

## 끊긴 구역을 하나씩 잇기

전술을 맵에서 뽑으려면 모든 구역이 이어져 있어야 한다. 맵 세션은 끊긴 곳을 하나씩 찾아가며 메웠고, 원인은 맵마다 달랐다.

Abyss의 A Secret과 B Danger는 바로 옆 바닥에서 2.0~2.5m 떨어진 난간이었고, 사이에는 아무것도 없었다. 측정한 셀 사이에 `kind: "jump"` 연결 네 개를 넣었다(`99427ea`). 그 간격을 양방향으로 점프할 수 있다는 건 측정이 아니라 게임 지식이라고 문서에 따로 적었다. Icebox의 A Nest는 높이 5.70의 119셀짜리 섬이었고, 장면에 있는 어센더 오브젝트 여섯 개 아래에서 로프와 집라인을 측정해 이었다(`a42c3a7`). Split의 Mid Vent는 문간 바닥 밑에 매달린 조명 하나(`BalconyScaffolding_0_LightFixtureA.007`)의 면이 바닥 층에 섞여서 자기 셀을 막고 있었다. 그 오브젝트 하나를 격자에서 빼자 걸어서 이어졌다(`fecde40`).

Haven B Site와 Pearl은 콜아웃 자체가 바닥 위에 있지 않았다. Haven B Site의 콜아웃은 사이트 가운데 구조물 지붕에 있었고, Pearl의 다섯 구역은 건물 안이나 Mid Shops 위층에 겹쳐 있었다. 구역이 실제로 서는 바닥 지점을 지정하는 `zoneAnchors` 키를 새로 만들어 고쳤다. 이 작업을 하던 하위 에이전트는 다시 생성한 내비 그래프를 커밋된 것과 비교하던 중에 사용량 한도에 걸렸고, 통합 세션이 그 상태를 `wip` 커밋(`b0ed5ed`, `11ec870`)으로 저장했다. 한도가 풀린 뒤 Haven 420/420, Pearl 650/650 구역 쌍이 연결되는 것까지는 확인했지만, 바뀐 간선 시간과 시야선이 모두 의도한 것인지는 아무도 검토하지 않았다고 인계서에 남아 있다.

Bind의 텔레포터에서는 이동 엔진 버그가 나왔다. 텔레포터 안에 있는 선수에게 새 목표를 주면 남은 이동이 출구까지 직선 걷기로 바뀌었다. 2.3km와 13.2km짜리 직선이 달리기 속도로, 바닥에서 838uu 떠서 그려졌다. 수비가 Bind 자기 위치에서 출발하게 되면서 Bind 바닥 테스트가 깨진 덕에 드러났다. 이동 중인 연결은 경과 시간과 함께 유지하도록 `mover.ts`를 고쳤다(`60ef687`). 텔레포터 양 끝도 구역 기준점이 아니라 프레임 아래 셀과 도착 방 바닥 가운데로 다시 측정했다(`bde66f4`). 이동 시간 1.5초는 여전히 추정값이다.

이렇게 찾은 오브젝트는 `<map>.objects.json`에 점과 종류로만 모았다. 낙하 높이가 붙은 한 방향 낙하, 로프·집라인·텔레포터·점프, 문, 부서지는 물체가 들어간다. 소리가 나는 위치는 기록했지만 `soundRadiusUu`는 `null`, `soundVerified`는 `false`다. 잰 값이 없으니 비워 둔 것이다. 로프 이동 시간도 달리기 속도 6.75m/s로 길이를 나눈 값이라고 적혀 있다. 궁극기 오브는 모든 맵에서 비어 있다. 오브젝트 이름에서 Orb, Ult, Ultimate, Pickup을 찾았지만 정적 장면에는 없었고(오브는 게임 중에 생성되는 액터다), 위치를 추측하지 않았다. Ascent의 문짝과 A 스위치, Lotus의 회전문과 부서지는 벽, Icebox Mid Boiler 로프처럼 장면에서 찾지 못한 것은 `notLocated`에 이유와 함께 들어갔다. 19차 시점에는 모든 맵에 근사 연결이 하나도 남지 않았고, 테스트의 `ROADMAP_GAPS` 목록도 비었다.

## 그래도 기본값은 Ascent

19차 머지 직전, 실제 로스터로 각 맵을 60경기씩 다시 돌렸다(Ascent는 기본 지형 160경기). 목표는 공격 승률 0.42~0.58, 전멸 약 0.60~0.75, 폭발 약 0.15 이하다.

| 맵 | 공격 / 전멸 / 폭발 / 해체 | 판정 |
|---|---|---|
| Ascent | 0.455 / 0.728 / 0.085 / 0.136 | 6/8 |
| Abyss | 0.507 / 0.618 / 0.163 / 0.155 | 7/9 |
| Bind | 0.501 / 0.572 / 0.237 / 0.104 | 3/8 |
| Breeze | 0.522 / 0.764 / 0.085 / 0.122 | 6/8 |
| Fracture | 0.482 / 0.540 / 0.279 / 0.155 | 6/8 |
| Haven | 0.489 / 0.416 / 0.236 / 0.288 | 4/8 |
| Icebox | 0.454 / 0.578 / 0.218 / 0.181 | 4/8 |
| Lotus | 0.493 / 0.475 / 0.204 / 0.255 | 4/8 |
| Pearl | 0.421 / 0.585 / 0.212 / 0.170 | 3/8 |
| Split | 0.496 / 0.594 / 0.209 / 0.172 | 3/8 |
| Sunset | 0.519 / 0.582 / 0.202 / 0.174 | 4/8 |

공격 승률은 열한 개 맵 모두 범위 안에 들어왔다. Haven은 0.390에서 0.489가 됐다. 하지만 여덟 개 맵에서 라운드의 5분의 1 이상이 폭발로 끝나고 전멸은 0.60 아래다. 범위에 든 건 Breeze 하나였고, Abyss는 폭발이 0.013 넘쳤다. 통합 세션도 같은 조합을 따로 재서 같은 결론을 냈다. 그래서 `geometry: "own"`은 옵트인으로 남았다. 인계서의 마지막 단계에는 "모든 맵이 범위에 들어올 때만 기본값으로 제안하고, 그것도 별도 커밋으로"라고 적혀 있다.

Breeze의 "범위 안"도 믿을 만한 증거가 아니라는 측정이 같이 있다. Bind는 로드맵을 다시 생성하기 전(지점 두 개 적고, 텔레포터 끝이 3.5m 미만 움직였고, 구역은 같다)에는 0.502 / 0.751 / 0.135 / 0.083으로 범위 안이었다. 다시 생성한 뒤에는 위 표의 3/8이다. 홀딩 지점을 로드맵 노드 중에서 고르기 때문에 노드가 조금만 바뀌어도 지점이 움직인다. 한 로드맵에서 60경기가 범위에 들었다는 건 약한 증거다.

원인을 잘못 짚었다가 바로잡은 기록도 있다. Split과 Bind의 경기 기록을 몇 개 보고는 연속 킬을 의심했다. 결투에서 이긴 선수가 결투의 처치 시간과 상관없이 다음 100ms 틱에 바로 다시 싸울 수 있어서, 스파이크를 지키는 공격수 한 명이 0.3초 안에 두 명을 잡는 장면이 보였기 때문이다. 그런데 맵별로 재 보니 한 선수가 2.5초 안에 세 명을 잡는 라운드가 Ascent에서 58%로, 기준을 못 맞춘 맵들보다 오히려 많았다. 전투 루프의 성질이지 맵을 가르는 원인은 아니었다. 확인된 건 모든 맵에서 폭발이 수비 1~2명 대 공격 약 4명 상황에서 일어난다는 것, 즉 설치 시점에 수비가 이미 사이트 싸움에서 졌고 살아남은 수비는 되찾지 못한다는 것까지다. 왜 Ascent 밖에서는 설치 전 싸움을 더 자주 지는지는 "확인되지 않음"으로 적혀 있다.

이번에도 어느 맵에서도 교전 확률, 속도, 전역 상수는 바꾸지 않았다. 열한 개 맵은 데이터로는 다 갖춰졌지만, 기본 경기는 여전히 Ascent 지형에서 돈다. 남은 건 리테이크에서 수비가 한 명씩 엄폐를 떠나는 문제, 상대 모델이 아직 A와 B만 아는 문제, 그리고 Haven과 Pearl의 데이터 수정 검토다.
