## 1. 시간 초과: 500ms마다 마음이 바뀌는 선수

원인을 찾은 것은 코어 세션(PV-3)입니다.
팀 정책은 500ms마다 선수별 명령을 가중 추첨으로 다시 뽑습니다(6편).
그런데 스파이크 설치에는 4초가 걸립니다.
결정 여덟 번 연속으로 "설치"가 뽑혀야 설치가 끝납니다.

중간에 한 번이라도 "피킹"이나 "홀드"가 뽑히면 설치 진행도가 0으로 돌아갑니다.
로그에는 이렇게 남았습니다.
"dozens of plantStart, zero planted."
설치 시작은 수십 번, 설치 완료는 0번.

해체도 대칭으로 망가져 있었습니다.
7초짜리 해체가 끝날 리 없었습니다.
처음에 스파이크 소지자만 고치자 이번엔 모든 설치가 폭발로 끝났고, 경기가 공격 쪽으로 기울어 끝나지 않다가 30대30 라운드 상한에 걸렸습니다.
그래서 수비 쪽도 같이 고쳤습니다.

```ts
// packages/team-engine/src/policy.ts — b739123 (commitSpikeCarrier 발췌)
    const holderId = view.spike.holderId;
    const phase = view.spike.phase;
    const canPlant = phase === "carried" || phase === "planting" || phase === "dropped";
    if (view.side !== "attack" || !holderId || !canPlant || strategy === "save") return out;

    const carrier = view.teammates.find((p) => String(p.id) === String(holderId) && p.alive);
    if (!carrier) return out;

    const carrierZone = this.spatial.nearestZone({ x: carrier.position.x, y: carrier.position.y });
    let command: ActionCommand;
    if (this.spatial.isPlantableZone(carrierZone)) {
      command = { playerId: carrier.id, kind: "plant", targetZone: carrierZone, executeAtMs: 0, sourceActionId: "carrier-commit:plant" };
    } else {
      const site = this.nearestPlantableSite(carrierZone);
      if (!site) return out;
      command = { playerId: carrier.id, kind: "move", targetZone: site, moveMode: "run", executeAtMs: 0, sourceActionId: "carrier-commit:move" };
    }
```

스파이크 소지자 한 명의 명령만 덮어씁니다.
설치 구역에 있으면 설치, 아니면 가장 가까운 설치 구역으로 달리기.
나머지 네 명의 추첨은 그대로 둡니다.
`save` 전략일 때는 적용하지 않습니다. 에코 라운드에 혼자 자살하러 설치하러 가지 않게 하려는 것입니다.
해체 쪽(`commitDefuser`)도 같은 모양입니다.

결과(20경기, 428라운드)입니다.

그리고 새로운 편향 두 개가 생겼습니다.
**모든 라운드에서 설치가 일어나고, 폭발은 0이 됐습니다.**
공격이 항상 설치에 성공하고, 수비는 항상 리테이크를 갑니다.
이 두 줄은 이 글의 마지막 절에서 다시 만납니다.

채점표에 "어느 사이트에 설치했나"가 없어서 이 부작용은 보이지 않았습니다.

## 2. 오프닝 듀얼: 자리를 지키지 않는 수비수

다음으로 크게 어긋난 것은 오프닝 듀얼(공격 75.0%, 실측 43.7%)이었습니다.

교전 엔진은 멈춰 있는 수비수에게 미리 조준하는 이점을 줍니다(7편).
`preAim = 적을 봤고 && 적은 나를 못 봤고 && 멈춰 있음`.
그런데 PV-4가 만든 진단 도구(`engagementTrace`)로 첫 교전 순간의 자세를 보니, 대본 정책의 수비수는 첫 교전 때 움직이고 있는 비율이 0%였고, PV-3 팀 정책의 수비수는 100%였습니다.

원인은 역시 추첨이었습니다.
설치 전 결정의 약 28%에서 수비수가 "이동"이나 "세이브"를 뽑아 앵커 자리를 떠났습니다.
자리를 지키는 대본 정책은 공격 오프닝을 0.45 정도로 막았는데, 팀 정책은 0.75를 내줬습니다.

수정은 세 단계로 들어갔습니다.

1. `630e01c`: 홀드 계열 전략(기본 수비, A 스택, B 스택)이고 설치 전이면, 수비수의 이동·세이브를 홀드로 바꿉니다. "전진(aggroPush)"은 의도적인 푸시이니 추첨에 맡깁니다.
2. `0e4f82d`: 홀드하는 수비수는 입구를 `aimZone`으로 겨눕니다(7편의 바라보는 방향 수정을 사용).
3. `bc5bc88`: 7편의 피커 이점(210ms)이 들어간 뒤로는, **피킹하는 수비수가 오히려 불리한 쪽(움직이는 쪽)** 이 됐습니다. 그래서 피킹도 홀드로 바꿨습니다.

```diff
// git show bc5bc88 -- packages/team-engine/src/policy.ts
-      // Hold the angle: a move/save off the anchor trades away the pre-aim edge. Peeks (stationary
-      // info) and ability use are kept. ...

+      // Hold the angle: move/save/peek off the anchor all trade away the pre-aim edge, and under
```

세 번째 단계가 흥미롭습니다.
엔진 쪽(PV-4)에서 피커 이점을 넣자, 정책 쪽(PV-3)에서 "수비수의 피킹"이 갑자기 나쁜 선택이 됐습니다.
한 세션의 보정이 다른 세션의 정책을 다시 고치게 만든 것입니다.
그리고 이게 현실과도 맞습니다.
실제 발로란트에서도 수비수가 먼저 피킹하면 불리합니다.

## 3. 공격 62%는 누구 탓인가

5차 머지(20:44) 뒤에도 공격 승률은 0.619였습니다.
실측 0.509보다 11%p 높습니다.
여기서 PV-3가 격리 실험을 했습니다.
**팀 정책을 빼고, 대본 정책끼리 붙여 봤습니다.**

0.633이 나왔습니다.

정책을 바꿔도 공격 승률이 같다면, 원인은 정책이 아닙니다.
PV-2가 하네스 현실성 감사(`HARNESS_REALISM_AUDIT.md`)로 원인을 짚었습니다.

- 시나리오가 수비 5명을 처음부터 사이트에 고정 배치했습니다(A에 2명, B에 2명, 미드에 1명).
- 경기 진행기가 스킬 없이 라운드를 돌렸습니다. 연막도, 섬광도, 몰리도 없습니다.
- 그러니 공격 5명이 한 사이트에 도착하면, 그곳의 수비는 2명입니다. **국지적 5대2.**

결론은 "엔진이나 정책의 버그가 아니라 하네스 현실성의 공백"이었습니다.
감사는 측정 정의도 점검했습니다.
공격 승률, 종료 사유 분류, 첫 킬 정의는 실측과 1:1로 같았습니다.
정의는 같은데 조건(스킬, 수비 배치)이 다르다는 것입니다.

그래서 보고 규칙이 하나 생겼습니다.

> 스킬이 켜지고 수비 셋업이 다양해지기 전까지, sim-batch 수치는 "기준 대비 추세"로만 읽는다. 실측에 보정된 값으로 읽지 않는다.

이 규칙이 지금 이 연재의 숫자들을 읽는 방법이기도 합니다.
4/8은 "실제 VCT와 절반이 맞는다"가 아니라 "처음보다 네 개 더 맞는 방향으로 왔다"입니다.

PV-2는 수비 셋업 데이터를 세 가지 만들었습니다.
`standard-2-1-2`(가중치 2), `a-stack-3-1-1`, `mid-control-2-2-1`.
라운드마다 시드로 결정적으로 고릅니다.
그리고 이 셋업은 스킬을 켰을 때만 적용합니다.

## 4. 스킬을 켜면

스킬을 켜면 문제가 반대로 뒤집혔습니다.
6편에서 경기 진행기의 주석을 소개했습니다.
"스킬을 켜면 수비가 압도적이 된다(공격 승률 약 0.02)."
실제로 처음엔 약 1%였습니다.

### 시전하는 쪽이 진다

7편에서 다룬 이야기입니다.
PV-3가 시전 효과만 분리해 측정해 보니(300시드, 멀리 던지는 정찰 스킬), 공격만 시전하면 공격 오프닝 0.007, 수비만 시전하면 0.987이었습니다.
스킬 시전이 결정 틱의 행동 전체를 차지하고 있었습니다.
PV-4가 시전 모델을 "시전 시간(windup) 동안만 무기를 못 든다"로 바꿨습니다(`782030d`).

### 스킬을 덜 쓰게

그다음엔 정책 쪽입니다(`61b6d70`).

```ts
// packages/team-engine/src/player-policy.ts (61b6d70)
  // Casting occupies the weapon (windup) — over-casting loses duels. Keep stochastic ability use
  // RARE so it reads as opportunistic; coordinated execute/retake utility goes through the policy's
  // commitAttackUtil/defender paths, not this draw.
  if (kind === "individual.useAbility") w *= 0.25;
```

1. 선수 개인의 추첨에서 스킬 가중치를 0.25배로 줄였습니다. 아무 때나 스킬을 쓰지 않게.
2. 진입할 때의 유틸은 추첨이 아니라 팀 정책의 확정 경로(`commitAttackUtil`)로 조율합니다. 진입 시점 기준 3.5초, 7초 창 안에, 2편의 전술 지식 베이스에서 가져온 연막 목표(`SMOKE_TARGETS`)로.
3. 설치 후에는 3초 안에 닿는 공격수들이 스파이크 구역을 겨누고 홀드합니다(`commitPostPlantContest`).

결과(20경기, 스킬 켬): 공격 0.197 → **0.411**, 해체 0 → 0.160 **통과**.
오프닝 0.647은 여전히 높았고, 폭발은 여전히 0이었습니다.

### 연막을 칠 사람이 스파이크를 들고 있었다

`1867674`에서 재미있는 문제가 하나 더 나왔습니다.
스킬을 켰을 때 스파이크를 컨트롤러(atk1, Omen)가 들고 있었습니다.
그런데 1절의 수정 때문에 스파이크 소지자는 무조건 설치하러 달려갑니다.
**연막을 쳐야 할 사람이 연막 대신 스파이크를 들고 달리고 있었습니다.**

스킬을 켰을 때는 센티넬(atk4)이 스파이크를 들게 바꾸고, 진입 연막 목표에 앞쪽 입구를 추가했습니다(A 사이트는 A 메인·래프터·와인, B 사이트는 B 메인·보트하우스).
오프닝 0.453 통과, 해체 0.23, 공격 0.269.

### 동시에 맞출 수 없었다

6차 머지(21:03) 시점의 정리입니다.

| 설정 | 공격 승률 | 비고 |
| --- | --- | --- |
| 스킬 끔 (기본값) | 0.619 | 판정 3/8 |
| 스킬 켬, 셋업 끔 | 0.41 | |
| 스킬 켬, 셋업 켬 | 0.25 | 오프닝 0.469 통과 |

목표는 "공격 승률 0.45~0.56과 판정 3/8 이상을 동시에"였습니다.
달성하지 못했습니다.
셋업 가중치, 유틸 위력, 진입 유틸을 같이 조정해야 하는 문제로 남겼고, 스킬은 지금도 기본값이 꺼짐입니다.

이 과정에서 지킨 장치가 하나 있습니다.
**스킬 켬 경로의 모든 변경은, 스킬 끔 결과를 바이트 단위로 바꾸지 않는다.**
커밋마다 "abilities-off byte-unchanged"를 확인했습니다.
그래서 스킬 쪽에서 아무리 실험을 해도 기본 시뮬레이션의 3/8은 흔들리지 않았습니다.

## 5. 스파이크는 왜 터지지 않았나

마지막 남은 큰 구멍은 폭발이었습니다.
실측에서는 라운드의 8.2%가 스파이크 폭발로 끝납니다.
시뮬레이션은 스킬을 켜든 끄든, 어떤 정책을 바꾸든 **0**이었습니다.

6차 머지 뒤 기록된 추정은 이랬습니다.
"정책이 아니라 시뮬레이터 구조(설치 후 스파이크 타이머 대 리테이크 타이밍) 문제로 추정. 다음 스프린트 1순위(PV-4)."

틀린 추정이었습니다.
원인은 정책이었고, 1절의 바로 그 수정이었습니다.
해체가 끊기지 않도록 해체 담당을 고정한 `commitDefuser`가, 상황과 무관하게 **항상** 리테이크를 하게 만들고 있었습니다.
수비가 항상 해체하러 가면 설치 라운드는 두 가지로만 끝납니다.
해체에 성공하거나, 해체하러 온 수비가 전멸하거나.
스파이크가 터질 때까지 기다려 주는 수비가 없으니, 폭발은 구조적으로 0입니다.

실제 프로 경기에서 스파이크가 터지는 라운드는 대부분 수비가 리테이크를 **포기한** 라운드입니다.
1대4로 남은 수비수는 해체하러 가지 않고 무기를 들고 도망칩니다.
4편의 세이브 계산이 정확히 이 상황입니다.

수정(`b00eaa2`, 8차 머지)은 리테이크 가능성 판단입니다.

```ts
// packages/team-engine/src/policy.ts (b00eaa2)
   * Threshold sweep (sim-batch, 20 matches, Ascent): 1v3+ → 12.8% detonations, 1v4+ → 9.0%,
   * down-3 → 24%; real 8.2%, so the lone-defender 1v4+ rule is used.
   */
  private retakeViable(view: PolicyView, defendersAlive: number, defuserTravelMs: number): boolean {
    const timer = view.spike.detonationInMs;
    if (timer != null && defuserTravelMs + DEFUSE_DURATION_MS > timer) return false;
    const attackers = view.knownEnemyAliveCount;
    if (attackers == null) return true;
    return !(defendersAlive <= 1 && attackers >= LONE_SAVE_MIN_ATTACKERS);
  }
```

두 조건 중 하나라도 맞으면 해체를 포기하고 수비 스폰으로 물러납니다.

- (a) 해체 담당이 스파이크까지 가는 시간 + 해체 7초가 폭발까지 남은 시간보다 길 때. 갈 수는 있지만 해체할 시간이 없습니다.
- (b) 수비 1명 대 공격 4명 이상일 때.

난수를 쓰지 않는 결정적 규칙이고, 결정마다 다시 평가합니다.
도망가다 킬을 따서 인원이 바뀌면 다시 리테이크를 갑니다.

(b)의 임계값은 감으로 정하지 않았습니다.
`sim:batch`로 세 가지를 돌려 보고 실측에 가장 가까운 것을 골랐습니다.

| 포기 조건 | 폭발 비율 |
| --- | --- |
| 1대3 이상 | 12.8% |
| **1대4 이상** | **9.0%** |
| 3명 이상 열세 | 24% |
| 실측 | 8.2% |

3편에서 만든 채점기가 이렇게 쓰이기 위해 존재했습니다.
규칙 후보를 몇 개 만들고, 같은 20경기에 돌리고, 실측에 가까운 것을 고른다.

결과(20경기, 410라운드): 폭발 0.000 → **0.090 통과**, 판정 3/8 → **4/8**.
공격 승률은 0.617로 거의 그대로였고, 시간 초과·오프닝·피스톨은 통과를 유지했습니다.
스킬을 켠 경우는 1/8 → 2/9.

## 정리: 숫자를 쫓는 법에 대해

이 열두 시간의 수정 다섯 개를 나란히 놓으면 패턴이 보입니다.

| 수정 | 고친 숫자 | 새로 만든 문제 |
| --- | --- | --- |
| 스파이크 소지자 고정 | 시간 초과 | 설치가 항상 B, 공격 과다 |
| 해체 담당 고정 | 시간 초과 | 폭발 0 |
| 수비 홀드 고정 | 오프닝 듀얼 | (피커 이점과 맞물려 피킹 금지로 확장) |
| 스킬 시 센티넬이 스파이크 | 스킬 켬 진입 | — |
| 리테이크 포기 규칙 | 폭발 | — |

다섯 개 중 네 개가 같은 모양입니다.
**"500ms마다 다시 추첨하는 선수"를 특정 상황에서 고정한다.**
6편의 팀 엔진이 가진 근본적인 성질, 즉 매 순간 행동을 새로 고르는 구조가 실제 경기의 "한번 정하면 끝까지 하는" 행동과 맞지 않았고, 그 차이를 확정 규칙으로 하나씩 메운 것입니다.
그리고 확정 규칙은 그 순간의 숫자를 고치면서, 다음 숫자의 문제를 만들었습니다.

언젠가는 이 확정 규칙들을 "의도(intent)를 유지하는 정책"으로 바꿔야 할 것입니다.
한번 A 진입을 부르면 진입이 끝날 때까지 그 계획을 유지하고, 계획이 깨지는 사건(진입수 사망, 적 로테이션)이 있을 때만 다시 고르는 구조입니다.
그러면 6편의 "스파이크는 항상 B로" 문제도 자연스럽게 사라질 것입니다.

그리고 끝까지 지켜진 원칙들이 있습니다.

1. 라운드 통계를 맞추려고 교전 숫자를 비틀지 않는다.
2. 보정값은 모든 정책에 하나("one truth").
3. 실험 경로(스킬 켬)는 기본 결과를 바이트 단위로 바꾸지 않는다.
4. 새 규칙은 난수를 쓰지 않아서 기존 난수열을 보존한다.
5. 정의가 같아도 조건이 다르면 "추세로만" 읽는다.

이 원칙들 덕분에 4/8은 "어딘가에서 숫자를 억지로 맞춘 4/8"이 아니라, 원인을 하나씩 고친 4/8이 됐습니다.
나머지 넷은 아직 원인을 고치지 못한 것들이고, 그 원인이 어디 있는지는 대략 알고 있습니다.

다음 편이 마지막입니다.
AI 세션 여섯에게 게임 엔진을 맡겨 보고 배운 것을 정리합니다.
