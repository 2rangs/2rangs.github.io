15:05에 main에 들어간 시뮬레이션은 경기를 끝까지 돌릴 수는 있었지만, 거의 모든 라운드가 시간 초과로 끝났다. 그다음 열두 시간은 같은 일의 반복이었다. 3편에서 만든 채점기(`sim:batch`)로 20경기를 돌리고, 실제 VCT 통계와 비교하고, 가장 크게 벗어난 숫자의 원인을 고치고, 다시 돌린다. 한 지표를 고치면 다른 지표가 같이 움직여서 매번 전체를 다시 봐야 했다. 판정 지표 통과 수는 0/9에서 4/8까지 올라갔다.

## 채점표와 출발점

실측 기준은 VCT Reference의 국제전 Ascent다. 라운드 종료 사유는 전멸 0.714, 해체 0.160, 폭발 0.082, 시간 초과 0.043이고, 공격 라운드 승률 0.509, 공격 측 오프닝 듀얼 승률 0.437이다. 허용 오차는 ±0.04, 구매 매치업(피스톨 대 피스톨, 풀 대 풀 등)은 칸마다 ±0.05다.

기준 스냅샷(통합 브랜치 `482a304`, 20경기 461라운드)의 판정은 "0/9 judged — attacker-broken"이었다.

| 지표 | 시뮬레이션 | 실측 |
| --- | --- | --- |
| 시간 초과 | 0.618 | 0.043 |
| 전멸 | 0.377 | 0.714 |
| 폭발 | 0.004 | 0.082 |
| 해체 | 0.000 | 0.160 |
| 공격 승률 | 0.197 | 0.509 |
| 공격 오프닝 듀얼 | 0.686 | 0.437 |

PV-2의 진단은 "공격이 첫 듀얼은 이기는데(0.686) 라운드는 진다(0.197)"였다. 총싸움은 이기는데 스파이크를 못 심고 시간을 다 쓴다는 얘기다. 그래서 가장 큰 지렛대는 사이트 도달과 설치라고 보고 거기서 시작했다.

손대기 전에 정해 둔 원칙이 하나 있었다. 마스터 프롬프트 31장과 PV-4의 첫 검증 문서에 같은 말이 있다.

> 교전 파라미터는 오프닝 듀얼로만 보정한다. 라운드 승률을 맞추려고 교전 파라미터를 왜곡하지 않는다.

공격 승률이 낮다고 명중률을 올리면 숫자는 금방 맞는다. 대신 공격이 지는 원인은 그대로 남고, 나중에 원인을 고치면 공격이 너무 강해진다. PV-4도 7편에서 공격 라운드 승률이 0.309에서 0.257로 떨어졌을 때 명중률 배율을 되돌리지 않고 원인(스파이크를 줍지 않는 정책)을 찾아 고쳤다. 이번 열두 시간의 수정 커밋에도 메시지마다 "NO combat/engagement parameter touched."가 들어 있다.

## 시간 초과: 500ms마다 바뀌는 행동

원인은 코어 세션(PV-3)이 찾았다. 팀 정책은 500ms마다 선수별 명령을 가중 추첨으로 다시 뽑는다(6편). 스파이크 설치는 4초가 걸리니 "설치"가 여덟 번 연속 뽑혀야 끝난다. 중간에 한 번이라도 "피킹"이나 "홀드"가 뽑히면 진행도가 0으로 돌아간다. 로그에는 "dozens of plantStart, zero planted."가 남았다. 7초짜리 해체도 같은 이유로 끝나지 않았다. 처음에 스파이크 소지자만 고쳤더니 모든 설치가 폭발로 끝나고 경기가 공격 쪽으로 기울어 30대30 라운드 상한에 걸렸다. 그래서 수비 쪽도 같이 고쳤다.

```ts
// packages/team-engine/src/policy.ts — b739123 (commitSpikeCarrier 발췌)
    const holderId = view.spike.holderId;
    const phase = view.spike.phase;
    const canPlant = phase === "carried" || phase === "planting" || phase === "dropped";
    if (view.side !== "attack" || !holderId || !canPlant || strategy === "save") return out;

    const carrier = view.teammates.find((p) => String(p.id) === String(holderId) && p.alive);
    if (!carrier) return out;

    const carrierZone = this.spatial.nearestZone({ x: carrier.position.x, y: carrier.position.y });
    let command: ActionCommand;
    if (this.spatial.isPlantableZone(carrierZone)) {
      command = { playerId: carrier.id, kind: "plant", targetZone: carrierZone, executeAtMs: 0, sourceActionId: "carrier-commit:plant" };
    } else {
      const site = this.nearestPlantableSite(carrierZone);
      if (!site) return out;
      command = { playerId: carrier.id, kind: "move", targetZone: site, moveMode: "run", executeAtMs: 0, sourceActionId: "carrier-commit:move" };
    }
```

스파이크 소지자 한 명의 명령만 덮어쓴다. 설치 구역에 있으면 설치하고, 아니면 가장 가까운 설치 구역으로 달린다. 나머지 네 명의 추첨은 그대로 두고, 에코 라운드에 혼자 설치하러 가지 않게 `save` 전략에서는 적용하지 않는다. 해체 쪽 `commitDefuser`도 같은 구조다.

20경기 428라운드를 다시 돌리니 시간 초과는 61.8%에서 0%가 됐다. 대신 공격 승률이 19.7%에서 61.7%로 뛰어 이번엔 실측보다 높아졌고, 공격 오프닝 듀얼은 75.0%, 해체 38.3%, 폭발 0%였다. 판정은 2/8. 모든 라운드에서 설치는 일어나는데 폭발은 하나도 없다는 문제가 생겼다. 이건 뒤에서 다시 나온다.

## 오프닝 듀얼: 자리를 지키지 않는 수비수

다음으로 크게 벗어난 건 오프닝 듀얼(공격 75.0%, 실측 43.7%)이었다. 교전 엔진은 멈춰 있는 수비수에게 미리 조준하는 이점을 준다(7편). `preAim = 적을 봤고 && 적은 나를 못 봤고 && 멈춰 있음`. PV-4의 진단 도구(`engagementTrace`)로 첫 교전 순간의 자세를 보니, 대본 정책의 수비수는 움직이고 있는 비율이 0%였고 PV-3 팀 정책의 수비수는 100%였다.

이번에도 추첨이 원인이었다. 설치 전 결정의 약 28%에서 수비수가 "이동"이나 "세이브"를 뽑아 앵커 자리를 떠났다. 자리를 지키는 대본 정책은 공격 오프닝을 0.45 정도로 막았고 팀 정책은 0.75를 내줬다. 수정은 세 번에 걸쳐 들어갔다. `630e01c`에서 홀드 계열 전략(기본 수비, A 스택, B 스택)일 때 설치 전 수비수의 이동·세이브를 홀드로 바꿨다. "전진(aggroPush)"은 의도한 푸시라 추첨에 맡겼다. `0e4f82d`에서 홀드하는 수비수가 입구를 `aimZone`으로 겨누게 했다. 마지막 `bc5bc88`은 7편의 피커 이점(210ms)이 들어간 뒤의 조정이다. 피킹하는 수비수가 움직이는 쪽이 되면서 불리해졌으니 피킹도 홀드로 바꿨다. 엔진 쪽(PV-4)에서 피커 이점을 넣자 정책 쪽(PV-3)이 선택을 다시 맞춘 경우다. 실제 발로란트에서도 수비가 먼저 피킹하면 불리하니 방향은 맞다.

4차 머지(20:00) 뒤 20경기 445라운드에서 판정은 3/8이 됐다. 전멸 0.710(실측 0.714), 시간 초과 0.034, 풀 대 풀 0.487이 통과했고, 공격 승률 0.587, 오프닝 듀얼 0.575, 해체 0.256, 폭발 0.000은 실패였다. 오프닝 듀얼은 5차 머지 이후(피커 이점 재보정 포함) 0.474로 내려와 통과했다.

## 공격 승률 62%는 정책 탓이 아니었다

5차 머지(20:44) 뒤에도 공격 승률은 0.619로 실측보다 11%p 높았다. PV-3가 팀 정책을 빼고 대본 정책끼리 붙여 봤더니 0.633이 나왔다. 정책을 바꿔도 같으면 원인은 정책 밖에 있다.

PV-2의 하네스 현실성 감사(`HARNESS_REALISM_AUDIT.md`)가 원인을 정리했다. 시나리오가 수비 5명을 처음부터 사이트에 고정 배치했다(A에 2명, B에 2명, 미드에 1명). 경기 진행기는 스킬 없이 라운드를 돌렸다. 연막도 섬광도 몰리도 없으니, 공격 5명이 한 사이트에 도착하면 거기 수비는 2명, 국지적으로 5대2가 된다. 감사의 결론은 "엔진이나 정책의 버그가 아니라 하네스 현실성의 공백"이었다. 공격 승률, 종료 사유 분류, 첫 킬 정의는 실측과 1:1로 같았다. 정의는 같은데 조건(스킬, 수비 배치)이 달랐다.

그래서 보고 규칙을 하나 정했다.

> 스킬이 켜지고 수비 셋업이 다양해지기 전까지, sim-batch 수치는 "기준 대비 추세"로만 읽는다. 실측에 보정된 값으로 읽지 않는다.

이 연재의 숫자도 그렇게 읽어야 한다. 4/8은 실제 VCT와 절반이 일치한다는 뜻이 아니라, 처음보다 네 개 지표가 실측 범위 안으로 들어왔다는 뜻이다. PV-2는 수비 셋업 세 가지(`standard-2-1-2`(가중치 2), `a-stack-3-1-1`, `mid-control-2-2-1`)를 만들고 라운드마다 시드로 결정적으로 고르게 했다. 이 셋업은 스킬을 켰을 때만 적용된다.

## 스킬을 켜면 반대로 수비가 이긴다

6편의 경기 진행기 주석에도 "스킬을 켜면 수비가 압도적이 된다(공격 승률 약 0.02)"라고 적혀 있고, 처음 잰 값은 약 1%였다. 7편에서 쓴 대로 PV-3가 시전 효과만 떼어 재 보니(300시드, 멀리 던지는 정찰 스킬) 공격만 시전하면 공격 오프닝 0.007, 수비만 시전하면 0.987이었다. 스킬 시전이 결정 틱의 행동 전체를 차지하고 있었다. PV-4가 시전 모델을 "시전 시간(windup) 동안만 무기를 못 든다"로 바꿨다(`782030d`).

정책 쪽은 `61b6d70`에서 시전 빈도를 낮췄다. 선수 개인 추첨에서 스킬 가중치를 0.25배로 줄여(`if (kind === "individual.useAbility") w *= 0.25;`) 아무 때나 스킬을 쓰지 않게 했다. 진입 유틸은 추첨 대신 팀 정책의 확정 경로(`commitAttackUtil`)로 맞췄다. 진입 시점 기준 3.5초, 7초 창 안에, 2편의 전술 지식 베이스에서 가져온 연막 목표(`SMOKE_TARGETS`)를 쓴다. 설치 후에는 3초 안에 닿는 공격수들이 스파이크 구역을 겨누고 홀드한다(`commitPostPlantContest`). 스킬을 켜고 20경기를 돌리니 공격 승률이 0.197에서 0.411이 됐고 해체는 0에서 0.160으로 통과했다. 오프닝은 0.647로 아직 높았고 폭발은 여전히 0이었다.

`1867674`에서는 스파이크를 누가 드는지를 바꿨다. 스킬을 켰을 때 컨트롤러(atk1, Omen)가 스파이크를 들고 있었는데, 앞의 수정 때문에 스파이크 소지자는 곧장 설치하러 가니 진입 연막을 칠 수가 없었다. 그래서 스킬을 켰을 때는 센티넬(atk4)이 스파이크를 들게 하고, 진입 연막 목표에 앞쪽 입구(A 사이트는 A 메인·래프터·와인, B 사이트는 B 메인·보트하우스)를 추가했다. 오프닝 0.453으로 통과, 해체 0.23, 공격 0.269.

6차 머지(21:03) 시점에 공격 승률은 스킬 끔(기본값)에서 0.619(판정 3/8), 스킬 켬·셋업 끔에서 0.41, 스킬 켬·셋업 켬에서 0.25(오프닝 0.469 통과)였다. 목표는 공격 승률 0.45~0.56과 판정 3/8 이상을 동시에 만족하는 것이었는데 아직이다. 셋업 가중치, 유틸 위력, 진입 유틸을 같이 만져야 하는 일로 남겼고, 스킬은 지금도 기본값이 꺼짐이다.

여기서 지킨 규칙이 하나 더 있다. 스킬 켬 경로의 변경은 스킬 끔 결과를 바이트 단위로 바꾸지 않는다. 커밋마다 "abilities-off byte-unchanged"를 확인했기 때문에 스킬 쪽 실험을 아무리 해도 기본 시뮬레이션의 3/8은 그대로였다.

## 폭발 0%: 항상 리테이크하는 수비

남은 큰 차이는 폭발이었다. 실측은 8.2%인데 시뮬레이션은 스킬 설정이나 정책과 상관없이 0이었다. 6차 머지 뒤에는 "정책이 아니라 시뮬레이터 구조(설치 후 스파이크 타이머 대 리테이크 타이밍) 문제로 추정. 다음 스프린트 1순위(PV-4)"라고 적었는데, 원인은 정책 쪽, 앞에서 만든 `commitDefuser`였다. 해체가 끊기지 않게 해체 담당을 고정했더니 상황과 상관없이 항상 리테이크를 갔다. 수비가 항상 해체하러 가면 설치 라운드는 해체 성공이나 수비 전멸로만 끝나고 폭발은 나올 수가 없다.

실제 프로 경기에서 스파이크가 터지는 라운드는 대부분 수비가 리테이크를 포기한 라운드다. 1대4로 남은 수비수는 해체하러 가지 않고 무기를 지키며 빠진다. 4편의 세이브 계산이 다루는 상황이 바로 이거다. 8차 머지의 `b00eaa2`는 리테이크가 가능한지를 판단하는 `retakeViable`을 넣었다. 해체 담당이 스파이크까지 가는 시간에 해체 7초를 더한 게 폭발까지 남은 시간보다 길거나, 수비 1명 대 공격 4명 이상이면 해체를 포기하고 수비 스폰으로 물러난다. 난수를 쓰지 않는 결정적 규칙이고 결정마다 다시 평가하니, 물러나다 킬을 따서 인원이 바뀌면 다시 리테이크를 간다. 임계값은 세 후보를 `sim:batch`로 돌려 골랐다. 1대3 이상이면 12.8%, 1대4 이상이면 9.0%, 3명 이상 열세면 24%였고, 실측 8.2%에 가장 가까운 1대4를 택했다. 후보를 몇 개 만들고 같은 20경기에 돌려 실측에 가까운 걸 고르는 것, 3편에서 채점기를 만든 이유가 이거였다.

20경기 410라운드에서 폭발은 0.000에서 0.090으로 통과했고 판정은 3/8에서 4/8이 됐다. 공격 승률은 0.617로 거의 그대로였고, 시간 초과·오프닝·피스톨은 통과를 유지했다. 스킬을 켠 경우는 1/8에서 2/9가 됐다.

8차 머지 때 기록된 숫자와 정확히 같다. 결정론 덕분에 다른 컴퓨터에서 하루 뒤에 돌려도 같은 결과가 나온다. 참고용 지표 중에는 5대3 상황 공격 승률 0.981이 있는데, 설치 후 리테이크 교전에서 공격 우위가 크다는 신호로 보이고 해체 비율이 실측보다 낮은 것(0.102 대 0.160)과 같은 방향이다. 실측에 인원 우위 승률 데이터가 없어서(3편) 판정에는 넣지 않았다.

열두 시간 동안 들어간 큰 수정 다섯 개 중 네 개(스파이크 소지자 고정, 해체 담당 고정, 수비 홀드 고정, 리테이크 포기 규칙)는 500ms마다 다시 뽑히는 행동을 특정 상황에서 고정하는 규칙이다. 나머지 하나는 스킬을 켰을 때 센티넬이 스파이크를 드는 것이었다. 6편의 팀 엔진은 매 순간 행동을 새로 고르는데, 실제 경기에서는 한번 정한 행동을 끝까지 하는 경우가 많다. 그 차이를 규칙으로 하나씩 메웠다. 다음에는 이 규칙들을, A 진입을 한번 부르면 진입수 사망이나 적 로테이션 같은 사건이 있을 때까지 계획을 유지하는 정책으로 바꿀 생각이다. 6편의 설치 사이트 쏠림도 같이 풀 계획이다. 공격 승률, 전멸, 해체, 풀 대 풀 네 지표가 남아 있고, 해체는 위의 리테이크 교전 공격 우위부터 볼 생각이다. 스킬 기본값을 켜는 건 공격 승률 0.45~0.56과 판정 3/8 이상을 같이 맞춘 다음이다.

> 덧붙임: 이 글의 `sim:batch` 숫자는 나중에 알고 보니 모든 선수가 리그 평균(0.6)인 미러 경기 조건에서 나온 것이었다. 검증 도구가 팀 id를 잘못 읽고 있었기 때문이다. 이 이야기와 실제 로스터로 다시 잰 결과는 13편에 적었다.
